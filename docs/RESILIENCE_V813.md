## 1. 现状（动手前核对过代码）

### 1.1 已经有的

- **写操作带操作编号**（幂等键）：同一个编号原样重提返回第一次的结果，内容不同拒绝；服务端行锁 + 数据库约束兜底。
- **「结果待确认」**：提交前本机先存原编号与原请求并读回核对，存不下就不发；超时、断网、写请求遇到 5xx 都不当成失败，按原编号查回、原样重提或经服务端确认作废（`lib/pendingOps`、`lib/erpPending`、前台与管家部各自的一份）。
- **请求**：15 秒超时；网关的 502 / 503 / 504 算网络问题。页面数据（React Query）不是 4xx 的自动重试 2 次，切回窗口重新取。
- **页面代码按需下载**，下载失败那一页显示「重新加载」按钮。
- **服务端**：每个事务等锁 5 秒、语句 10 秒，超了回 409「系统忙、没生效」（`BUSY`）；登录（Z4）、员工食堂登录与自己登记、供应商链接、对账链接各有失败次数限制；安全响应头（`nosniff`、不让别的网站嵌入、跳出去不带地址）；停机时先关端口再断数据库。
- **对外接口**：扫码收款、平台验券每分钟自己去查「支付中 / 核销中」，超时撤单（相当于 brandur 说的 completer）；短信待发箱认领后在事务外发送。

### 1.2 缺口（这一版补）

1. **页面不知道网络断了**：浏览器的「在线 / 离线」只看网卡，连着 Wi-Fi 但到不了服务器时照样当在线，页面一次次等满 15 秒；真断网时页面数据「暂停」，骨架一直转、没有任何提示。
2. **网络恢复后不会马上刷新**：要等切回窗口或各页自己的定时；「结果待确认」的自动查回最快一分钟，ERP 单据查回失败后要员工手点。
3. **后台刷新失败时旧数据照常显示**，看不出数据已经不是最新。
4. **一处出错整页白屏**（只有「页面代码没下载下来」有兜底）；系统更新后开着的页面去要已经换掉的文件，只能手动刷新，也不知道系统更新了。
5. **「系统忙」要人重做**：等锁超时已经回「没生效」，但页面直接报错让人再点一次；死锁（`40P01`）、串行化冲突（`40001`）回 500，写请求被当成「结果待确认」，要人去查回。
6. **断网时点了提交**：请求发不出去也要等满 15 秒，之后变成「结果待确认」——其实根本没发出去。
7. **服务端没有总量保护**：网络一恢复，几十台终端同时重新取数据、查回、重提，一下子涌进来；除了几个入口的失败次数限制，没有频率限制。
8. **卡住的事务一直占着行锁**；进程收到停止信号时没有时限，异常退出前不收尾。
9. **出了问题现场只能说「刷不出来」**：没有一处看得到本机的连接、版本、待确认与最近的问题；页面报错服务器不知道。

## 3. 设计

### 3.1 代码整洁（WL1、WL2）

1. **删掉没用到的代码**：主线 47 个文件（`c3a5586`）。小程序线剩 3 处（`src/server/modules/mp/coupon-center.ts` 的 `boundMember`、`tests/mp-member.test.ts` 的 `memberId`、`tests/mp-reminders.test.ts` 的 `MpReminderLeased`），在 PR 里告诉小程序线，主线不改。
2. **整洁检查**：`npm run check:code`（`scripts/check-code.mjs`），CI 跑，挂了不能合：
   - 没用到的导入、变量、参数（`tsc --noUnusedLocals --noUnusedParameters`，跳过小程序线的目录，那边由 Gemini 决定什么时候接上）；
   - 事务里没有不等结果的查询（`tx\`…\`` 写了却没 `await`、没 `return`、没交给 `Promise.all`），见第 2 节 postgres.js 一行；
   - 只用到类型的导入写成 `import type`。
3. **格式统一**：Prettier 3.8.5（固定版本，开发依赖），`.prettierrc.json`：单引号、行宽 200、对象照原来的写法换不换行（`objectWrap: preserve`）、不动模板字符串里的 SQL；`.prettierignore` 跳过小程序线目录、构建产物、文档与 JSON 样例。`npm run format` 改、`npm run format:check` 查（CI 跑）。全仓库一次排版放在单独一个提交（只动空白、引号与换行），记进 `.git-blame-ignore-revs`，`git blame` 跳过它；排版前后类型检查、构建、全量用例、逐屏截图核对都要一样。**别的分支合 `main` 之前先在自己的分支上跑一次 `npm run format`，冲突大多会消失。**
4. **重复与超大文件**：只做「拆出来以后行为一模一样、用例覆盖得到」的——导入预览的共用部件、两个需求单导入页、管家部 `Workspace.tsx` 按页签拆文件；收银的三个结账弹窗涉及钱，这一版不合并（第 4 节）。实际做了哪些写在交接说明。
5. **各模块自己写的轮询**（客户部、管家部各几处 3 秒一次、自己听 `online`、`focus`）改用共用的 `useLivePoll`：断网时停、恢复马上取一次，后台标签页不取。

### 3.2 页面知道网络断了、恢复后自己刷新（WL3、WL4）

- **连接状态**（`lib/connection.ts`）：
  - 平时不额外发请求：每个请求收到服务器的回应就记「刚连上过」；请求发不出去、超时、网关 502 / 504 时马上去问一次服务器。
  - 问的是新加的 `GET /api/ping`：不查数据库、不读会话，回版本、提交、这一版页面的入口文件与服务器时间；5 秒超时。
  - **连续两次问不到才算断了**；断了以后 2、4、8、15 秒（带随机）再问，网卡恢复（`online` 事件）、切回这个页面、点「立即重试」马上问。
  - 页面开着、在前台时每 60 秒问一次（顺便看系统有没有更新）。
  - 断了 → 告诉 React Query 离线（数据先停着不取，不一次次报错）；恢复 → 随机等 0–2 秒（几十台终端不同时涌进来）再告诉它在线，开着的页面马上重新取数据；同时通知各处「结果待确认」马上查回。
- **顶上的提示条**（`components/NetworkBanner.tsx`，盖在页面上、不挤动版面，打印时不显示）：
  - 断了：「连不上服务器（网络断了或很慢），正在重新连接… · 页面上的数据截至 14:32 · 现在提交不会发出去，填的内容还在」+「立即重试」。
  - 恢复：「网络恢复了，页面数据已刷新」，4 秒后消失。
  - 电子菜单、对客导览大屏上缩成角落的一个小圆点 + 一句话，不盖住版面。
- **断网时点提交**：发之前先确认连得上（离线状态下当场问一次服务器，最多等 4 秒）；连不上就**不发**，提示「连不上服务器，这次没有发出去，填的内容还在，网络恢复后再提交」——这是确定没发出去的，不进「结果待确认」。

### 3.3 服务器明确没处理的自动重发（WL5）

- 服务器回这三种时，**确定没有处理**，页面原样自动重发（同一个操作编号、同样的内容）：409「系统忙」（`BUSY`，等锁超时、语句超时、死锁、串行化冲突）、429「请求太频繁」（`RATE_LIMITED`）、503「系统正忙」（`OVERLOADED`）。
- 间隔：有 `Retry-After` 照它，没有就 0.5、1、2 秒左右（带随机）；最多再发 3 次、总共不超过 12 秒；还不行照旧报原来的错（「没生效，请稍后重试」）。
- 断网、超时、5xx 的写请求**不自动重发**（照旧「结果待确认」，由员工决定）。
- 页面数据的自动重试只在一层：上面三种已经在请求里重试过的，React Query 不再重试；其余照旧最多 2 次，间隔加随机。
- 服务端：死锁 `40P01`、串行化冲突 `40001` 和等锁超时一样回 409 `BUSY`（事务已经回滚）。

### 3.4 页面不白屏、更新后提示刷新（WL6、WL7）

- **页面代码没下载下来**（按需加载的都是整页，这时上一页已经离开、这一页还没打开，没有填了一半的内容）：1 秒后再导入一次（有的浏览器不记住失败的下载）；还不行——实测 Chrome 会记住这次失败，再导入也不去取——就在**连得上服务器时整页重新加载这一页一次**（连不上就等网络恢复，最多 5 分钟；同一页 1 分钟内只自动加载一次，免得一直刷；「结果待确认」的记录在本机存储里，加载以后还在）；再不行才显示「重新加载」。转圈处写着正在做什么。也认出样式表没下载下来的情况（`Unable to preload CSS`），并记下 Vite 的 `vite:preloadError`。
- **系统更新了**：`/api/ping` 回的页面入口文件和这一页的不一样，提示条写「系统已更新到新版本，方便时点『刷新』」；这时页面代码下载失败，按钮直接写「系统已更新，点这里刷新」。
- **错误边界**（`components/ErrorBoundary.tsx`）：门店、后台、ERP 的内容区各一层（换页面自动重置），最外面再一层兜底；只换掉出错的那一块，导航还能用；「重试」「刷新页面」「回首页」。
- **报给服务器**：渲染出错、页面代码下载失败、没接住的异常，带版本、提交、地址（去掉查询参数）、浏览器，发到 `POST /api/client-errors`（不用登录；每台每分钟最多 20 条、每条 8 KB 以内；**不带填的内容**）；服务器写进日志、记在内存里最近 200 条（重启清空）。

### 3.5 服务端防护：「防火墙」（WL8–WL11）

- **过载保护**（照 under-pressure 的做法）：同时在处理的接口请求超过 256 个，或事件循环卡顿超过 1 秒时，新来的接口请求直接回 503 `OVERLOADED` + `Retry-After: 2`（**确定没处理**，页面自动稍后重发）。`/api/ping`、`/api/health` 不受影响。员工食堂的端口也加。
- **频率限制**（令牌桶，在内存里）：登录了的每个会话每分钟 600 次（一下子最多 600 次，之后每秒补 10 次）；没登录的每个 IP 每分钟 300 次。超了回 429 `RATE_LIMITED` + `Retry-After`（确定没处理）。只管 `/api/*`，静态文件、页面不管。数字都能在 `.env` 改，写 0 关掉。
- **访问网段**（防火墙，**默认不设、与 Z5 一致**）：`.env` 里设了 `ACCESS_ALLOW_CIDRS`（例如门店网段、Tailscale 的 `100.64.0.0/10`）以后，只有这些地址能用系统的接口；供应商、对账链接（`/api/public/*`）照常对外，`/api/ping`、`/api/health` 不拦；命令行不受影响，设错了改 `.env` 重启即可。地址按 `TRUST_PROXY` 认（前面有反向代理时认它转来的地址）。
- **数据库**：死锁、串行化冲突回「系统忙」（第 3.3 节）；应用的连接设 `idle_in_transaction_session_timeout = 2 分钟`：事务卡住（开着不动）超过 2 分钟由数据库断开、放掉行锁（这一笔照旧是「结果待确认」）；命令行（导入等）不设。
- **停机**：收到停止信号或出现没接住的异常时，最多等 10 秒把正在处理的请求做完、关端口、断数据库再退出（Docker 自动拉起）；没接住的异常写进日志。

### 3.6 补救（WL12）

- **待确认马上查回**：网络恢复时，会员记账、前台、ERP 单据的「结果待确认」马上按原编号查一遍（ERP 单据只重查上次没查成的，不抢员工正在处理的）。
- **交班前提醒**：交班弹窗里写「这台电脑上还有 N 笔结果待确认，先处理再交班」（只提醒，不拦）。
- **「网络与同步」页**（头像菜单进，`/network`）：
  - 本机：连没连上、最近一次连上服务器的时间、往返多久；这一页的版本与服务器的版本（不一样有「刷新」）；这台电脑上的待确认（会员记账、前台、ERP 单据各几笔，点了去处理）；浏览器本机存储能不能用；最近的问题（断网、恢复、自动重发、页面报错，最近 30 条）。
  - 按钮：「立即检查连接」「重新查回待确认」「清掉页面缓存并刷新」（只清页面数据缓存，**不清待确认记录**）。
  - 店主另看「全店最近的页面报错」（服务器内存里最近 200 条，重启清空）。

## 4. 不做的与理由

- **离线记账、断网排队代发**：钱的操作必须在线确认；Odoo、ERPNext 的经验是离线单会重复、会丢；门店是 http 局域网，Service Worker 用不了。继续「只在线写 + 操作编号 + 结果待确认」。员工食堂扫码的「断网补登」（`docs/CANTEEN.md` 第 6 节）照旧。
- **主系统加 Service Worker、把页面数据存到本机**：版本错乱、旧数据当新数据看的风险大于好处。以后要的话只考虑电子菜单这种只读的。
- **出错就自动刷新整页**：渲染出错、系统更新以后都不自动刷新（会丢弹窗里填了一半的内容），只有「这一页的代码没下载下来」时按上面的条件重新加载一次。
- **外部接口熔断**：对外的只有扫码收款、平台验券、开票服务商三家，都已经是「事务外调用 + 结果不确定时按单号查回 + 每分钟补查」；熔断会把「根本没发出去」和「结果不确定」混在一起，收银时更难判断。超时照各家现有设置。
- **升级 postgres.js 到 4.x**：2026-10-29 才发的大版本（参数类型改由服务器推断、去掉 `sql.array()`），要单独评估；3.4.9 的风险用第 3.1 节的检查兜住。
- **合并三个结账弹窗**：涉及钱、各自有用例与验收，合并的风险大于整洁的好处；以后改结账时顺手收。
- **引入 under-pressure、rate-limit、helmet、opossum 等依赖**：要的只是几十行的逻辑，而且要按我们的会话、错误格式与「确定没处理」的约定来；不为它们多 4 个运行时依赖（现在一共 8 个）。
