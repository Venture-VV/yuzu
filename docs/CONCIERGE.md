# 管家部 · 8.0.12

管家部位于企业后台 `/admin/concierge`。复用 yuzu 员工账号、会话、岗位权限、PostgreSQL、原图存储、审计与数据库备份。员工不需要 GPT 账号，也不运行另一套站点或 iframe。

## 使用与权限

店主在原有「员工账号」中，给后勤岗位添加「管家员工」或「管家经理」职责。两者属于同一职责组，不与库存、采购、财务等职责跨组兼任；店主不受限制。原岗位权限与其他模块默认权限保持不变。

- 管家员工：共享全部管家会员、协调预约、接待、人工核余额、拍单、服务、回访、交班；只有自己的审计详情。
- 管家经理：上述业务，以及全部业务监管、核准名称、已确认凭证更正、完整导出。不会因此获得企业员工/密码管理或收银扣款权限。
- 店主、店总默认可以使用管家模块。后台的四项 `concierge.*` 权限也可按原有岗位规则调整；接口逐项校验。
- 纯管家账号登录后直接进入管家部，页面保留原生改密码和退出入口。

## 会员与企业数据的关系

名单从空开始，不导入独立站，也不自动纳入 yuzu 历史会员。逐个新建管家服务档案，编码从 `000001` 起递增且唯一，收银卡号单独记录。号码不复用；事务失败可能留出空号。

可选关联企业会员（需要原有 `member.read`）。搜索只用于明确选择，不会自动开卡、发权益、修改企业手机号、级别或钱包；同一企业会员只能关联一份管家档案。管家档案允许仅有收银卡号，因此没有伪造手机号去强建企业会员。

管家协调预约与前台正式预约含义不同：这里记录沟通与服务接续，指定协调资源时检查本模块时段冲突，**不代表锁定前台技师、客房或空间**。有原生 `booking.manage` 权限时，可关联同一企业会员的前台预约。协调状态不反写正式预约。

消费凭证可在原有 `frontdesk.read` 权限下关联企业结账编号，须核对该企业会员实际在该结账的来访或钱包支付中。会籍折扣会员不当作扣卡会员。关联只记录依据，完全不调用充值、收款、扣款、退款、日结或库存写接口。

## 手机业务流程

1. 建档或选会员 → 代录协调预约 → 到店接待 → 服务记录/待办/交班。
2. 余额核对：人工查收银后追加快照，保留核对人、时间、来源、说明和照片/消费依据。旧快照不可覆盖；追加依据独立留痕。低余额严格 `< 30000` 元，等于3万元不标低余额，未知不当成0。该分组不改变服务资格。
3. 拍小票：1–4张JPEG/PNG/WebP，单张≤4MiB、每批≤12MiB；先持久保存原图及可恢复草稿，再在浏览器本机识别。
4. 名称增强与金额识别分开：Tesseract识别票面与金额，PP-OCRv5/ONNX增强中文名称；不调用付费OCR或第三方图片识别服务。模型从企业自己的同源静态资源加载。
5. 经理核准标准名、规格、别名与套餐属性后复用。只有唯一全名/已核准别名自动匹配，模糊候选由人选；不自动学员工修改，不存价格，不按历史价格补金额。
6. 正常项目折叠，员工核对异常后整单确认。服务端重新计算异常及字段指纹；修改后旧勾选失效。缺失金额保留null，0元保持0；套餐子项未单价明确时必须明示，不用整单差额补造。
7. 点消费记录查看逐项明细、数量、金额、应付/实付/抹零、支付分录、票头、识别提示、确认人和原图。接待会员与实际扣卡会员分开保存。

OCR仍可能错字或漏字，首次名称校准不能省略；没有准确率百分比承诺。长票、模糊票、陌生项目及支付方式不明确时保留待核。退款凭证保持待复核，不执行资金退款。

## 稳定性与历史

业务写入在PostgreSQL事务中串行核对管家模块，包含真实员工审计、修订历史及操作结果。更新带版本号；余额与服务事实只追加。余额最新值按数据库追加序号判断，不按可能受事务等待影响的时间戳覆盖。

写操作先在设备读回验证操作编号可持久保存，再发送。断网/超时/5xx进入结果待确认，保留原编号与请求；可查回、原样重试，或在服务端同一把锁下确认不再执行。曾不确定的请求不会因后续4xx丢失恢复编号，未决时不能修改同一表单的内容另建一笔。

每3秒先查轻量修订号，有变动才同步工作区。近期列表最多500份消费摘要，完整项目及识别原文按需获取；全部历史可分页检索。操作列表保留最近2000条轻量摘要，点开读取完整前后值；按筛选条件导出的CSV读取全部匹配审计并流式输出，不限于列表2000条。处理待确认结果不会重建工作台或清空当前编辑。

照片使用原有 `erp_images` 的私有 `concierge` 用途，按SHA去重并通过专用鉴权接口读取。采购和合同图片接口不能借用编号读取管家照片。原图bytea及新业务表随既有pg_dump备份、恢复和数据指纹自动覆盖。模块JSON导出不含企业密码/会话，原图超过20MiB时明确拒绝，改用完整企业数据库备份。

## 构建资源

约64MiB的本机OCR资源随应用部署。三份较大的模型/运行文件在源码中按小分片保存，`scripts/prepare-concierge-assets.mjs` 逐字节重组并检查总大小及SHA256。`npm run build:client`、`npm run dev:client` 自动调用；不从外部下载模型、不涉及客户图片。许可与名称资源哈希清单随源码保留。

## 迁移与接口

迁移 `135_concierge.sql` 新建管家档案、分类JSONB业务记录、修订历史、图片引用、余额依据及幂等结果；只扩大员工职责和图片用途约束，不改已有钱包、余额、订单或会员资料。

核心接口为 `/api/concierge/workspace`、`/revision`、`/receipts`、`/receipts/:id`、`/uploads`、`/uploads/:id`、`/ops/:id`、`/ops/:id/abandon`、`/audits/:id`、`/audits/export`、`/native-members`、`/backup`。均复用企业登录，图片和导出禁止公共缓存。
