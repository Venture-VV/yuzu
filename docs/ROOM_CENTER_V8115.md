# 8.1.15 / 8.1.16 · 房态中心（《浴族系统需求汇总》房态中心 1–4）

店主 2026-11-19 的《浴族系统需求汇总》里房态中心有四条：新增「房态中心」与分类页签、房间多状态与颜色规范、卡片式房态登记、房间动作。总的对照与分块在 [`YUZU_REQ_V8115.md`](YUZU_REQ_V8115.md) 第 3-D 节，这里写做出来的样子。迁移 `190_room_center.sql`（表与索引）、`193_room_center_ops.sql`（房间动作的操作编号类型，8.1.16）。

## 1. 做了什么

- 门店主导航「房态」组里一个入口「房态中心」（`/room-center`）。房间来自空间台账，按**房型**分页签；每个页签顶上是总数与空闲、在用、待清、维修、已预订各几间（点一下按状态筛），另有「总览」。
- 每间房是一张卡片：房号、状态（颜色 + 文字 + 图标）、客人、技师、已用时长、金额。
- **技师服务的房间**点卡片登记：手牌号（刷卡或手输）、项目、档次、技师（点钟 / 轮钟）、出单员工号、备注、开始时间。登记 = 挂账 + 派钟 + 占房，一个事务做完。之后在房间详情里上钟、下钟、续钟、换房、并房、退房，看房间历史。
- **派对房一类**（开单即占用）点卡片开单、结束计费、撤单——还是原来的使用单，多了待清、维修两道核对。
- **客房**的卡片来自客房原来的房态看板，点开就是原来的入住、入住单、改房态三个对话框，没有重做；夜审、客房详情、预约到店在「客房」页签上。
- **大厅类**（休息大厅等）没有业务单据，只标待清、清洁完成、维修。
- 原来的「客房」页（房态看板、平面图、派对房）**并进来**（8.1.16）：客房在「客房」页签，平面图是「视图 → 平面图」，派对房在各自的房型页签；旧地址 `/rooms` 跳到房态中心（第 7.6 节）。
- 后台「空间台账 → 房态中心房型」配房型：名称、排序、管哪几种业态、是哪一类房间、启用 / 停用。

## 2. 数据（迁移 190、193，只加表、索引与类型）

| 表                   | 是什么                                                                                                                                                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `room_categories`    | 房型：名称、排序、管空间台账里的哪几种业态（`business_types`）、来源（`service` 技师服务的房间 / `party` 开单即占用 / `hotel` 客房 / `hall` 大厅类）、启用、版本号。按门店各一份，迁移给当时已有的门店建好默认的七个 |
| `space_room_states`  | 房态行，一个空间一行：最近一次「清洁完成」的时刻、手动标的待清、维修（原因、预计完成时间、谁、几点）、并房并到哪一间、版本号                                                                                         |
| `room_registrations` | 登记单：哪位客人（来访）登记在哪间房、登记时建的钟单、出单员（工号与姓名的快照）、备注、几点登记、怎么结束的（退房 / 结账离店 / 撤销来访）、退房时账单还有多少没结                                                   |
| `space_room_events`  | 房间事件，只追加：登记、换房（换出、换入）、退房、续钟、并房、拆并、标待清、清洁完成、维修、恢复——带经办人、时刻与当时的内容                                                                                         |

- 客房的表（`rooms`、`room_stays`、`room_moves`、`room_housekeeping_events`）、钟单、使用单都**没有加列**，房态中心读它们。
- 另加两个索引：钟单按「房间 + 下钟时刻」、使用单按「房间 + 结束时刻」，算待清用。
- 默认房型：按摩房（按摩、踩背、头疗）、足浴房（足浴、投影足浴）、SPA 房（SPA）、休息大厅（休息大厅、休息区、休息厅）、宠物轰趴房（宠物轰趴房）、派对房（派对房、娱乐室）、客房（客房）。**没归到任何房型的业态放在「其他」页签**，不会因为没配到就看不到。
- 升级时给已有的空间各建一行房态行，「最近一次清洁完成」记成升级那一刻——以前做完的钟不会让所有房间一下子都变成待清。
- 迁移 193（8.1.16）：`idempotency_keys`、`op_fences` 的类型约束在当时的基础上追加 `space_state`、`space_dispatch`（写法同 162、188；190 没动）。

## 3. 五种状态怎么算

| 状态   | 颜色 | 什么时候                                                                                                                                                                         |
| ------ | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 空闲   | 绿   | 下面几样都不是                                                                                                                                                                   |
| 在用   | 蓝   | 有开着的登记单；或有还没结束的钟单（客人在店，钟房直接派进来的也算）；或有开着的使用单；客房是有在住的入住单                                                                     |
| 待清   | 黄   | 没人用，而且最近一次「清洁完成」以后——有钟单在这间房做完（或上了钟被退钟）、有使用单结束、有登记单退房或客人结账离店、被手动标过（换房换出去的也记在这里）。客房是房态「待打扫」 |
| 维修   | 红   | 房态行上记着维修（原因 + 预计完成时间）。客房是房态「维修」                                                                                                                      |
| 已预订 | 灰   | 今天有订这间房、还没到店的预约（预约看板里的派对房等；技师预约、客房预约不订具体哪一间）                                                                                         |

- **先后：维修 > 在用 > 待清 > 已预订 > 空闲**（`@shared/room-center` 的 `roomStatusOf`）。用着的房间不算待清；待清的房间今天有预订，清洁完成之前照样显示待清；客房沿用房态看板自己的口径（在住优先）。
- 「待清」不另存开关，是从事实推出来的。好处是钟房里直接派进房间的钟、平面图上开的使用单也算数，不用在那几条路径里各写一遍；撤单、撤销来访（没用过房间）不算。
- 取消派钟（还没上钟）不算用过；上了钟被退钟算。
- 「在用」一直到退房：下钟以后客人还在房里，卡片写「已下钟 · 待退房」，不会提前变成待清。客人在收银台结账离店，登记单跟着结束，房间自己转待清。

## 4. 登记与房间动作

### 4.1 登记（技师服务的房间）

- 填：手牌号（刷卡或手输；带出会员与档阶、账单此刻多少、是不是已经登记在别的房间）、项目、档次（价格跟技师等级时由技师的等级定，不用选）、技师与点钟 / 轮钟（轮钟默认队列里的第一位，改派要写原因）、钟数、出单员工号、备注、开始时间。
- 必填：手牌号、项目、技师、上钟方式、出单员、开始时间；页面上没填不能提交，服务端再核对一遍。
- 出单员的工号先找员工名单（柚子饭堂的全员名单）里的工号，没有再按系统账号的登录名找；找不到拒绝。登记单上记工号与姓名的快照。
- 开始时间三种：现在开始；已经开始了（补记几点开始的，最多补到 120 分钟以前，不早于客人入场、不早于这位技师上一个钟下钟）；稍后上钟（先占房、挂账、派钟，技师到了再点上钟）。
- 挂账、建钟单、核对技师与价格都是钟房派钟的那条路（`frontdesk/bills.ts` 的 `postChargesTx`），没有另写金额的算法。任何一步不过整笔回滚：不会挂了账没占房，也不会占了房没挂账。
- 房间在用、待清、维修的不能登记。在用的房间再加一位客人用「同房加人」（双人间两位客人各一位技师）。
- 一位客人同时只登记在一间房（部分唯一索引兜底）。

### 4.2 续钟

就是钟房的加钟：按这张钟单的项目与档次加收，钟数与计划时长累加；多记一条房间事件。

### 4.3 换房

- 这间房里的客人整间换到另一间**空闲（或已预订）**的技师服务房间。
- **单与计时不变**：钟单还是那一张（只改它记的房间，与钟房的「换房间」同一个函数），明细、金额、开始时间都不动；登记单改到新房间。
- 两间房各记一条事件（从哪间到哪间）。原来的房间有人上过钟就转待清，都还没上钟的不算用过。
- 并房的关系跟着走（新房间接替原来那间）。

### 4.4 退房

- 技师还在钟上、或派了还没上钟的不能退：先下钟或取消派钟（预览里有按钮）。
- 「退房前须结清或预览结账」做成：**退房前先看结账预览**（这次登记的明细、手牌账单此刻的合计），带回预览里的合计——看过以后账又变了（加了菜、续了钟）要重新看一遍。账没结的，经办人要明确确认「客人带着手牌继续在店，离店时在收银台结」；未结金额记在登记单与房间事件上。预览里有去收银台的入口；在收银台结清的客人，登记单在结账时就结束了，不用再退。
- 没有另设「经理才能确认」：浴场的账挂在手牌上、离店时一起结，做完项目就离开房间的客人这时多半还没结，每次都要经理不现实（FT2）。
- 退了以后房间转待清。

### 4.5 并房、拆并

两间都在用的房间记成一起的（一间并入另一间，那一间是主房）。只是显示与历史上连在一起——账还在各自客人的手牌上，不搬明细、不动钱。哪一间退房、换空了，关系自己解除；也可以手动拆并。客房、大厅类不参加。

### 4.6 维修 / 恢复、标待清 / 清洁完成

- 维修要原因（至少 2 个字）与预计完成时间（比现在晚、一年以内）；有人用着的不能设。已经在维修的再提交一次是改原因与预计完成时间。
- **维修中的房间哪条路都进不来**：房态中心不能登记、不能换进来、不能开单；钟房派钟选房间、换房间，平面图上的开单也拒绝（`SPACE_MAINTENANCE`）。
- 恢复以后回到维修以前的样子（维修前就待清的仍是待清）。
- 标待清：空闲、已预订的房间手动标（客人弄脏了、借用过）。清洁完成：待清 → 空闲（今天有预订的回到已预订）。

## 5. 加锁与幂等

- 房态中心的写操作**先锁房态行**（`space_room_states`，id 升序；并房的几间一起锁），同一间房上的登记、换房、退房、并房、改状态串行；之后照各模块原来的顺序：
  - 登记、续钟：房态行 → 来访 → 账单 → 技师队列 → 空间一行（共享锁）→ 钟单 → 技师状态 → 技师预约咨询锁 → 当前位置；之后只插入登记单与事件；
  - 派对房开单：房态行 → 来访（共享锁）→ 空间一行（`FOR NO KEY UPDATE`）→ 当前位置；
  - 换房：两间房的房态行 → 钟单一行（id 升序）→ 新房间的空间一行（共享锁）→ 当前位置 → 登记单；
  - 退房：房态行 → 登记单（id 升序）；读账单、钟单不加锁；
  - 维修：房态行 → 空间一行（`FOR NO KEY UPDATE`）；恢复、标待清、清洁完成、并房、拆并只锁房态行。
- 别的模块不锁房态行：钟房、使用单只**读**上面的「维修」。设维修时锁空间一行，与派钟、换房间（共享锁）、开单（`FOR NO KEY UPDATE`）的空间锁排队——不会一边设了维修、一边刚好派进去。
- 结账、撤销来访在各自已有的锁之后锁这几位客人开着的登记单（id 升序，排在使用单之前），不碰房态行。所以没有反过来的路径。
- **每个写操作都带操作编号**，超时、断网以后照前台的「结果待确认」（查回、原样重提、确认作废，`AGENTS.md` 开发约定）：
  - 登记、续钟记成挂账的操作编号（`bill_post`），派对房开单记成 `usage_open`——都是已有的类型；
  - 换房、退房、并房、拆并记成 `space_dispatch`，维修、恢复、标待清、清洁完成记成 `space_state`（8.1.16，迁移 193 加的类型）。编号记在 `idempotency_keys`，`ref_id` 是这一步记下的第一条房间事件；写编号前在编号的咨询锁里核对「确认作废」（`saveKey`），作废先登记的整笔回滚（`OP_ABANDONED`），编号已有结果的作废不了、返回查回的结果；同一个编号原样重提返回第一次的结果，换了内容拒绝（`IDEMPOTENCY_CONFLICT`）；两次几乎同时到的，后到的那次撞上版本号以后也按编号查回。
- 这八样另外带页面看到的**房态版本号**（这间房每次写操作加一），是第二道核对：两个人同时点、带着旧状态另起一笔的都对不上（`ROOM_STATE_MOVED`），不会做两遍。
- 加锁顺序写进了 [`LOCKING.md`](LOCKING.md) 第 1 节。

## 6. 权限与留痕

没有新加权限，沿用已有的四项：

| 做什么                                                                | 要的权限                                                                                                                                                             |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 看房态中心                                                            | 「客房入住、退房」「客房打扫、维修」「钟房派钟」「结账收款」有一项就行（与客房页、钟房同一批岗位）                                                                   |
| 登记、续钟                                                            | 「钟房派钟」+「接待发牌、挂账」（与钟房派钟一样）                                                                                                                    |
| 换房、退房、并房、拆并、看结账预览、查手牌与出单员                    | 「钟房派钟」                                                                                                                                                         |
| 派对房开单                                                            | 「客房入住、退房」（与平面图上的开单一样）                                                                                                                           |
| 标待清、清洁完成、维修、恢复                                          | 「客房打扫、维修（房态）」                                                                                                                                           |
| 房间动作「结果待确认」的查回、确认作废（`/api/room-center/ops/:key`） | 原业务的权限：改房态那一类要「客房打扫、维修」，换房那一类要「钟房派钟」（只管打扫的后勤没有前台权限，也能处理自己改房态的那一笔）；查到的是别的业务的编号按查不到回 |
| 后台配房型                                                            | 「门店基本规则」或「价目管理」（与空间台账一样）                                                                                                                     |

- 没有前台、钟房、客房操作权限的岗位（只管打扫的后勤）看得到房态与手牌号，看不到客人姓名、档阶、出单员与备注。
- 每个写操作一条房间事件（房间的「历史」）加一条审计：`room_center_register`、`room_center_extend`、`room_center_move`、`room_center_checkout`、`room_center_merge`、`room_center_state`、`room_category`；登记、续钟另有原来的 `frontdesk_post`，派对房开单是原来的 `usage_open`；确认作废是前台原来的 `frontdesk_abandon`。
- 房间历史 = 房态中心的事件 + 这间房里的钟单（派钟、上钟、下钟、退钟）+ 使用单（开单、结束、撤单），按时间倒排——钟房直接派进来的也看得到。

## 7. 页面

### 7.1 看板（`src/client/features/room-center/RoomCenterPage.tsx`）

- 顶上「视图」：房态（卡片）/ 平面图；有后台权限的另有「房型配置」（到后台的房型页签）。
- 页签：「总览」+ 每个房型（带总间数；没归类的「其他」有房间才出）。手机上一行左右滑，宽屏折行。页签与状态筛选写进地址（`?tab=c3&status=dirty`），刷新、返回都还在；打开时默认「总览」。
- 每个页签顶上一排数量（全部、空闲、在用、待清、维修、已预订，图标 + 文字 + 数字，44 像素高）：点一下只看这一种，再点看全部。页签有说明的（客房功能没开、今天几张客房预约还没到店、「其他」怎么归类）写在上面。
- 总览：每个房型一张小卡（共几间、各状态几间，点一下进那个页签），下面按房型分组列全部的房间（也按状态筛）。
- 卡片（`RoomCard.tsx`）：房号与状态章（颜色 + 文字 + 图标，16 像素）、显示名 · 楼层 · 容量、并房的标、按状态的两三行（在用：客人、技师、已用时长与剩几分 / 超几分、待上钟、已下钟 · 待退房、金额；客房在住另写手牌、几号入住与预离或钟点房已住多久、押金；派对房按现在约多少；待清：几点起、说明；维修：原因、预计几点完成，过了时间标红；已预订：几点、谁、几位）。空闲的写点了会做什么（登记 / 开单 / 入住）。
- 五种状态的样子（`status.tsx`）：空闲绿、在用蓝、待清黄、维修红、已预订灰，都走样式表里的色名，深浅两套主题跟着变。
- 看板 10 秒刷新一次（`useLivePoll`：页面在后台、连不上服务器时不取，回到页面、网络恢复时马上取）。

### 7.2 登记对话框（`RegisterDialog.tsx`、`TagField.tsx`）

- 点空闲（或已预订）的技师服务房间卡片打开；在用的房间在详情里点「同房加人」。
- 手牌号用发卡台那一块的刷卡部件（经 `VisitDialogs.tsx` 的 `InStoreTagInput`，就是 `TagCardInput`，刷到的牌要在店）：读卡器状态一行、桥报的与键盘式读卡器打进来的都先按芯片号查绑定（第 8 节），随时能手输；牌号齐了带出会员与档阶、账单此刻多少，已经登记在别的房间的写明。
- 项目（只列需要技师的、与客人分区对得上的）、档次（价格跟技师等级时写明由技师定）、上钟方式（轮钟默认队列里的第一位，改派要写原因；点钟列出上了牌的技师，在钟上的写「登记后等钟」）、钟数（1–9）、出单员工号（默认自己的登录名，输完核对是谁）、开始时间（现在开始 / 已经开始了〔5–30 分钟前〕/ 稍后上钟）、备注。
- 底下一行写还差什么（没填齐不能提交）或合计；提交照前台的「结果待确认」（`useFrontdeskOp` 的挂账，结果不确定时对话框里查回、原样重提或确认作废）。

### 7.3 房间详情与动作（`RoomDialog.tsx`、`RoomActions.tsx`）

- 卡片右上角的「详情」（技师服务的房间点在用、待清、维修的卡片也是它）：并房、维修、待清、今天的预订各一条说明；每位客人一块（手牌、称呼、档阶、出单员、备注、几张钟——上钟、续钟、下钟）；派对房开着的使用单；动作；房间历史（先列 8 条，能看全部）。
- 动作按状态给：空闲 → 登记 / 开单、标待清、维修；在用 → 退房（有登记单时）、换房、同房加人、并房（派对房是结束计费、撤单）；待清 → 清洁完成、维修；维修 → 恢复、改维修信息。没有权限的按钮是灰的，下面写明要哪项权限。
- 续钟、换房、并房、退房、维修、标待清、恢复各一个对话框：换房、并房从一排房间里挑一间（写状态与客人）；退房先看结账预览（每位客人的明细、手牌账单合计；还在钟上的直接点「下钟」，派了没上的去钟房取消派钟；账没结的勾「客人带着手牌继续在店」）；维修填原因与「多久以后修好」（小时 / 天，页面算出预计完成时间）。
- **结果待确认**（8.1.16）：房间动作照前台的规矩——提交前本机存原编号与原请求（存不了就不发），超时、断网、服务器出错以后这间房上同一类的动作锁住（换房、并房连着的另一间也锁），对话框与房间详情顶上写明，能「查回结果」「按原内容重新提交」「确认作废，重新填写」；页面顶部的「结果待确认」提醒里点「去处理」回到这间房的详情。查回、作废走 `/api/room-center/ops/:key`（第 6 节）。

### 7.4 后台房型（`src/client/features/admin/RoomCategoriesCard.tsx`）

后台「空间台账」的「房态中心房型」页签（`/admin/spaces/room-categories`）：房型清单（名称、启用、排序、哪一类与说明、管的业态与各几间）、新建、修改（名称、排序、哪一类〔四选一〕、业态〔从台账里用到的与常用的里点选，也能另写一种〕、启用）。一种业态已经归了别的在用房型的点不了、写明归在哪；来源与业态对不上的保存不了、写明原因（服务端再核对，带版本号）。有房间、没归类的业态在顶上写明。一个房型都没有时能按默认的建一份。

### 7.5 客房（「客房」页签）

- 卡片来自客房的房态看板；点在住的看入住单、空闲的入住、待打扫和维修的改房态——都是原来的对话框（`features/rooms/HotelDialogs.tsx` 的入住、夜审，`StayDialog`、`HousekeepingDialog`、`RoomDetailDialog`）。
- 页签上：「客房详情」（房态与入住的时间线）、「夜审」，夜审提醒；客房功能没开时写明去哪开。
- 预约到店：预约看板点「到店」带 `?booking=` 过来，自动到「客房」页签、同房型的空房描边标出，点一间就按预约入住。

### 7.6 原来的「客房」页

- `/rooms` 跳到房态中心（`App.tsx` 的 `RoomsMoved`）：房态看板 → `?tab=hotel`（第一个客房房型的页签），派对房看板 → `?tab=party`，平面图（`?view=map`）→ `/room-center?view=map`；预约到店（`booking`）、结果待确认（`resume`）的参数照带。主导航里原来的「客房」入口换成「房态中心」。
- 平面图还是原来的（`FloorMap.tsx`）：点客房开原来的入住、入住单、改房态，点派对房开单、结束、撤单照平面图原来的接口（只拦维修，FT13）。客房功能没开时平面图上的客房不着色。
- 派对房看板（原来「客房」页的「派对房」视图）去掉了：派对房、宠物轰趴房在各自的房型页签里开单、结束计费、撤单（FT14）。
- 顶部「结果待确认」的「去处理」：客房的入住、续住、押金、退房，派对房的开单、结束、撤单，房态中心的房间动作都回到房态中心（`PendingBanner.tsx`）；登记、续钟是挂账，照旧在发卡台处理。

### 7.7 三台设备

1920 × 1080、1280 × 720、360 × 800、1355 × 903 都不横向滚动（`e2e/target-devices.spec.ts` 的 `room-center`，合成的看板）：卡片宽屏 4–5 列、平板 4 列、手机 1 列；页签在手机上一行左右滑；对话框在手机上占满宽度，提交按钮在屏幕里。字号不小于 12 像素，金额与状态不小于 16 像素，按钮与可点的卡片不小于 44 像素。

## 8. 给别的模块的入口

- `currentGuestOfSpace(db, spaceId)`（`src/server/modules/room-state.ts`）：这间房里现在的客人 `{ visitId, tagNo, memberId }`——有登记单的取先登记的那位，钟房直接派进来的取还没结束的钟里最早那张的客人，派对房等取开着的使用单的使用人，都没有为 `null`。只读、不加锁。
- 餐饮「只填房号」点单（`dining-order-v8115.ts` 的 `findGuestByRoom`）：先找在住的客房（房号是客房的房号），再按空间台账的编码找房态中心里这间房的客人（本店在用的空间，「客房」业态的不算），用的就是上面这个（FT9）。点单页找客人、下单时在挂账的事务里再核对一次，都是只读。
- 登记表单的手牌号用发卡台那一块的 `TagCardInput`（`docs/FRONTDESK_RISK_V8115.md` 第 2.5 节）。房态中心不直接引它，引的是 `VisitDialogs.tsx` 里包了一层的 `InStoreTagInput`：8.1.16 实测多一个模块直接引 `TagCardInput`，打包时前台的共用代码（手牌状态章、前台的取数等）会被挤进首屏主包（881 KB → 903 KB，超过 `check:bundle` 的 900 KB 上限）；经已经引了它的模块转一手就不会。
- 刷卡带出牌号的认法（Codex 审查 d12390f 的 P2，8.1.16 一起修了）：读卡器、扫码枪连续打进来的一串，**先按芯片号查绑定**，没绑定的、本身是牌号的才当牌号用（`@shared/frontdesk-risk` 的 `resolveScan`）；输入框里、输入框外刷都走这一条，桥报上来的一定是芯片号、不当牌号猜。以前先看像不像牌号，芯片号「00000001」按数字比较配得上 A001，刷 A002 的卡反而选中了 A001。

## 9. 没做的

- 客房的维修没有「预计完成时间」：客房沿用原来的「改房态」（只有原因）。要加得给客房的房间加一列，这次没动客房的表。
- 钟房里直接派钟选到**待清**的房间这一版不拦（只拦维修）：钟房原来的流程里没有「清洁完成」这一步，一上线就全拦，钟房会派不出去。房态中心自己的登记、换房、开单都拦。平面图上的派对房开单同样只拦维修（FT13）。
- 技师预约、客房预约不订具体哪一间房，所以技师服务的房间、客房不会显示「已预订」；客房页签上只提示今天有几张客房预约还没到店。
- 派对房、大厅类不能换房（派对房结束使用后在新房间开单）。
- 没有「清洁完成」这一步的开关（要不要像桌台一样在设置里能关，等店主说）。
- 休息大厅这类大厅不数里面有几个人（实时位置里有，这次没接）。
- 登记、续钟的「结果待确认」照挂账的规矩在发卡台处理（顶部提醒「去处理」到发卡台的那张手牌），不回到房态中心的那间房。
- 派对房的计费说明（每小时多少、起步几分钟）原来写在派对房看板的分组标题上，现在在开单、结束对话框与房间详情里。
