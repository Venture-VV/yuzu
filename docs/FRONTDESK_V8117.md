## 1. BW-12「流水」的订单详情：与结账单同一个部件

- **做法**：「流水 → 订单查询」点开一张结账单，用结账完成页、「结账记录」、桌台结账完成页的同一个部件 `CheckoutReceipt`（8.1.17 从 `CheckoutDialog.tsx` 搬到 `src/client/features/frontdesk/CheckoutReceipt.tsx` 单放，「流水」只引这一个文件）：
  - 抬头：单号、时间、收银（写明「收银 某某」）、已反结账、补录；
  - 每张手牌（桌台）一行：客人、门票与档、在店多久、金额；带着逐行明细的（「流水」取的是打印的那一份）在每张手牌下面列结账那一刻的明细——名称、被签赠 / 券 / 会员折扣抵到的标「赠」「券」「折」（与 80mm 小票同一个标法，颜色加字）、所属部门、数量 × 单价、技师、金额、摊到这一行的优惠；
  - 「优惠与赠送」一栏：每笔的类别、名称、说明与经办人（发放、授权、渠道），「共优惠」；
  - 收款：只列真收的钱与预付抵扣，储值写会员、消费单号、本金 / 赠金与扣前扣后的余额；合计。
  - 「流水」自己的在下面：状态（已结账 / 有退款 / 已反结账）、营业日、备注、这张单的退款单、打印结账单。
- **接口**：「流水」照旧取 `GET /api/ledger/orders/checkouts/:id`（权限照旧：「查看当日流水与日结」，不是今天的单另要「查看历史营业日」）。它本来就带打印的那一份（`doc`：结账单详情 + 每张手牌结账那一刻的明细，每行带 `perks` 标记 + 储值余额），这次每一行多带 `category`（所属部门）与 `discount`（摊到这一行的优惠，分）——按明细编号对上原来逐行算的那一份（`checkoutOrderDetail`，只读）。打印接口不带这两项。
- **补录到更早时刻的单**（按项目快照显示，`source = 'items'`）：按时刻取的明细与快照对不上，结账单部件里不列逐行（标不出抵到哪一行），下面照旧按项目快照列一张表（所属部门、数量、单价、金额、优惠）。
- 结账完成页、「结账记录」拿到的结账单详情没有逐行明细，部件照旧只列手牌一行，与以前一样。

## 2. BW-4 退菜按出品口：康美部自己退菜

- **新权限**（`src/shared/permissions.ts`，后台「岗位权限 → 餐饮：按出品口退菜」）：「退菜：餐厅的菜」「退菜：水吧的菜」「退菜：果吧的菜」（`dining.voidRestaurant` / `dining.voidWater` / `dining.voidFruit`）。
  - 原来能退菜的是有「前台挂账」（`frontdesk.operate`）的岗位（手牌的退菜接口只要它，桌台的退菜接口还要「餐饮点单」），默认是店主、店总、值班经理、店员——这四个岗位三项都有；
  - 康美部（职责 `kangmei`）默认有水吧、果吧两项（没有餐厅，与下单一样）。
- **核对**：退一条明细时逐行核对（`authorizeLineVoid` 开头的 `assertLineVoidPermission`，`src/server/modules/dining-v8117.ts`）：
  - 餐饮的菜要这道菜所在出品口的「退菜」权限。出品口与下单核对同一个判断（`diningSlotOf`：按菜现在的点单分类，后台没设的按默认归），没有的拒绝（403 `OUTLET_VOID_FORBIDDEN`，写明是哪一处、哪道菜）；
  - 别的明细（洗浴、技师、手动金额……）照旧要「前台挂账」；
  - 之后原因、时限、授权的规矩照旧：小额直接退（能退这一处的菜的就能直接退，原来是「前台挂账」）、有更正权限的直接退、当场授权、本人 15 分钟内。
- **接口**：手牌的退菜接口 `POST /api/frontdesk/lines/:id/void` 有「前台挂账」或任一项「退菜：某出品口」就进得来（康美部没有「前台挂账」），进来以后逐行核对；桌台的 `POST /api/dining/tables/lines/:id/void` 照旧要「餐饮点单」+「前台挂账」，再逐行核对出品口。退大额的菜申请当场授权（`POST /api/auth/authorize`，用途 `line_void`）也按这道菜的出品口核对申请人（原来是「前台挂账」），康美部能为水吧、果吧的菜申请。
- **页面**：点单页「还没上的菜」、桌台详情里，只在有这道菜所在出品口退菜权限时显示「改」「退菜」（菜单里没有的菜照样显示，服务端核对）；有不能退的菜时写一句「你的岗位只能退水吧、果吧的菜，别的退菜、改单请找有权限的同事」。
- **与菜品那一份的接头**：退主菜连带加料（BW-8）是先把要退的几行列出来再逐行走 `authorizeLineVoid`，出品口的核对在逐行的那一步，两边各改各的。
- **迁移 199**：后台「岗位权限」里给哪个岗位加了「前台挂账」，也给它加上这三项；去掉了「前台挂账」的也去掉这三项（不然原来不能退菜的岗位升级以后反而能退）；再跑一次不重复加。

## 3. BW-3 发卡台「加项目」按出品口核对

- **做法**：发卡台「加项目」（`POST /api/frontdesk/visits/:id/charges`）挂进厨房的菜时，按出品口的下单权限逐行核对，用点单页的同一个函数 `assertOrderOutlets`（`dining-order-v8115.ts`）：有一道不行整单拒绝（403 `OUTLET_FORBIDDEN`，写明哪几道）。
  - 「进厨房的菜」与挂账判断的是同一份：餐饮开着、挂在启用的出品档口上、不需要技师的项目（`kitchenStationsOf`）。洗浴、技师、手动金额等不进厨房的项目不受影响；
  - 核对在挂账的事务里（来访 → 账单之后，挂账的 `PostOptions.outlets`），只读、不加锁；同一个操作编号原样重提照原样返回第一次的结果，不再按此刻的权限核对（与点单页一样）；
  - 点单页（事务外已经核对）、钟房派钟与加钟、小程序扫码点餐不带这一项；平板电子菜单按平板账号的岗位核对是另一份（BW-3 的另一半）。
- **页面**：「加项目」里，这个岗位不能下单的出品口的菜标「不能在水吧下单」、不能点（按点单页菜单里那道菜的出品口；服务端照样核对）。

## 4. BW-1 超时加收按小时先填好、到点自动提醒

### 4.1 超时加收

- 后台「手牌与前台 → 前台规则」多一项「超时加收：每超 1 小时（元）」（`frontdesk_rules.overtimeSurchargeHourlyCents`，分；默认 0 = 不算价；0–¥1,000；按店，第二家店存自己的）。只有能改经营规则的人（店主）改。
- 客人卡「异常处置 → 加收」：这位客人在店超过 12 小时、又设了每小时的价时，金额先填好 = 超过 12 小时以后的小时数 × 每小时的价，**不足 1 小时按 1 小时算**（超 1 分钟算 1 小时；`overtimeSurchargeOf`，`src/shared/frontdesk-v8117.ts`），一笔最多 ¥10,000（与手填的上限一样，超了按上限填并写明）；原因先填「超时 N 小时」。下面一行写明怎么算的。
- 金额、原因都能改；照旧要点「确认加收」才挂，照旧的权限与授权（值班经理及以上直接加，别人凭当场授权），**不自动收钱**。服务端没有改：加收照旧是一条手动金额的明细。没超过 12 小时、没设价的照旧手填。

### 4.2 超时提醒

- 每分钟的任务（`src/server/jobs.ts` → `sweepOvertimeReminders`，`src/server/modules/frontdesk/overtime.ts`）：各家店在店的客人到了 12 / 24 / 72 小时（就是手牌板上超时在店的三级 `OVERSTAY_TIERS`），在「异常待办」里记一条「超时提醒」（`visit_incidents.kind = 'overtime'`，`overtime_hours` 记是哪一级），经办人是系统账号「系统」（`system.auto`，第一次用到时建，不能登录、员工名单里不显示）。
  - **每一级只记一次**：部分唯一索引 `visit_incidents_overtime_uq`（来访 + 级别）兜底，插入 `ON CONFLICT DO NOTHING`；几个进程同时跑、同一分钟跑两次都只记一次。
  - 停机后才跑到、一下子跨了几级的，只记到了的最高一级（低的算被它盖过，不补记）。
  - 操作编号按「来访 + 级别」算出来（`overtimeOpKey`），查得到是哪一笔；审计记 `visit_incident`（`detail.kind = 'overtime'`、`auto: true`），经办人「系统」。
- **待办**：超时提醒与上报、未结离店一样进「异常待办」，能指派、写处理结果（有「接待发牌、挂账、换牌」的人都能写，只写一次）；另外两种情况自动不再算待办——**客人离店以后**、**这次来访有了更高一级的超时提醒以后**（24 小时那条把 12 小时那条盖过）。手牌板上每张牌的待办数、发卡台顶上的条数、「异常待办」清单是同一个口径（`openTodoWhere`，页面上是 `isOpenTodo`）。客人卡的异常记录里，不再算待办的写「不再跟进」。
- 页面上不能自己登记「超时提醒」（登记接口只认原来的六种）。

## 5. BW-2 桌台提醒：维修到点、待清台太久

- **维修过了预计恢复时间**：维修中的桌，格子上原来的「维修中 · 原因 · 预计几点」下面多一行「已过预计恢复时间」（陶土色、闹钟图标、16 像素），格子的边框加粗；算进餐饮的待办数。
- **待清台太久**：结账以后待清台（从结账那一刻 `state_since` 算）超过 N 分钟（餐饮规则「待清台多久算久了」，默认 15，1–240）还没清台，格子上多一行「已待清台 23 分钟」（深橙色、闹钟图标），边框加粗；算进待办数。升级前就待清台、没有时刻的不提醒。
- **餐饮的待办数**：「桌台」页签上一个小标「待办 N」（N = 上面两种的桌数，没有时不显示），桌台页顶上写「待办 N 桌 · 已过预计恢复时间 X · 待清台超过 15 分钟 Y」。都按看板上现成的状态与时刻、服务器的钟算（`tableReminderOf` / `tableTodos`，`src/shared/frontdesk-v8117.ts`），不另存、不另加接口。
- **到点自动恢复**（餐饮规则「维修到点自动恢复」，`dining_rules.autoRestore`，默认关；按店）：开着时每分钟的任务（`src/server/jobs.ts` → `sweepTableRestores`，`src/server/modules/tables-v8117.ts`）把过了预计恢复时间的桌恢复——走手动「恢复」的同一个函数 `restoreTable`，同样的锁、同样记一条桌台记录（`table_events` 的 restore）与审计 `table_restore`，经办人是系统账号「系统」，桌台历史里写「系统」。
  - 操作编号按「桌台 + 这一次维修的开始时刻」算出来（`autoRestoreKey`）：几个进程同时跑，后到的按编号原样返回第一次的那条，只恢复一次；
  - 锁住桌台以后再核对预计恢复时间确实到了（`restoreTable` 的 `dueAt`，`MAINTENANCE_NOT_DUE`）：挑候选到锁住之间有人恢复后又重新报修的，新的那次维修还没到点不动；
  - 关着时什么都不做，格子上标着、等人去点「恢复」。
- 后台「餐饮 → 餐饮规则」多这两项（只有店主能改）。

## 6. BW-11 第二家店的本店价改价留痕

- **在哪改**：照旧在第二家店里打开后台「价目 → 本店价」（`StorePricesCard`，`PUT /api/admin/catalog/store-prices`，权限照旧「管理充值套餐与消费项目」；本店不能设本店价）。
- **要写原因**：点「保存」「按全公司的」先弹出写原因（至少 2 个字、最多 100 字；快捷原因与菜品改价同一份 `dishPriceReasons`），弹窗里写着改前 → 改后。
- **记什么**：菜品（挂了出品档口、不需要技师的价目项目，与全公司价目的改价记录同一个口径）的本店价每改一档，在菜品的改价记录 `dish_price_changes` 里记一条——哪家店（`store_id`）、改前改后（为空 = 同全公司，没有单独定价）、那时这一档全公司的价（`base_price`）、谁、几点、原因，来源「本店价」（`store_price`）。不是菜品的项目照旧只记审计。每一次（菜品不菜品）都记审计 `store_price_changed`「改本店价」（改前、改后、全公司价、原因）。
- **改价记录按门店筛**：「餐饮 → 菜品管理 → 改价记录」有第二家店时多一个「门店」下拉（全部 / 全公司的价目 / 某家店的本店价），`GET /api/dining/dishes/price-changes?store=hq|<门店编号>`；本店价的记录写「标准 同全公司（¥38.00） → ¥35.00」、标「本店价 · 南山店」。每道菜的改价弹窗里也列着这道菜的本店价记录。
- **重复与并发**：改成的价与现在一样的什么都不做（回 `changed: false`，上一次的回复丢了再点一次不会多记一条）；页面带上打开时看到的本店价（`expected`），别人刚改过的拒绝（409 `STORE_PRICE_STALE`，刷新后再改）。两人同时改同一档一个接一个，记录前后接得上。

## 8. 权限、审计、加锁

- **新权限**：「退菜：餐厅的菜」「退菜：水吧的菜」「退菜：果吧的菜」（第 2 节）。别的照旧：超时加收的规则要「修改经营规则」，加收照旧值班经理及以上直接加、别人凭当场授权；超时提醒的指派、处理结果要「接待发牌、挂账、换牌」；餐饮规则要「修改经营规则」；本店价要「管理充值套餐与消费项目」。
- **新审计动作**：`store_price_changed`「改本店价」。超时提醒记 `visit_incident`（`detail.kind = 'overtime'`、`auto: true`），自动恢复记 `table_restore`，经办人都是系统账号「系统」。
- **系统账号「系统」**（`system.auto`，`src/server/modules/system-staff.ts` 的 `systemAutoStaffId`）：每分钟的任务自己记的事的经办人；第一次用到时建，不能登录、员工名单里不显示。
- **加锁**（写进 `docs/LOCKING.md` 第 1 节「8.1.17」一条）：
  - 退菜按出品口：在原来退菜的锁里只读地查这道菜的点单分类，不另加锁；
  - 发卡台加项目按出品口：挂账的事务里（来访 → 账单之后、沽清之前）只读地核对；
  - 超时提醒：一次来访一个事务，来访（`FOR UPDATE`）→ 写异常，「来访 + 级别」的部分唯一索引兜底；
  - 到点自动恢复：走手动恢复的同一个函数——操作编号的咨询锁 → 桌台一行（`FOR UPDATE`，锁住以后核对还在维修、到了点）→ 写 `table_events`；
  - 本店价：价目项目一行（`FOR NO KEY UPDATE`，与菜品维护、后台价目同一批行）→ 本店价一行 → 改价记录（只追加），在锁里读改前的本店价与全公司价。

## 10. 默认做法（待确认）

与 `docs/PENDING_DECISIONS.md`「8.1.17」BW1、BW2、BW3、BW4、BW11、BW12 同一份；这一份里另外定的：

| 事项 | 这一版的做法 |
| --- | --- |
| 超时加收「超了几个小时」 | 从在店满 12 小时起算，不足 1 小时按 1 小时算（超 1 分钟算 1 小时）；一笔最多 ¥10,000；原因先填「超时 N 小时」。每小时的价 0–¥1,000，按店 |
| 超时提醒跨级 | 每一级只记一次；停机后一下子跨了几级的只记到了的最高一级，低的不补；有了更高一级的，低一级的不再算待办 |
| 超时提醒什么时候不再算待办 | 写了处理结果、客人离店（结账、撤销）以后、有了更高一级的以后；客人卡的异常记录里写「不再跟进」 |
| 「系统」是谁 | 新的系统账号 `system.auto`（显示「系统」），与「小程序」「赠品出库」「自动扣料」一样不能登录、员工名单里不显示 |
| 餐饮的待办数在哪 | 「桌台」页签上的小标「待办 N」与桌台页顶上一行；按看板现算、不另存 |
| 待清台从几点算 | 从结账那一刻（桌台状态的开始时刻）算；升级前就待清台的没有时刻，不提醒 |
| 自动恢复的范围 | 只在餐饮开着、规则开着的店做；锁住以后再核对还在维修、到了点；同一次维修只恢复一次 |
| 退菜权限与小额直接退 | 能退这一处的菜的就能小额直接退（原来是「前台挂账」）；康美部退别人点的大额的菜照旧要当场授权，能自己申请 |
| 去掉「前台挂账」的岗位 | 迁移把三项退菜权限一起去掉（升级以后与原来一样退不了）；以后后台再单独给退菜权限也行 |
| 发卡台加项目的页面 | 不能下单的出品口的菜标「不能在水吧下单」、不能点；补录纸质单也按出品口核对 |
| 本店价要不要原因 | 要（菜品不菜品都要），记进审计；菜品的另记进改价记录。改成一样的价不报错、什么都不做 |
| 「流水」的订单详情 | 结账单部件多列逐行（带「赠」「券」「折」、所属部门、摊到的优惠），储值写扣前扣后；结账完成页、「结账记录」没有逐行，看起来与以前一样 |

## 11. 不在这一版

- 平板电子菜单按出品口核对、菜品的几样（BW-5–BW-10）：另一份。
- 超时加收不自动挂、不按小时自动收钱（只把金额先填好）；超时提醒不发到手机、不响铃（在「异常待办」里）。
- 桌台提醒不发到手机；自动恢复只看预计恢复时间，不看维修的人有没有修好。
- 本店价的批量改、按门店导入价目表；本店价不分「菜品管理」里改（仍在后台「价目 → 本店价」）。
- 「流水」里退款单的详情照旧（退了哪几项、退款方式），没有换成结账单部件。
