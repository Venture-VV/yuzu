## 1. 长期项目为什么会失控（原文第二节）

作者用 AI 从零做了一个 Mac 录屏剪辑应用。功能多、要长期迭代的项目，没有约束时会出五类问题：

| 问题 | 怎么来的 | 后果 |
| --- | --- | --- |
| 样式重复实现 | AI 每次只盯着眼前的需求，不复用已有的组件 | 各处样式差一点，整体观感变差 |
| 硬编码 | 颜色、间距、配置、路径直接写死在各个文件里 | 要统一改的时候漏改 |
| 重复逻辑 | 不知道别的目录已经有了，又写一份 | 同一件事几份实现，改一处漏一处 |
| 冗余代码残留 | 换了新方案，旧函数、旧文件没删 | 读代码白花 Token，还干扰判断 |
| 文档越积越多、过期 | AI 爱写方案和记录，写完没人管 | 过期文档和代码对不上，把后面的开发带偏，也白花 Token |

## 2. 动手前（原文第三节）

- 选型先调研生态、可维护程度、性能上限；用开源项目要看协议（MIT、Apache 2.0 可以改了商用，GPL、AGPL 要求改完开源）。
- 有成熟的开源项目先考虑二次开发：老项目里「奇怪的写法」多半是给边角问题兜底的。
- 用能力最强的模型调研，几个模型交叉判断；把大应用拆成一个个能单独验证的里程碑。

## 3. 日常开发的闭环（付费，按 Skill 原文补）

六个 Skill 把一次改动拆成五步，外加一条修缺陷的支线：

| 步骤 | Skill | 做法 | 防的是什么 |
| --- | --- | --- | --- |
| 探索 | `oil-explore` | 只读地查清调用链，列出能复用的组件、函数、真实的测试命令；大仓库按模块分给便宜的只读子 Agent | 没看清就动手，又写一份重复的 |
| 方案 | `oil-plan` | 按轻重分三级：小改直接改；常规需求在对话里对齐；跨模块的写成规格文档。方案用「外面看得到什么变化、复用什么、这次不做什么」来讲，要人拍板的单独列出 | 方案太技术、看不出改什么 |
| 委托 | `oil-delegate` | 把边界清楚的活交给另一个 Agent（另一家的模型），在独立工作树里做 | 一个窗口从头做到尾，上下文越来越乱 |
| 审查 | `oil-code-review` | 先对照方案查越界（碰了高风险目录、禁改目录、超出范围的文件），再按风险分级：核心逻辑从业务闭环、复用、冗余、运行期错误、安全与兼容五个方面深审，界面微调轻审 | 改动超出范围；自己审自己 |
| 治理 | `oil-govern` | 体检文档、测试、工作树；把项目的硬规则写成仓库里的自动检查 | 规则只写在文档里，没人执行 |
| 修缺陷 | `oil-bug-fix` | 先写一个会失败的测试复现，再找根因、在坏数据产生的地方修；判断是个例还是普遍问题，普遍的全仓排查 | 只挡住了症状，同样的写法别处还在 |

几条贯穿的做法：

- **规则放一处，入口要小**。`AGENTS.md` 每次对话都整份载入，只留「按任务去哪看」的路由和少数硬规则，专题规范放专题文档，不重复抄写。
- **测试分层**。写代码途中只跑秒级的检查（类型、lint），写完跑和这次改动相关的快测，全量测试和构建留到合并前。
- **硬规则写成自动检查**。同一类问题第二次出现，就不再靠提醒，写成脚本进 CI。规则「单源优先、严进常删」：高频、跨模块的才沉淀成规则。
- **高风险操作先独立检查**。合进主干、删数据、改数据库结构、发版之前，由一个干净上下文的只读 Agent 看影响面和能不能撤回。
- **开发约定写进 `AGENTS.md` 的一个小节**（不超过 10 行）：快测命令、合并门禁、高风险目录、禁改目录，几个 Skill 都读它。

## 4. 测试与环境（付费，只有预告要点）

- 自动化测试要能在后台静默跑、不抢焦点、不碰真实数据。
- 疑难问题让两个强模型讨论；连续修不好的非核心功能，果断砍掉。
- `oil-code-review` 里对测试的要求：排除只靠 mock 自己证明自己的、固定 `sleep` 的、有副作用的用例。

## 5. 长期治理（付费，只有预告要点）

- 高频踩坑的地方补规则。
- 界面用统一的共享组件（作者的 `oil-ui`：先定设计方向，再照真实截图改）。
- 测试分层，别让 AI 动不动跑重型测试；清掉只做表面功夫、白花 Token 的用例。
- 定期巡检过期文档。

## 6. 发版（付费，只有预告要点）

- 发版动作写成规范文档，不同模型照同一份做。
- 不做重型灰度，靠程序里的硬限制、能回退的更新配置、启动保护保证基本可用。

## 7. 子 Agent 怎么用（配套文章，公开）

- 适合交出去的：会产生大量中间信息、最后只要一份摘要的活——大范围搜索、只读审查、看大日志、几个方案并行评估。
- 不适合并行的：会改同一批文件的、必须先后做的、上线和删数据这类高风险的。
- 子 Agent 不天然省钱：每个都要重新读背景。探索类的显式指定便宜的模型才划算；一两步能做完的小改动主 Agent 直接做。
- 四个角色：探索者（只读、最便宜的模型）、执行者（边界清楚的修改）、审查者（独立上下文，查过度复杂与重复造轮子）、专家顾问（疑难问题才请最强的模型）。

## 8. 对照 yuzu：已经在做的、还没做的

| 视频里的做法 | yuzu 现状 |
| --- | --- |
| 多模型分工、独立审查 | **已有**：Claude 开发、Codex 审查与验收、Gemini 小程序线、测试会话；报告按线发在 PR 上 |
| 里程碑、每期能单独验证 | **已有**：G 点、交接说明、固定预期的演示数据 |
| 测试不碰真实数据 | **已有**：环境隔离红线、独立测试库与演示库 |
| 硬规则写成自动检查 | **部分**：`check:code`（没用到的导入、事务里没等结果的查询）、排版、线范围、shellcheck；硬编码、重复、文档没有检查 |
| `AGENTS.md` 是精简的入口 | **没有**：88 KB，其中「加锁顺序」一行 4.6 万字节，每个会话开工都整份读进去 |
| 文档巡检、过期的归档 | **没有**：158 份文档没有索引，82 份是发版当时的交接快照；`README.md` 还停在 0.x 的状态 |
| 测试分层（秒级 / 快测 / 门禁） | **部分**：有「改了什么先跑哪些」的对照表，全量靠 CI；没有不要数据库的秒级一档 |
| 统一共享组件与界面规范 | **部分**：有动效、二级页签、数量输入等公共部件的约定；没有一份界面规范，字号手写了 4198 处、32 种 |
| 冗余代码清理 | **部分**：`check:code` 查没用到的导入与变量；导出了没人用的查不到 |
| 开发约定小节（快测、门禁、高风险、禁改） | **没有** |

## 9. 能配合这套思路的开源项目、工具、Skill

### Skill 与方法

| 项目 | 是什么 | 怎么用到 yuzu |
| --- | --- | --- |
| [oil-oil/oil-dev-skills](https://github.com/oil-oil/oil-dev-skills)（MIT） | 视频作者的六个 Skill：探索、方案、委托、审查、修缺陷、治理 | 采用它的做法（入口瘦身、开发约定小节、分层测试、硬规则转检查）。脚本是 Python、只在 macOS 上测过，**不直接装进仓库**；想在本机用，对 Agent 说「安装 https://github.com/oil-oil/oil-dev-skills 」，或 `npx skills add oil-oil/oil-dev-skills` |

### 工具（按要解决的问题）

| 问题 | 工具 | 实测 | 结论 |
| --- | --- | --- | --- |
| 冗余代码 | [knip](https://github.com/webpro-nl/knip) 6.45 | 没用到的文件 0；没人引用的导出 44 个、类型 24 个；只在本文件用却 `export` 的约 830 个；没声明的依赖 3 个 | **采用**（一期装、记基线，二期清） |
| 重复代码 | [jscpd](https://github.com/kucherenko/jscpd) 5.4 | 24.8 万行里重复 1930 行（0.78%），集中在五个导入页、两个结账弹窗 | **采用**（记基线，二期合并最重的几处） |
| 代码规范 | [oxlint](https://github.com/oxc-project/oxc) 1.94 | 1165 个文件 0.1 秒，默认 96 条规则报 107 处 | **采用**（二期修完进 CI）；比 ESLint 快两个数量级，适合「写代码途中秒级检查」 |
| 结构化的自定义规则与批量改写 | [ast-grep](https://github.com/ast-grep/ast-grep)（只看了说明） | — | 备选。yuzu 已经用 TypeScript 自带的语法树写检查（`check-code.mjs`），先沿用，不多引一个工具 |
| 存量问题只降不升 | ESLint 的 [bulk suppressions](https://eslint.org/docs/latest/use/suppressions)、knip 的 `--suppress-all`、[betterer](https://github.com/phenomnomnominal/betterer)（只看了说明） | — | **采用思路、不引工具**：自己写一份基线文件，检查只许持平或下降 |
| 模块依赖方向 | [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)（只看了说明） | — | 备选。先用脚本查两条（`shared` 不引 `server` 与 `client`，`client` 不引 `server`） |
| 文档死链 | [lychee](https://github.com/lycheeverse/lychee)（只看了说明） | 自己写的脚本查过：相对链接死链 0，引用了不存在的文档 1 处（用例里故意的） | 用脚本（不用下载二进制、只查仓库内的链接） |
| 打包体积 | [size-limit](https://github.com/ai/size-limit)（只看了说明） | 首屏主包 811 KB（gzip 241 KB） | 二期用脚本记基线，超了 CI 提示 |
| 测试质量 | Vitest 自带的覆盖率（v8）；[Stryker](https://github.com/stryker-mutator/stryker-js) 变异测试（只看了说明） | 228 个集成测试文件里 31 个不要数据库 | 三期：覆盖率记基线、分出秒级一档；变异测试太重，不做 |
