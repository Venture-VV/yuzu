## 1. 储值退回（MP21）

会员要把储值里的钱退回去（多半是不来了、退卡）。退的是**本金**；**赠金扣回、不退钱**。

### 1.1 谁办、谁批

- 会员详情「退储值」：店员及以上能发起（新权限「退储值」）；**店主或店总当场授权**，授权人在弹窗里输自己的账号密码，记在单子上（M69）。
- 授权与「超过单笔上限」同一套：一次性，5 分钟内有效，绑定这位会员与退的金额。店主、店总自己办时，再输一次自己的密码确认。

### 1.2 退多少、赠金怎么扣

- 退的本金在本金余额以内，默认全退。
- 赠金按退的本金占本金余额的比例扣回，四舍五入到分；本金退到 0 时，剩下的赠金全部扣回（M70）。
- 赠金扣回时，先扣这几笔充值自己的赠金批次，不够再按最早到期的扣。

### 1.3 按原收款方式退（M71、M72）

- 先进先出地消费：剩下的本金算作最近的几笔充值。所以退的本金按**最近的充值先退**，分到每一笔充值上。每一行用那一笔充值的收款方式，每一笔累计不超过它收的钱。
- 期初余额（老卡迁移）与合并转入的本金没有原收款方式，按员工选的方式退。
- 页面先列出分配结果，员工核对后提交；提交时服务端重新分配，与页面的不一致就拒绝（`REFUND_ALLOCATION_CHANGED`）。
- **现金**：从选定的钱箱退，与退款单同一套（所选钱箱当班的班次）；不选就是自己的班次。
- **微信、支付宝、银行卡**：在商户后台原路退回后，登记退款单号。
- **其他**：写明怎么退的。
- **线上充值（小程序）的那一行**：原路退回由小程序线接上（`MP_RECHARGE.md` 2d）。接上之前，在商户平台手动退、登记退款单号。

### 1.4 记账

- 一张退储值单（单号 `TC…`）+ 每一行（哪一笔充值、方式、金额、退款单号）+ 一条余额流水「储值退回」（本金减、赠金减）+ 赠金批次的扣回记录。
- 只追加，**不能作废**（M74）：员工与授权人当场核对过；登记错了按实际补一笔充值，或再退一次。
- 「结果待确认」与充值同一套：本机保存原编号与原请求、读回核对、确认作废。

### 1.5 对档阶、券、权益的影响（M73、M74）

- 退回的本金从那一笔充值里扣掉：滚动 365 天累计充值按「充值 − 退回」算，以后的升档按扣完的算。
- **降档**：同时满足下面两条，就当场降到够得上的那一档的初阶，会籍周期不变，记一条状态变化「储值退回」：
  - 会员现在的档级是本会籍周期里靠充值升上来的；
  - 扣掉退回以后，滚动累计充值够不上这一档。

  靠保级、手动调整、上线定档留在这一档的不降。
- **连续退回、最多降到哪**（做的时候补充，测试会话 c938e79 的 P2）：退过一次、降过一档的，剩下的这一档仍算那次充值升上来的，再退照样按滚动累计降（L3 退一部分降到 L2，再退清降到 L0）；最多降到靠充值升上来之前的档级——从最近的状态变化往回找，连着的「充值升档」「储值退回降档」算一段，这一段之前的档级（上线定档、保级、手动调整等留下的）不因退回而降。
- 已经发的券不收回（充值赠券、升级礼、每月的券）；权益的使用记录、临时身份不动。

### 1.6 账怎么算

- 储值退回不是营业额，是储值（负债）减少、钱退回去。
  - **日结**「储值」一节加「储值退回」（按方式）。储值余额的核对式加一项：期初 + 充值 + 期初导入 − 消费 + 撤销 − 过期作废 − 储值退回 = 期末。
  - **交班**：退的现金从那个钱箱的应有现金里减；扫码、银行卡列出来。
  - **看板、营业数据、对账包**：充值旁边单列「储值退回」，净充值 = 充值 − 退回。
- `check` 加：
  - 每张退储值单 = 它的几行 = 它的流水；
  - 每一笔充值退过的不超过它收的钱；
  - 赠金扣回与批次记录一致。

### 1.7 锁

- 经办人或所选钱箱的班次（共享锁，与退款单一样）→ 会员一行（到期没处理的先在这里处理）→ 授权核销。
- 读充值与退过的金额在会员一行锁住以后（同一会员的充值、消费、退回都串行）。

已做（`src/server/modules/member-refunds.ts`：`GET /api/members/:id/refund-plan` 先列分配、`POST /api/members/:id/refunds` 提交、`GET /api/member-refunds/:id` 单据；会员详情「储值与账户」→「退储值」；测试 `tests/member-refunds.test.ts`）：日结「储值」一节、交班、看板、营业数据与对账包（`11-储值退回.csv`）都已单列；`check` 加 2 项（退储值单 = 几行 = 流水；每笔充值退过的不超过它收的钱、赠金扣回与批次一致）。

## 2. 线上收款入口（给小程序第二期，`MP_RECHARGE.md` 第 5 节第 1–3 条）

小程序线的充值单到账时，在**它自己的事务里**调用钱包的线上收款，与充值单记「已到账」一起提交（M75）。已做（`src/server/modules/wallet-online.ts`，测试 `tests/wallet-online.test.ts`）。

- **函数**：`rechargeOnline(tx, deps, { memberId, paidAmount, planId, paymentRef, orderNo, at? })`，返回 `{ recharge, replayed, memberId, mergedFrom, frozen, grade }`：
  - `paymentRef` 是微信支付的交易单号（`transaction_id`），`orderNo` 是小程序线的充值单号（记在充值单的备注里），`at` 是到账时刻（默认现在，按它算营业日）；
  - `recharge` 是充值单（`RechargeDoc`，带 `channel: 'mp'`）；`replayed` 为真时是同一个交易单号已经入过账、这次没有再记账；
  - `memberId` 是实际入账的会员，`mergedFrom` 见下面合并；`frozen` 见下面停用；`grade` 是这次入账前后的档级（重复调用时为空）。
- **加锁**：函数里锁会员一行（同一会员的充值、消费、退回都串行）。调用方可以先锁会员一行、再锁自己的充值单一行，然后调用（同一事务里已经锁住的会员不会再等）；调用之前不要锁会员以外的业务行。同一张单的重复通知在调用方的充值单一行上排队，交易单号的唯一索引兜底。
- **经办人**：系统账号「小程序」（`system.mp`，第一次线上入账时建；停用、没有能对上的密码，不能登录；员工名单里没有，不能改、不能重置密码）。日结「按经办人」里线上的记在「小程序」名下。
- **渠道**：充值单记 `channel = 'mp'`，前台的是 `'counter'`。
- **不进班次**：`shift_id` 为空，不进任何收银员的交班表、不算哪个钱箱的钱。
- **收款方式**：微信；收款备注记微信支付的交易单号。按 `(channel, payment_ref)` 唯一，同一个交易单号只入账一次：再调用返回第一次的充值单；同一个交易单号金额或会员对不上拒绝（`ONLINE_REF_CONFLICT`）。
- **金额与赠金**：
  - 赠金按充完以后所在档自动算（不能自定义），按到账那一刻的规则；
  - 首充 / 续充最低（`RECHARGE_BELOW_MIN`）、单笔上限（`RECHARGE_OVER_LIMIT`）照旧，不够或超过直接拒绝（线上没有当场授权）；
  - 套餐只核对金额与是否启用（`PLAN_CHANGED`、`PLAN_UNAVAILABLE`）；套餐上挂的券照发；
  - 升档、首充礼、升级礼与前台充值同一套。
  - 拒绝时抛错，调用方的事务跟着回滚；钱已经付了的，由小程序线记异常给店主看（店主可以临时调规则后补单，或在商户平台原路退回）。
- **停用、合并**（与 `MP_RECHARGE.md` 第 3 节一致）：到账时会员已停用的，钱已经付了，**照样入账**、结果里 `frozen` 为真，小程序线记异常给店主看；来源会员已合并到另一位的，记到合并进去的那位（`memberId` 是那位，`mergedFrom` 是原来的会员），同一个交易单号按来源会员再到也认得出。
- **只读预估**：`previewOnlineRecharge(db, deps, memberId, paidAmount)` 返回这笔充完的赠金、档阶、首充还是续充、单笔最低与上限、会员是否停用、合并到了谁；到期没处理的按规则推算，不写任何东西（下单页「以到账时为准」）。
- **报表**：日结「充值实收」下单列「其中线上（小程序）」（日结页、打印、导出与对账包的日结汇总）；看板「会员充值实收」下单列；交班表不算它。充值单详情写明渠道与微信支付交易单号。
- **储值退回**：线上那一笔按原收款方式（微信）退，退款页标「小程序」；原路退回由小程序线接上（`MP_RECHARGE.md` 2d），接上之前在商户平台手动退、登记退款单号。

## 3. 会员停用 / 启用、换手机号（M76、M77）

### 3.1 停用 / 启用

- 会员详情「停用」「启用」：店主、店总（新权限「停用、启用会员」），写原因。每次一条记录（只追加），会员一行记当前状态。
- 停用以后：
  - 不能充值、储值消费、结账用储值（原来就拦）；
  - 不享会员折扣、浴票延迟、VIP 柜（按散客）；
  - 不发每月的券与事件礼，不能邀请体验、赠送会籍、被邀请；
  - 小程序会员码用不了（小程序线原来就拦）。
- 停用不动余额与档阶。启用以后照常，到期处理照常算。
- 有在店手牌的会员不能停用（先结账）。
- 已做（`src/server/modules/member-admin.ts`，`POST /api/members/:id/status`，测试 `tests/member-admin.test.ts`）：同一编号重提返回原来那条、结果待确认可查回 / 重提 / 作废（业务类型「停用 / 启用会员」）；停用的会员接待时 VIP 柜按散客（0 级），临时身份也不算；会员详情「储值与账户」列出停用 / 启用记录。

### 3.2 换手机号

- 编辑会员时改手机号：值班经理及以上（新权限「改会员手机号」）可以直接改；店员、客户经理改要值班经理及以上当场授权（授权绑定这位会员与新号码）。
- 都要写原因。每次一条换号记录：旧号、新号、经办人、授权人、原因。
- 新号已被别的会员用了照旧拒绝（要合并的走第 4 节）。
- 小程序：绑定按会员，换号以后原来的绑定还在。建议小程序线在会员换号后要求重新验证（已告知小程序线）。
- 已做：编辑会员改了手机号时页面多一栏「改手机号的原因」；没有「改会员手机号」的岗位保存时弹出当场授权（授权绑定会员与新号码，号码对不上拒绝）；只改别的资料不用原因、不用授权。换号记录列在「储值与账户」下面。

## 4. 会员合并（M78、M79）

同一个人建了两份档案（多半是换过手机号）：把「来源会员」并进「目标会员」。

### 4.1 怎么并

- 会员详情「合并到…」：店主、店总（新权限「合并会员」），选目标会员，写原因。
- 前提：
  - 两位都在用（没停用、没被合并过），不是同一位；
  - 来源会员没有在店手牌、没有体验中的临时身份、没有能用的券（先用掉，或作废后给目标会员手动补发）。

### 4.2 并了以后

- **余额**：本金、赠金全部转到目标会员。两条余额流水：来源「合并转出」、目标「合并转入」。赠金批次按原来的到期日搬过去。
- **档阶**：目标会员取两位里高的那个状态（档级、阶位、会籍周期、补充期），记一条状态变化「合并」。
- **以后的计算**：滚动累计充值、周期储值消费、是不是首充，都把来源会员的充值与消费算进去。
- **来源会员**：停用，标「已合并到 X」。手机号留在原档案上（历史单据还在原档案上）；查找时显示「已合并到 X」，点进去跳到目标会员。
- **储值退回**：转入的本金没有原收款方式，按员工选的方式退（第 1.3 节）。
- 合并不能撤销（两条档案的余额已经合在一起）。

### 4.3 做的时候定的细节（M78、M79 补充）

- **前提多一条**：来源会员**今天有储值消费**的不能合并（今天的单子可能还要撤销或反结账），明天再并。
- **合并以后来源会员不能再记账**：它合并之前的储值消费不能再撤销、对应的结账单不能反结账（余额已经转走；要更正在目标会员那里办理）；接待时选它会提示「已合并到 X」；资料不能再改；期初导入按它的手机号匹配到时整行拒绝（期初记到目标会员）；小程序线上到账记到目标会员（第 2 节）。
- **页面**：「储值与账户」上的「合并到…」先按手机号、姓名或会员号找目标会员，核对两位的余额、档阶、合并以后的档阶与不能合并的原因，写原因、勾「不能撤销」后确认；核对以后余额变了拒绝（重新核对）。
- **赠金批次**：来源批次记「合并转出」，目标会员新建同到期日的批次（记来源批次与合并单）；储值退回扣回赠金时与别的批次一样按到期先后扣。
- **档阶取高**：档级 → 阶位 → 不在补充期的高 → 会籍周期结束得晚的高；取了来源会员的状态时记一条「合并」，不发升级礼、不当场补本期的券（来源会员这一期的已经发过）。
- **自检**：加 2 项——合并单 = 转出 = 转入 = 搬过去的赠金批次、来源会员停用并记合并到目标；被并走的会员余额为 0、没有在店的来访。
- **与接待、停用并发**（测试会话 dcbf252 的 P2）：合并、停用 / 启用都在锁住会员一行以后才核对「有没有在店手牌」；接待在写来访之前对会员一行加共享锁（id 升序），锁住以后再核对没被合并、状态没变（合并了拒绝 `MEMBER_MERGED`，刚被停用 / 启用拒绝 `MEMBER_CHANGED`、重新核对）。原来接待只读核对，合并在它核对之后、写入来访之前提交时，合并走了余额的原档案照样被接待到店。
- 已做（`src/server/modules/member-admin.ts`，`GET /api/members/:id/merge-check`、`POST /api/members/:id/merge`，测试 `tests/member-admin.test.ts`）。

## 5. 同行优惠（QY-041，M80、M81）

会员文档：L3 起，高档可带 1 人、最高档 2 人；不照搬福田同行 88 折。

### 5.1 配置

- 折扣类加两种适用明细：「同行的门票」「同行的整张账单」。
- 加「同行几位」：起点一个数，各档阶一张表，与折扣的各档阶表同样按会员现在的档阶取一行、不相加。
- QY-041 导入时预填：
  - 起点 L3·初、同行 1 位，L6·初 起 2 位，适用「同行的门票」；
  - **不填折扣**，所以发布不了，等店主定了折扣再发布。

### 5.2 怎么算

- **同行**：合并结账里，这位会员本人以外、不是会员的客人。会员客人按自己的会员折扣算。
- **几位、哪几位**：每位能享的会员最多带「同行几位」。按省得多的先挑；相同时按手牌号。
- **金额**：这几位同行的适用明细合计 × (1 − 付几成 ÷ 100)，四舍五入到分。
- **与别的折扣**：一单一种（M13）。同行优惠与会员本人的折扣比较，自动用省得多的那一种；与券、「优惠 / 免单」二选一。
- **记账**：收款明细「会员折扣」记会员、权益与版本，备注写明打的是哪几位同行的手牌；适用明细只记那几位同行的，部门营业额快照照此分摊（与券抵扣同一个函数）。
- 桌台结账不算（M48）。

### 5.3 做的时候定的细节（M80、M81 补充）

- **谁算同行**：合并结账里没有挂会员的客人。挂了会员的客人（包括已停用的会员）不算同行——会员按自己的会员折扣算，停用的会员什么折扣都不享。
- **金额为 0 的不挑**：同行的适用明细合计为 0（比如门票已经结过、只剩 0 元）时不挑他，挑下一位；一位都挑不出来时不列同行优惠。
- **几位会员都能带**：每位能享的会员各算一项（各带自己的「同行几位」），一单一种，仍是省得最多的那一项自动带上；不会两位会员各带几位同行叠加。
- **结账前核对**：按此刻算出的门票（还没挂到账单）一起算，与本人的门票折扣一样；结账事务里在门票挂到账单、会员一行锁住以后按此刻的明细重新算，与员工确认的不一致时拒绝（`MEMBER_DISCOUNT_CHANGED`）。
- 已做（`src/server/modules/member-discounts.ts` 的 `pickCompanions`、`discountOptions`；后台「会员权益」的折扣类编辑加「起点能带同行几位」与各档阶表；测试 `tests/companion-discount.test.ts`、`tests/upgrade-ticket-extension-defaults.test.ts`）。

### 8.1 发券入口「小程序领取」（2c，`MP_COUPONS.md` 第 3 节，MP22）

```ts
// src/server/modules/coupons.ts
issueMpClaimCoupon(tx, deps, { templateId, memberId, claimId, at? })
  → { issueId, issueNo, replayed, coupon }   // coupon 与会员的券同一结构（券码、有效期、状态）
```

- 小程序线在自己的事务里调用，与它的领取记录一起提交；拒绝时抛 `AppError`，调用方的事务跟着回滚；
- 发券记录的种类「小程序领取」（`mp_claim`），经办人是系统账号「小程序」（`system.mp`，与线上收款同一个），一次 1 张；有效期、门槛、范围照模板；
- 同一个领取记录只发一次：去重键 `mp_claim:<claimId>`，再调用返回第一次那张（`replayed`）；同一个 `claimId` 已经发给别的模板或会员时拒绝（`MP_CLAIM_CONFLICT`）。`claimId` 是正整数，或 64 字以内的字母、数字、`_`、`-`；
- 拒绝：`NOT_FOUND`（会员或模板不存在）、`MEMBER_MERGED`、`MEMBER_FROZEN`、`TEMPLATE_INACTIVE`、`TEMPLATE_EXPIRED`（固定有效期已过）、`COUPON_LEVEL`（档级不在模板限定的里面，与手动发券一样看会员一行上的档级）；
- 哪些模板小程序可领、每人限领几张、领取记录，是小程序线自己的（迁移 `048`），这里不管；
- 锁：入口里对会员一行 `FOR UPDATE`（调用方已经锁过就不会再等；与停用、合并串行）→ 模板共享锁（与改模板串行）。两个事务同时发同一个领取记录也只出一张；
- 会员详情的券、发券记录里照常显示，种类写「小程序领取」；
- 领券中心的列表用只读判断 `mpClaimEligibility(db, deps, { templateId, memberId, at? }) → { ok, code?, message? }`（小程序线 11-04 要的）：与发券同一套规则、同样的拒绝码，不加锁、不发券；领没领满是小程序线自己的领取记录。列表与真正领取之间规则可能刚好变了，以领取时的结果为准。

### 8.2 退储值：线上充值那一行交给门店系统原路退回（2d，`MP_RECHARGE.md` 第 9 节，MP21）

- 退储值的每一行加「怎么退」：**员工退**（`manual`，v0.7.26 的做法：现金从钱箱退，扫码、银行卡在商户后台退后登记单号）或**门店系统原路退回**（`mp_auto`）；
- `mp_auto` 只能用在来源是线上充值（渠道 `mp`）、微信付的那一行，退款单号空着（数据库约束兜底：只能是充值、微信、不带单号）；员工已经在小程序的商户平台退过的，照旧选员工退、填退款单号，门店系统不会再退；
- **开关在小程序线**：小程序线的原路退回接上、微信支付配好并打开时，在启动时注册
  `registerOnlineRefundRoute({ available: async (db) => boolean })`（`src/server/modules/member-refunds.ts`）。没注册、`available()` 为 false 或出错时，核对接口返回 `onlineRoute: false`，页面不给选，提交 `mp_auto` 拒绝（`ONLINE_REFUND_UNAVAILABLE`），与 v0.7.26 一样要在商户平台退、填退款单号——不会出现「标了自动退、但没有人退」，也不会退两次；
- 小程序线按行取：`listOnlineRefundLines(db, { afterId, limit })`，按行号升序给 `mp_auto` 的行（`lineId`、`refundId`、`refundNo`、`memberId`、`rechargeId`、`rechargeDocNo`、`paymentRef` 即充值单上的微信支付交易单号、`amount`、`createdAt`），小程序线按 `lineId` 唯一建原路退回单；
- 小程序线怎么取（2026-11-04 小程序线告知）：`pullRefundLines` 先只读查 `member_refund_lines`，找还没建原路退回单的最小行号（`min(id) … WHERE route = 'mp_auto' AND NOT EXISTS 原路退回单`），再从那里起用 `listOnlineRefundLines` 一页一页取。不加锁、不写。不能只记「取到的最大行号」：行号插入时分配，提交顺序可能不同，晚提交的小行号会漏。所以小程序线依赖 `member_refund_lines.route` 这一列和 `'mp_auto'` 这个值；主线以后要改名、换表或加新的取值，先告诉小程序线。小程序线的 `available()` 在门店系统的微信支付配好、而且小程序线「线上充值」设置里的自动原路退回开着（默认开）时才回 true；关掉只影响以后的退储值，已经交出去的照样退完；微信退不了的在小程序线后台处理；
- 页面：会员详情「退储值」里线上那一行可选「门店系统原路退回」（开着时默认）或「已在商户平台退过」（填单号）；没开时写「请在小程序的微信支付商户平台原路退回后填退款单号」；退过的储值写明「门店系统原路退回」；
- 账：退储值单照旧（本金、赠金扣回、流水、降档都不变）。日结「储值退回」单列「其中退线上充值（小程序）」——钱从小程序的商户号退，其中交给门店系统的多少；异常清单与对账包 `11-储值退回.csv` 的单号一栏写「门店系统原路退回（小程序）」；
- 员工退的行不带 `route` 进请求摘要：v0.7.26 的页面提交、升级后「结果待确认」原样重提，仍是同一笔。
- 默认做法记在 `PENDING_DECISIONS.md` M82（待确认）。
