# 8.0.21 设计 · 对外接口（支付直连、平台验券、OTA、开票与银企直连的适配器）

排期见 `docs/SCHEDULE_V8020.md` 第 3 节 CW-G、CW-H、CW-I；默认做法 CW7–CW9 已确认，细分出来的记在 `docs/PENDING_DECISIONS.md`（CW11 起，店主 2026-11-14「都按默认」）。财务部分见 `docs/FINANCE_V8021.md`。

开工前读代码核对的现状：

- **收款方式**：结账 `CHECKOUT_METHODS`（现金类 `wechat|alipay|cash|bank_card|other` + 储值、团购券、券、优惠、会员折扣、次卡、挂账），现金类只记「方式 + 金额 + 参考号」，收银员手选方式、手输金额；充值同样（`recharges.payment_method / payment_ref`）。退款单只能按原方式退，退的是记账，不碰支付方。
- **小程序线**有微信支付（JSAPI）的客户端与模拟（`mp/pay.ts`、`mp/wxpay*.ts`），那是小程序线的目录，主线不改、不引用；主线没有任何「支付方 / 适配器」的抽象。
- **团购券**：结账时手选平台（美团 / 点评 / 抖音 / 其他）、手输券码与项目，存 `group_buy_coupons`（同一平台同一券码只有一张有效的，「平台 + 券码」咨询锁与「平台核销补录」共用）。不向平台验券。
- **客房预约**：`bookings`（`kind room`，按房型占房量，来源 `front|phone|mp`，不收钱），到店后按预约入住（`room_stays.booking_id`）。没有渠道订单。
- **扫码**：设备桥（WebSocket）有扫码枪事件，前台页面也认键盘输入式的扫码枪。

## 1. 适配器的做法（三样共用）

- `src/server/integrations/`：每一种对外接口一个**接口**（`PayTerminal`、`PlatformVoucher`、`EInvoice`、`BankDirect`）+ 一个**模拟实现** + 将来的正式实现。
- 每一样的模式：`off`（没配置）/ `mock`（模拟）/ `live`（正式）。**模式只由运行环境决定**：
  - 模拟：`INTEGRATIONS_MOCK=true`，只许在 `APP_ENV` 是 development、test，且实例不是 `prod|shadow|test`（与小程序线 `MP_PAY_MOCK` 同一个规矩），和任何正式密钥同时出现时拒绝启动；
  - 正式：对应的密钥都在环境变量里才算配置好（名字见第 6 节）；**密钥只放运行环境，不进库、不进仓库、不进聊天与飞书**。
- **8.0.21 只做接口与模拟实现**；正式实现等店主拿到商户号、平台应用后联调时做（`docs/SCHEDULE_V8020.md` 第 5 节）——没有账号写出来的正式实现测不了，接错了就是真钱。页面与流程按正式的样子做完，联调时只换实现。
- 每次对外调用记一行 `integration_calls`（接口、动作、业务对象、请求摘要（打码）、结果、耗时、错误），后台「对外接口」页能看最近的、能按对象查；不记付款码、密钥、完整手机号。这张表开票「交给服务商开」最先用到，**挪到迁移 `143` 建**（`src/server/integrations/calls.ts` 的 `withCallLog`）。
- 已做（8.0.21 第一块，随开票）：`src/server/integrations/config.ts`（模式只看运行环境；`INTEGRATIONS_MOCK=true` 只许开发、测试，且实例不是 prod / shadow / test，与正式密钥同时配置时拒绝启动）、`calls.ts`、`einvoice.ts`（模拟：99 开头的 20 位号码 + 一页写着「MOCK」的 PDF）。用例的配置默认是模拟的（`tests/helpers.ts`）。
- 后台「场地、设备与线上」新分区「对外接口」（`settings.manage`）：每一样现在是哪种模式、门店开关（启用扫码收款、启用平台验券、自动对账的时间）、最近的调用。

## 2. 支付直连（CW-G，迁移 `148`）——已做（接口与模拟实现）

B 扫 C：收银员扫客人的付款码，到账自动记收款（CW7）。

- `pay_transactions`：支付方（`wechat|alipay`）、用途（`checkout|recharge`）、本店单号（唯一）、金额、状态 `paying|paid|failed|closed|refunding|refunded`（只往前走）、支付方单号、付款时间、用掉它的结账单 / 充值（`consumed_kind`、`consumed_id`）、经办人、班次、操作编号；`pay_refunds`：退款（原交易、金额、原因、状态 `pending|done|failed`、支付方退款单号、来源退款单）。
- **收款**（结账、充值的收款区里「微信 / 支付宝」那一行多一个「扫码收款」）：
  1. 扫付款码 → `POST /api/pay/terminal`（操作编号、方式、金额、付款码）→ 先写一条 `paying` 的交易（提交），**事务外**调支付方；
  2. 支付方说成功 → `paid`；说「用户正在输密码」→ 页面每 3 秒查一次（`GET /api/pay/terminal/:id`，服务端去支付方查），最多 60 秒；超时、断网 → 状态不确定，按支付方查回为准（每分钟的任务继续查，查到失败或超过 5 分钟没结果的去支付方撤单，撤成功记 `closed`）；
  3. `paid` 以后这一行锁定（金额、方式、参考号 = 支付方单号），收银员照常点结账 / 充值；结账、充值的请求里带交易编号。
- **入账**：结账、充值的事务里，在现有的锁之后锁交易一行（`FOR UPDATE`，几笔按 id 升序），核对 `paid`、没被用过、方式与金额一致，记 `consumed_*`；同一笔交易只能用一次（部分唯一索引）。收款明细照旧记 `wechat|alipay`，`ref` = 支付方单号，另记交易编号。
- **收了钱没入账**（结账被拒、关了页面）：交易停在 `paid` 没被用，前台顶上提示「有 N 笔扫码收款还没入账」，可以挂到下一次结账 / 充值，或「原路退回」（调支付方退款，写原因，`pay_refunds`）。交班时还有没入账的拦着、要先处理。
- **反结账**：用过的交易解开（`consumed_*` 清掉、记一条变化），回到「没入账」，由收银员挂到重新结账或原路退回——**反结账本身不自动退钱**（与现在一样，反结账只撤销记账）。
- **退款单**：原方式是微信 / 支付宝、而且那一笔是扫码收的，退款单上默认「原路退回」：退款单生效的同一事务里写 `pay_refunds`（`pending`），事务外调支付方，结果回写；失败的留在待办、可以重试或改成「线下已退」（写原因）。不是扫码收的照旧只记账。
- 锁：收款先取操作编号的咨询锁（新业务类型 `pay_terminal`，与「确认作废」串行）→ 写交易（新行）；查询、撤单、退款只锁交易一行（`FOR UPDATE`），对外调用都在事务外；入账在结账 / 充值原来的锁之后锁交易行；反结账在结账单之后锁它用过的交易（id 升序）。
- 现在手选「微信 / 支付宝」、手输金额的做法**照旧留着**（CW7）——没配置支付直连、或客人用的是别的码时用。
- **做出来的样子**（8.0.21）：
  - 交易状态只有 `paying|paid|failed|closed`（只往前走，触发器兜底）；退款不改交易状态，记在 `pay_refunds`，交易上的 `refund_cents` 是已经申请退的（待退、已退、失败待重试、线下已退都算），退过款的不能再入账。用掉、解开记在 `pay_tx_events`（只追加）。本店单号 `YZP<日期><序号>`、退款单号 `YZR<日期><序号>`；不存付款码，对外调用记录里只留后四位。
  - 接口：`/api/pay/terminal`（开始收款，带操作编号；同一编号原样重提返回那一笔）、`/:id`（查，支付中的去支付方查）、`/open`（没入账、支付中、原路退款没完成的）、`/by-key/:key`（结果待确认时按编号查回）与 `/by-key/:key/abandon`（确认作废，新业务类型 `pay_terminal`）、`/:id/refund`（没入账的整笔原路退回）、`/api/pay/refunds/:id/resolve`（失败的重试或改线下已退）；开始收款要「结账收款」或「会员充值」，退回要「开退款单」。
  - 结账（手牌、桌台）的现金类收款、充值单带 `payTxId`；收款明细 / 充值单记下交易编号（`checkout_payments.pay_tx_id`、`recharges.pay_tx_id`），参考号是支付方单号。反结账解开（回到没入账），不自动退钱。退款单的微信 / 支付宝一行勾「原路退回」时不用登记退款单号（`refund_payments.via_terminal`），超过扫码收的拒绝；有原路退回的退款单不能作废。交班时这个班次有没入账、支付中的拦着（`PAY_UNSETTLED`）。
  - 页面：结账收款行、充值的「微信 / 支付宝」旁边「扫码收款」（扫码枪像键盘输入、回车）；扫码对话框里也能挑一笔没入账的同方式、同金额的直接用；前台顶上「N 笔扫码收款收了钱没入账」→ 去处理（原路退回、查结果、重试、线下已退）。模式是 off、live（等联调）或门店关了时不显示按钮，照旧手选。
  - 模拟实现按付款码尾号给结果：0000 余额不足、1111 第二次查询到账、2222 一直等（5 分钟后撤单）、3333 退款失败，其余直接到账。

- 原路退款停在「退款中」（记下退款以后进程停了、没去支付方退）：每分钟的任务把超过 1 分钟的再去退一次，前台「收了钱没入账」里也能点「再去退一次」；都用原来的退款编号，支付方按它只退一次（Codex 审查 `55ccc5e` 后补）。

## 3. 平台验券（CW-H，迁移 `149`）——已做（接口与模拟实现）

美团、抖音各一个适配器，验券即核销（CW8）：

- `platform_verifications`：平台（`meituan|douyin`）、券码、项目名、面值、结算价、份数、状态 `verifying|verified|failed|cancelled`、平台核销单号、用掉它的团购券记录（`group_buy_coupon_id`）、经办人、操作编号。
- **结账**：团购券那一行选了美团 / 抖音、输入（或扫）券码后点「验券」：
  1. `POST /api/platform/verify/prepare` → 平台返回项目、面值、能核几份（只读，不核销）；
  2. 收银员确认 → `POST /api/platform/verify`（操作编号）→ 写一条 `verifying`，事务外调平台核销 → `verified`；
  3. 这一行锁定（项目、金额 = 面值），结账请求里带核验编号；结账事务在「平台 + 券码」咨询锁之后锁核验一行，核对 `verified`、券码一致、没被用过，团购券记录挂上核验编号。
- **核了没结账**：前台提示；可以挂到下一次结账，或「撤销核销」（调平台撤销；平台只许核销后一段时间内撤，过了就只能转成「平台核销补录」记一条，钱照样是平台结算）。
- **反结账**：团购券记录作废（与现在一样），核验回到「没用」，同上处理。
- **平台不通**：照旧手输（不验券），和现在一样；补录（`platform_redemptions`）也照旧。
- **每天对账**：每天设定的时间（默认 06:10）按平台拉前一天的核销明细（适配器的 `bill`），与团购券记录、补录对：平台有、系统没有的，系统有、平台没有的，金额不同的，进「平台 → 对账」与 ERP 待办；人看过后标「已处理」。
- 锁：核销先取操作编号的咨询锁（新业务类型 `platform_verify`）→「平台 + 券码」咨询锁（与结账、补录同一把）→ 核对团购券、补录、核验三处都没有这张有效的 → 写 `verifying`；结果回写只锁核验一行。
- **做出来的样子**（8.0.21）：
  - 状态：`verifying → verified | failed`；`verified → cancelled`（撤销核销）| `recorded`（平台不让撤了，转成一条平台核销补录，`redemption_id`）；触发器兜底只往前走、平台核销单号不改。用掉时 `group_buy_coupon_id` 挂上团购券记录（结账单的团购券记录多了 `verification_id`），反结账解开。同一平台同一券码同时只有一张核销中 / 已核销的（部分唯一索引）。
  - 结账：团购券那一行选美团 / 抖音、填券码后「验券」→ 先问平台（`/api/platform/verify/prepare`，只读）→ 确认核销（`/api/platform/verify`，带操作编号，平台此刻的面值与看到的不一样拒绝 `VOUCHER_CHANGED`）→ 这一行锁定（平台、券码、项目、金额 = 面值）；验券对话框里也能挑一张「验过还没结账」的同平台的直接用。手输的团购券（不验券）不能是已经验过的（`COUPON_VERIFIED`）；补录也不能登记验过还没用的。
  - 验券请求发出去之前先把操作编号与原请求存在本机、读回核对（存不了就不发，照旧手输）；超时、断网、5xx 以后关掉对话框、刷新页面再打开，照样按原编号查回或确认作废，查清之前不能再验（与扫码收款同一个做法，Codex 审查 `beabd59` 后补）。
  - 停在「核销中」的（写了「核销中」、还没写回结果进程就停了）：过 2 分钟由每分钟的任务、或原样重提时，按我们的核销编号去平台**查**（`query`，只查不核销——不能再调一次核销，客人可能已经走了）：平台核销了的补成「已核销」，平台上没有的记「没成功」（券可以重新验），查不到结果的下次再查（Codex 审查 `55ccc5e` 后补）。
  - 前台顶上「N 张团购券验过还没结账」→ 撤销核销（`platform.void`，值班经理以上；平台不让撤的 `CANCEL_FAILED`）→ 转补录。撤销先在锁里「占住」（记下撤销人与原因、还不记撤销时刻，页面上显示「撤销中」）再去问平台：占住时结账用不了（`VERIFICATION_CANCELLING`）、转补录不了；平台撤了记「已撤销」，平台明确不让撤放开占位，平台没回应留着「撤销中」（`CANCEL_UNKNOWN`，再点一次会再问平台）；同一次验券同时只有一个撤销（会话级咨询锁，`CANCEL_IN_PROGRESS`）。（Codex 审查 `354e34c` 后补：原来先问平台再锁，结账可能在中间用掉这张券。）
  - 对账：每分钟的任务在设定的时间（后台「对外接口」，默认 06:10）以后，对前一个营业日每个平台跑一次（`platform_recon_runs`，自动的 `staff_id` 为空）；也可以在「平台核销补录 → 验券对账」手动对任一天（`platform.settle`）。比的是平台核销明细 与 结账里的团购券 + 补录（有效的）：平台有系统没有、系统有平台没有、金额不同（`platform_recon_issues`），人看过写说明标已处理。页面上只看每天最近一次对账的差异。
  - 模拟按券码尾号给结果：0000 不存在、2222 两份 ¥398、9999 撤销不了、5555 第一次撤销平台没回应（再撤一次才撤掉）、7777 不进对账单，其余美团 ¥99（应结 ¥92）、抖音 ¥88（应结 ¥82）。

## 4. OTA 渠道订单（CW-I，迁移 `150`）——已做

先做渠道订单表导入成预约，直连是可选项；房量房价不自动推给渠道（CW9）：

- `ota_channels`：名称（携程、美团酒店、飞猪……）、佣金比例、**渠道房型 → 本店房型**的对照、导入用的列对照、启用。
- 导入渠道后台导出的订单表（CSV / xlsx）：订单号、入住人、电话、渠道房型、入住日、离店日（或晚数）、间数、金额、付款方式（预付 / 现付）、状态。`ota_orders`：渠道 + 订单号唯一，存原始行、状态 `new|booked|cancelled|failed|skipped`、对应的预约（几间就几张）。
  - 新订单 → 按对照的房型建客房预约（`bookings`，来源新加 `ota`，备注写渠道与订单号），房量不够照样建、标「超订」提醒；对照不上的房型记 `failed`、等人补对照后重试。
  - 再导一次：渠道里取消的 → 没到店的预约取消；日期变了 → 没到店的改时间；已经到店的只提醒。
- **钱**：预付的订单，客人入住、结账时房费照常挂在手牌账单上，收款区默认带一行**团购券**（平台「其他」、券码按渠道 + 渠道订单号生成、项目 = 渠道名称 · 房型、金额 = 订单金额，不超过房费）——就是现在团购券的做法，渠道打款照旧在「平台打款登记」登记、对账（CW9「渠道佣金进平台打款登记」）。现付的照常收钱。
- 渠道对账表：按渠道、按月：订单数、间夜、订单金额、佣金（按比例算，可以改成渠道账单上的数）、应收净额、已登记打款，可导出。
- 锁：导入先取操作编号的咨询锁（新业务类型 `ota_import`）→「渠道 + 文件摘要」的咨询锁 → 每张订单在自己的事务里：订单一行（`渠道 + 订单号` 的唯一索引兜底）→ 建 / 改 / 取消预约走预约原来的锁（房型一行 `FOR NO KEY UPDATE`）。
- 入口：前台「预约」页的「渠道订单」页签（`booking.manage`）；渠道与对照在后台「营业项目 → 客房」的新页签（`room.manage` 类的权限，照客房后台）。
- **做出来的样子**（8.0.21）：
  - 渠道在后台「营业项目 → 客房 → 渠道」（`settings.manage` 或 `catalog.manage`）：名称、佣金比例、渠道房型名 → 本店房型；改带版本号。
  - 前台「预约」页右上「预约 | 渠道订单」（`/bookings?view=ota`，`booking.manage`）：选渠道、选订单表 → 先看认出几张、哪些房型没对照（列按同义词认：订单号、入住人、电话、房型、入住日、离店日或晚数、间数、金额、付款方式、状态）→ 导入。同一渠道同一份文件只导一次（`OTA_FILE_DUP`）；导入带操作编号、走「结果待确认」（与网银流水导入同一套：发出去之前把编号与原请求存进本机，存不了不发；没收到结果的记在页面上方，刷新、关掉再开都还在，可以查回、按原内容重新提交——没处理完的订单接着处理——或确认作废，业务类型 `ota_import`；Codex 审查 `e64932b` 后补，原来编号只在页面里，刷新以后换了编号，同一份文件又被 `OTA_FILE_DUP` 拦住，没处理完的订单就补不回来）。订单表放在请求体里，预览与导入的请求体上限放宽到 15 MB（与网银流水导入一样；全局默认 64 KB，原来超过的导不进，Codex 审查 `e64932b` 后补）。
  - 一张订单一个事务：新订单按对照建客房预约（来源「渠道」、已预约，预计到店 = 入住日 14:00，当天已过的按现在；备注写渠道、订单号、几晚、预付 / 现付；客人电话不是 11 位手机号的不记），几间几张；房量不够照样建、订单标「超订」；对照不上的「没建成」（补了对照点「重试」）；入住日已经过了的「跳过」。再导：渠道取消 → 没到店的取消；入住日变了 → 没到店的改时间；间数变了 → 多退少补；房型变了 → 没到店的取消、按新房型重建；已经到店的只在订单上写提醒。单张出错不影响别的（记「没建成」、写原因）。「超订」在每张订单处理完以后按这张订单没到店的预约重算：所在房型、营业日的预约比能用的房间多就标——改到约满的日子也标，只改了金额照样留着，取消、减了间数放得下了就清掉（只读、不加锁；Codex 审查 `e64932b` 后补，原来只看这一次新建的预约，改时间不标，只改金额又把原来的提醒清掉）。
  - 一张没处理成（例如对照的本店房型停用了）：已有的订单只记「没建成」与原因，上一次处理成的房型、日期、间数、金额照旧，这一次的内容留在 `raw` 里；新订单也留一行「没建成」。补好以后点「重试」按这一次的内容来（Codex 审查 `ee51abe` 后补）。
  - 导入记录与逐张处理分在几个事务里：原样重提（同一个操作编号）照样逐张走一遍——这次（或更晚的一次导入）已经处理过的那几张按订单上的 `last_import_id` 认出来记「没变化」，没处理完的接着做；更晚的一次导入改过的那张不拿旧文件盖回去（Codex 审查 `354e34c` 后补：原来重提就整份跳过，断在中间的那几张再也建不出来）。
  - 预约的「最远约几天」、过去时刻的核对对渠道来源不适用；预约的爽约、到店照旧。
  - 结账：这几位客人是按预付的渠道订单到店的（预约的到店手牌），结账核对返回 `otaPrepaid`，收款区打开时默认带一行团购券（平台「其他」、到店的每一间各一行（几间的订单分开结账时各用各的，Codex 审查 `beabd59` 后改）：券码 = `OTA` + 渠道编号 + 订单号里的数字字母（大写，最多 40 位）+「渠道 + 原订单号 + 这一间的预约」摘要的前 8 位——两个渠道同一个订单号、`AB-123` 与 `AB123`、同一订单的两间都不会撞成同一张券（Codex 审查 `354e34c` 后改）；金额 = 订单金额按间数均分（分不尽的摊在前面几间），这一间的券已经用在没反结账的结账单上的不再带、项目 = 渠道 · 房型、金额 = 订单金额，不超过应收）。
  - 渠道对账：按入住月份、已建预约的订单：订单数、间夜、订单金额、佣金（按比例）、应收净额，导出 CSV。渠道打款照旧在「平台核销补录 → 打款与对账」登记（平台选「其他」，备注写渠道）。
- **后台「对外接口」**（`/admin/integrations`，「场地、设备与线上」，`settings.manage`）：每一样的模式（扫码收款、平台验券、开票服务商为「没配置 / 模拟 / 已配置、等联调」；银企直连、OTA 这一版只有文件，固定显示没配置并写明怎么用）、正式接口要的环境变量配没配（只给名字）；门店开关（结账、充值显示扫码收款；结账验券与每天自动对账；对账时间），走规则锁、只改提交的字段；最近 100 次对外调用（打码后的摘要），可以按哪一样、只看失败的筛。

## 5. 电子发票、银企直连

- `EInvoice`：`issue(申请) → {状态, 发票号码, PDF}`、`query`、`red(作废)`。开票申请（`docs/FINANCE_V8021.md` 第 3 节）「交给服务商开」时调用，事务外；模拟实现直接返回一个假号码与一页 PDF（写明「模拟」）。
- `BankDirect`：`pay(批次)`、`query`。批量付款（同上第 5 节）有直连时多一个「直接付款」按钮，没有就只能导出文件。模拟实现按批次逐笔返回成功。
- 两样的正式实现同样等账号（数电票服务商、银行银企直连开通）联调时做。
