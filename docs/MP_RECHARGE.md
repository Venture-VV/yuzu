## 1. 顾客怎么用

1. 「我的」→「充值」：列出店主在后台勾选的充值金额（第 3 节）；后台开着「自定义金额」时，下面另有一个填金额的框（整元）。每一项（或填好的金额）写实付、按充完以后所在档预估的赠金、充完是哪一档、套餐上挂的券；首充、续充有最低额时写明。冻结的会员不能充（MP6）。
2. 点一项 → 确认 → 微信支付。
3. 付完回到小程序：
   - 门店系统已经入账：「充值成功」，写本金、赠金、充完的档阶；
   - 还没入账（到账通知在路上）：「已支付，门店系统入账中」，页面自己再查，最多等 1 分钟，之后可以离开，入账后在「余额与流水」里能看到；
   - 没有付：回到充值页，这张单 15 分钟后自动关掉。
4. 入账后的余额、流水、券、档阶都和前台充值一样显示（同一本账）。

同一位会员同时只能有一张没完成的充值单：还有没付完的，充值页最上面写「有一张待支付的充值单」，让顾客继续付或者取消，免得付两次。

钱付了、门店系统没能自动入账的（第 2 节「已付款待处理」）：结果页写「已付款，门店正在核对」和门店电话，店主在后台处理。

## 2. 流程：下单在门店系统，支付密钥只在门店（MP17）

```
小程序 ──① 下单（选的哪一项）──▶ 网关 ──▶ yuzu：建线上充值单（会员、金额、套餐、预估赠金），
                                              向微信支付下单（JSAPI，带 openid、15 分钟到期），签好支付参数
小程序 ◀─② 支付参数────────────── 网关 ◀── yuzu
小程序 ──③ wx.requestPayment ──▶ 微信支付
微信支付 ──④ 到账通知 ──▶ 网关 /v1/pay/notify（不看内容，原样转）──▶ yuzu：验签、解密、核对单号与金额
                                              → 同一个事务里：钱包充值入账 + 充值单记「已到账」
小程序 ──⑤ 查这张单 ──▶ 网关 ──▶ yuzu（单子的状态）
yuzu ──⑥ 补单：到账通知没送到时自己去微信支付查单（门店断网、网关出错之后）
```

- **为什么放门店**：网关在公网上。支付凭据放在网关，网关被攻破的人就能伪造「已到账」（凭空加储值），也能调退款接口（钱退走了、储值还在）。放在 yuzu，网关只转发：到账通知由 yuzu 自己验微信的签名、自己解密，要核实时 yuzu 自己去查单。门店的 Mac mini 本来就能出外网（备份上传就要），只多连微信支付的接口；进门店的方向照旧不开。
- **只认门店定的金额**：充值单的金额、套餐在 yuzu 建单时定下，小程序传来的只是「选的哪一项」。到账通知里的金额、商户单号、AppID、商户号、付款人 openid 都要和这张单对上，任何一样对不上都不入账，记「已付款待处理」给店主看。
- **记下了才回微信「收到」**：入账了，或者记成「已付款待处理」了，才回收到；验签失败、门店出错都回失败。微信会在 24 小时里按它的节奏重发；门店系统按商户单号与微信交易单号去重，重发多少次只入账一次。
- **门店断外网**：网关转不进门店，回微信失败，微信接着重发。门店连上之后，yuzu 把待支付超过 2 分钟的单子逐张去微信查（补单），已付的照样入账。顾客那边在这段时间里看到「已支付，门店系统入账中」。
- **15 分钟关单**：下单时就告诉微信 15 分钟后过期；到期没付的单子 yuzu 去微信关掉、记「已关闭」。关单之后才到的付款（极少见）照样入账，标出来给店主看（MP19）。
- **结果待确认**：建单、拉起支付、查结果都可能遇到断网、超时。小程序提交前把操作编号和选的哪一项存在手机上（存不了就不发），以门店系统里这张单的状态为准：没收到建单结果时只能原样重提（同一个编号返回同一张单），或请门店系统「确认作废」这个编号再重新选，和第一期绑定的「结果待确认」同一个做法。
- **单子跟着下单时的那条绑定**（小程序线测试 #49 `866ccfa` 的 P1）：充值单记下建单时这个微信的有效绑定。
  - **顾客能做的**：查单、继续支付、取消、模拟支付，同一个编号重提、确认作废，都只认这个微信**现在这条有效绑定**下的单。
  - **建单带确认时的绑定**（小程序线测试 #52 `6ee1e03` 的 P1）：可充项里带这个微信此刻的绑定状态版本号（与「我的」里的同一个数，绑定、解绑各加一），小程序建单时带上。门店系统在绑定锁里比对，版本号变了（确认之后解绑、换绑过）就拒绝（`BIND_STALE`），不建单。这样换绑以后才到的旧请求不会给换绑以后的会员建单，付款也就不会记到他身上；顾客回到充值页，看到的是现在的会员，重新确认。
  - **解绑、换绑之后**：没绑定的回「请先绑定会员」；之前那条绑定下的单当作没有（换绑回同一位会员也一样，付款人还是那个微信、绑定换了一条）。同一个编号重提回「编号已经用过，请重新选择」，确认作废回「已作废」。
  - **员工解绑之后**：门店系统马上请微信关掉那条绑定还没付的单。关不上的（当时微信支付连不上）每分钟的补查接着关；还没关上之前，同一位会员下新单会提示「换绑之前下的那张充值单还在关闭，请过一分钟再试」。
  - **已经付了的**：照常由验签过的到账通知或补查，按原单入账到原来的会员，钱不会因为解绑丢，也只入账一次。关单时微信回「已支付」的，当场查单入账。

### 2.1 充值单的状态

| 状态 | 意思 | 之后能变成 |
| --- | --- | --- |
| 待支付 | 建好单、等顾客付，15 分钟到期 | 已入账、已关闭、已付款待处理 |
| 已入账 | 微信支付核实已付，钱包已入账（与充值单记「已到账」同一个事务） | 不再变 |
| 已关闭 | 没付：顾客取消、到期、微信那边关了或下单失败 | 关单前一刻付了的（极少见）：已入账、已付款待处理 |
| 已付款待处理 | 钱付了、门店系统没能自动入账，分两类（见下面） | 第一类：店主在后台「重新入账」或「按金额入账（不发套餐券）」→ 已入账，或「已另行处理」→ 已处理；第二类：**只能**「已另行处理」→ 已处理。都要写原因 |
| 已处理 | 店主写了怎么处理的 | 不再变 |

「已付款待处理」的两类（MP24；门店系统按记下的原因区分，后台只给能用的处理，服务端另外核对、拒绝不允许的）：

- **第一类：入账被规则拒了**：到账时不够首充 / 续充最低、超过单笔上限、套餐停用或改价。钱、付款人、单子都对得上，只是到账那一刻的规则不让入。店主可以把规则调回来后「重新入账」，或「按金额入账」（不按套餐、不发套餐券，赠金照档算）。
- **第二类：到账与单子对不上**：通知或查单里的金额、付款的微信、AppID、商户号和单子不一样；微信那边已转入退款；同一个微信交易单号已经入过别的账。这一类**不能入账**（入了可能记到错的会员、记错金额），只能核对后「已另行处理」，例如在商户平台原路退回。

已入账的单子另外标出给店主看的情况（入账照常）：到账时会员已停用、记到了合并进去的会员、关单之后才付的、到账时的赠金与预估不一样。

单号、会员、微信、套餐、金额、预估建单后都不能改；状态只能照上表变（数据库触发器兜底）。单子的每一次变化、每一条验过签的到账通知、每一次查单的结论都记在只追加的记录里。

### 2.2 锁与事务

- **建单、确认作废**：先取这个微信的咨询锁（`mp_recharge:<openid>`），再查作废登记、查同一个编号的单子、写单子；不锁会员、不碰钱包。一位会员同时只有一张待支付的，靠唯一索引兜底。
  - 建单在查完作废登记之后，再取这个微信绑定状态那把锁（`mp_bind:<openid>`）的**共享**模式，之后才读有效绑定。绑定、解绑拿的是排他的。
  - 所以读到的绑定到写单、提交之前不会被解绑；解绑提交以后再扫这条绑定没付的单去关，不会漏掉同时建的那一张。
- **解绑之后关单**：在解绑的事务提交之后、事务外请微信关单（与取消同一条路），不在解绑的事务里调微信。
- **继续支付拿到新的 prepay_id 之后**：只有单子还是待支付、这条绑定也还有效，才记下来、给支付参数；不然请微信关掉刚下的这一单。记下 prepay_id 也在绑定锁的共享模式里。
- **继续支付、模拟支付签参数（或模拟付款）**：已经有 prepay_id 的，在这个微信绑定锁的共享模式里核对现在这条绑定、签参数，不调微信（小程序线测试 #52 的补充）。
  - 所以与解绑交错时，要么先签（解绑等它提交，之后请微信关单），要么解绑先提交、这里回「请先绑定会员」。解绑提交之后不会再签出支付参数。
  - 解绑时关单没成功的（微信连不上），之前已经签出去的参数在微信那边还能付：付了照样按原单入账到原来的会员，补查接着关没付的。
- **入账**（到账通知、查单补单、店主重新入账）：会员一行 → 充值单一行 → 主线的 `rechargeOnline`，同一个事务（它里面再锁同一位会员不会再等）。入账被拒时这个事务整个回滚，另开一个事务只锁充值单一行、记「已付款待处理」。
- **关单、取消**：只锁充值单一行。
- **调微信支付**（下单、查单、关单）都在事务外：不拿着锁等网络；回来以后再锁单子、按当时的状态处理。

## 3. 记账规则：与前台同一条充值入账

| 项 | 做法 |
| --- | --- |
| 走哪本账 | 钱包的充值（`recharges`、`ledger_entries`），与前台充值同一条入账；不另建余额（AGENTS.md：会员钱包是唯一的储值账本） |
| 赠金、充值赠券、升档、首充与续充最低、首充礼、升级礼 | 都按会员体系 v2，用前台同一套算法，赠金按档自动算（线上不能自定义赠金） |
| 预估与到账 | 下单页的赠金、档阶是预估：**按到账那一刻的规则入账**，页面写明「以到账时为准」；充值单上记下预估，入账后与实际的赠金不一样的标出来（MP19） |
| 入账被拒 | 到账时不够首充 / 续充最低、超过单笔上限、套餐停用或改了价：钱已经付了，不入账，记「已付款待处理」（第 2.1 节）。店主可以把规则调回来后「重新入账」、「按金额入账（不发套餐券）」，或在商户平台原路退回后记「已另行处理」 |
| 线上能充什么 | 两种（MP18，店主 11-04 定）：① 店主在后台「微信小程序」里勾选的充值套餐（固定金额，套餐上挂的券照发）；② 自定义金额的框（后台开关，默认开）：按整元填，最少是 1 元与首充 / 续充最低里大的那个，最多是线上单笔上限，不挂套餐、不发套餐券，赠金照样按档自动算——与前台不选套餐、直接填金额一样 |
| 限额 | 单笔不超过前台的单笔上限，另设线上单笔上限（默认 1 万元）与每人每天最多 3 笔；超过的不让下单——线上没有店主当场授权（MP20）。另以微信支付自己的限额为准 |
| 冻结、合并的会员 | 不能下单；下单之后被冻结的，到账照样入账（钱已经付了），标出来给店主看；下单之后被合并的，记到合并进去的那位（主线的入口自己找），也标出来 |
| 经办人 | 系统账号「小程序」（`system.mp`，主线第一次线上入账时建，不能登录） |
| 收款方式 | 微信；付款单号记微信支付的交易单号 |
| 班次、日结、交班表 | 不进任何收银员的班次、不算哪个钱箱的钱；日结与看板的充值实收下单列「其中线上（小程序）」，交班表不算它（主线 v0.7.26） |
| 退款 | 主线 v0.7.26 做了储值退回（MP21）：线上那一笔按原收款方式（微信）退，退款页标「小程序」。调微信支付退款接口的原路退回是 2d；接上之前在商户平台手动退，在退款单上登记退款单号。小程序里不能自己退 |
| 发票 | 不做 |
| 充值当日的储值消费比例（主线 8.0.4，HY01–HY03；RQ-014） | 线上充值也算「当天充值」：主线按充值与余额流水的营业日算，线上充值经 `rechargeOnline` 入账，自然算在里面。**按入账那个营业日算**：付款在营业日切换（早上 6 点）之前、到账通知 6 点以后才到的，算到账那天（余额那天才多出来）；付款那天不算（充值单上照记付款时刻与下单的营业日）。同一笔的通知重复、同时到只入账一次、只算一次；同一天几笔（线上、前台）加在一起，「充值前的余额」按当天第一笔之前。小程序充值本身不是储值消费，比例不影响小程序（小程序不扣储值）。用例 `tests/mp-recharge-quota.test.ts`。充值页要不要告诉顾客这条规则待店主（MP39，默认不写） |

## 4. 小程序线要做的

| 部分 | 内容 |
| --- | --- |
| 迁移 `046`（第二期，ROADMAP 第 7 节登记） | 只建自己的表，只用外键引用会员、绑定记录、充值套餐、充值单与员工：线上充值单 `mp_recharge_orders`（单号、操作编号、微信、绑定记录、会员、套餐、金额、预估、状态、微信交易单号、入账的充值单、关单、待处理的原因、店主怎么处理的）；单子的记录 `mp_recharge_events`（只追加：建单、微信下单、到账通知、查单、关单、入账、待处理、店主处理）；`mp_op_fences` 加一类 `mp_recharge`（建单的确认作废） |
| yuzu 小程序端口 | 可充的项（勾选的套餐与自定义金额，各自按这位会员现在算的预估；有待支付的单一并给出）、自定义金额的预估、建单（建单 + 向微信下单 + 支付参数）、确认作废、查单（待支付的顺带去微信查，同一张单 3 秒一次）、继续支付（重新给支付参数）、取消、到账通知（网关原样转来）；每分钟一次：待支付超过 2 分钟的去微信查，过了 15 分钟的去微信关 |
| 微信支付的配置 | 门店 yuzu 的 `.env`（MP17）：`WXPAY_APPID`、`WXPAY_MCHID`、`WXPAY_SERIAL_NO`、`WXPAY_PRIVATE_KEY_FILE`、`WXPAY_APIV3_KEY`、`WXPAY_PUBLIC_KEY_ID`、`WXPAY_PUBLIC_KEY_FILE`、`WXPAY_NOTIFY_URL`（网关的 `/v1/pay/notify`）。没配齐的，线上充值不开，后台写「微信支付没有配好」 |
| 网关 | `/v1/recharge…` 带会话转发；`/v1/pay/notify` 不要会话、不解析内容，连同微信的四个签名头原样转给 yuzu，按 yuzu 的结果回微信（成功回 204，其余回失败让微信重发）；限流 |
| 后台「微信小程序」 | 线上充值：开关（默认关）、线上可充的套餐、自定义金额的开关（默认开）、线上单笔上限与每人每天笔数（带版本号保存）、微信支付配没配好；线上充值单：每张单的状态与标出来的情况，「已付款待处理」的三种处理（第 2.1 节，要店主或店总）。2b 加对账，2c 加「领券中心」 |
| 小程序页面 | 「我的」→「充值」：可充的项、自定义金额、待支付的单；确认 → 微信支付 → 结果页（自己再查，最多 1 分钟）；「结果待确认」 |
| 模拟微信支付 | 只在 development、test 实例（`MP_PAY_MOCK=true`，其他环境启动时报错，没有绕过开关）：yuzu 里有一个模拟的微信支付，下单、查单、关单照真的签名；小程序在模拟模式下点「模拟支付」，yuzu 造一条照真的签名、加密的到账通知，走同一条验签、解密、入账的路 |
| 隐私保护指引 | `MP_PRIVACY.md` 加「订单信息」一项（充值单）；写明支付由微信支付处理，门店不接触银行卡信息 |

## 5. 要主线加的（主线 v0.7.26 已做，#48 的 `7c61d01`、`c938e79`）

1. **钱包的「线上收款」入口**：`rechargeOnline(tx, deps, { memberId, paidAmount, planId, paymentRef, orderNo, at? })`（`src/server/modules/wallet-online.ts`）。在小程序线自己的事务里调用，与充值单记「已到账」一起提交：
   - 经办人是系统账号「小程序」、渠道 `mp`、不记班次；收款方式微信，`paymentRef` 记微信支付的交易单号，同一个交易单号只入账一次（再调用返回第一次的充值单，`replayed`），金额或会员对不上拒绝（`ONLINE_REF_CONFLICT`）；
   - 赠金按到账那一刻的档自动算；首充 / 续充最低（`RECHARGE_BELOW_MIN`）、单笔上限（`RECHARGE_OVER_LIMIT`）、套餐停用或改价（`PLAN_UNAVAILABLE`、`PLAN_CHANGED`）直接拒绝；套餐上的券照发；
   - 到账时会员已停用照样入账（`frozen`）；来源会员已合并的记到合并进去的那位（`mergedFrom`）。
2. **只读预估**：`previewOnlineRecharge(db, deps, memberId, paidAmount)`：赠金、档阶、首充还是续充、单笔最低与上限、是否停用、合并到了谁。
3. **日结、看板**：充值实收下单列「其中线上（小程序）」；交班表不算它。
4. **储值退回**：线上那一笔按原收款方式退，退款页标「小程序」；小程序线的原路退回（2d）接在退储值单上。

小程序线这边按第 2.2 节的锁：会员一行 → 充值单一行 → `rechargeOnline`；入账的时刻用门店系统入账的那一刻（不传 `at`），微信的付款时间另记在充值单上。

## 8. 2b 对账（设计）

微信支付每天出前一天的交易账单（按北京时间的自然日；上午 10 点以后能下载）。门店系统每天 10 点半以后自动下前一天的账单，逐笔和线上充值单核对，结论给店主看。

对账自己不动钱、不改单子，只看、只记。唯一会引起入账的，是「微信有、门店没记」的那一笔：对账**调用 2a 每分钟补查的同一条路**。这条路去微信按商户单号查单（应答验签），已付的走与到账通知相同的入账：
- 先与单子核对，再在同一个事务里按会员一行 → 充值单一行 → 主线 `rechargeOnline` 入账；
- 按微信交易单号去重，记录与审计都照 2a；
- 被拒或对不上的照样记「已付款待处理」。

所以对账跑几次、和到账通知或每分钟补查同时到，都只入账一次。经办人照 2a 记系统账号「小程序」。对账结论里记的是查单之后的结果。

| 情况 | 意思 | 门店系统怎么办 |
| --- | --- | --- |
| 都对上 | 微信那天的每一笔成功交易，门店系统都有一张单子：按同一个微信交易单号入了账，或记成已付款待处理、已另行处理，金额也一样；门店系统那天入账的每一笔，微信账单里也都有 | 记「对上了」 |
| 微信有、门店没记 | 到账通知没送到，补查也还没查到（例如门店断网很久） | 调用 2a 的补查（同上）；补上了就不算没对上，补不上的列出来、标红 |
| 门店记了、微信没有 | 不该出现（门店系统只认验过签的到账）。付款在 23:59、账单算在第二天的，先看前后一天的账单 | 标红，请店主核对 |
| 金额对不上 | 同一笔交易，两边的金额不一样 | 标红，请店主核对 |
| 退款 | 账单里的退款：在商户平台手动退的；以后 2d 自动退的 | 列出来，与退储值单核对（2d） |

- **记在哪**：对账结果存在门店系统，每天一条，重新核对就再追加一条，不改旧的；表加在迁移 `046` 里（046 还没发布到任何环境，可以改）。
- **在哪看**：后台「微信小程序 → 线上充值 → 对账」看最近 30 天；有标红的，这一页最上面提醒，可以按天「重新核对」。
- **账单接口**：
  - 先申请交易账单，拿到下载地址和摘要；
  - 再下载（请求要商户签名，应答不签名），按摘要（SHA1）核对文件没被改；
  - 每个字段前有一个 `` ` `` 号；金额是元、两位小数，按字符串转成分，不用浮点数。
- **没有交易的日子**：微信回「账单不存在」，按 0 笔算。
- **模拟微信支付**也出账单：演示库上能看到对账，测试里用它。
- **之后**：对账结果要不要进每日对账包、`check`（主线的），等 2b 做完再和主线商量。

## 9. 2d 原路退回（设计与实现；主线 v0.7.27 配合）

主线 v0.7.26 的储值退回（#48，`MEMBERSHIP_FINISH.md` 第 1 节）按「最近的充值先退」分到每一笔充值。线上充值的那一行，方式是微信。现在的做法是：员工先在商户平台原路退回，再在退储值单上登记退款单号。退储值单只追加、提交以后改不了，也不能作废（M74）。2d 让门店系统自己调微信支付的退款接口原路退回，店里不用再去商户平台。

**为什么要主线配合**：主线现在要求微信退的每一行都先填退款单号。门店系统如果自己判断「看到线上那一行就自动退」，员工又在商户平台手动退了一次，**顾客会收到两次退款**。所以每一行由退的时候明确选「怎么退」，门店系统只退选了自动退的行。

**和主线约好的**（主线 #51，v0.7.27；接口写在主线 `MEMBERSHIP_FINISH.md` 第 6 节）：

| 谁 | 做什么 |
| --- | --- |
| 主线 | 退储值的每一行加「怎么退」：`manual`（照旧：员工在商户平台手动退、填退款单号）或 `mp_auto`（门店系统原路退回）。`mp_auto` 只能用在来源是线上充值、方式微信、退款单号空着的行。开关在小程序线：`registerOnlineRefundRoute({ available })`；没注册或 `available()` 为假时页面不给选、接口拒绝（`ONLINE_REFUND_UNAVAILABLE`），与 v0.7.26 一样要填退款单号。只读的取数 `listOnlineRefundLines(db, { afterId, limit })` 按行号升序给 `mp_auto` 的行（行号、退储值单、会员、充值单与它的微信支付交易单号、金额、时间） |
| 小程序线 | 启动时注册：真的微信支付配好、店主在后台打开「原路退回」时 `available()` 才为真。每分钟按行号往后取 `mp_auto` 的行，按行建原路退回单（只追加的记录，按行号唯一；商户退款单号建单时定下、存在单子上，重试用同一个，同一行只退一次），调微信支付的退款接口。结果按退款通知（网关同一个 `/v1/pay/notify`）或查退款更新：成功、处理中、异常、关闭。异常、关闭、微信拒绝（例如商户号余额不够、超过一年）的列给店主，店主在商户平台处理后登记 |
| 对账 | 2b 的账单退款行与原路退回单核对 |

- **只认主线已经提交的退储值单**：那张单是店主或店总当场授权过的、不能作废，门店系统不另外判断该不该退、退多少，只管把钱退到。
- **不锁主线的行**：只读；原路退回单按行号唯一，重复取到也只建一张、只退一次。

**实现（小程序线，接主线 #51 的接口；迁移 `048` 与 2c 一起）**：

| 部分 | 做法 |
| --- | --- |
| 开关 | 后台「线上充值」的设置里加「原路退回」（默认开）。门店系统的微信支付配好、开着时，`available()` 回真，主线的退储值才给选「门店系统原路退回」。关掉只影响以后的退储值，已经交给门店系统的照样退完 |
| 原路退回单 `mp_refund_orders` | 每分钟按行号往后取 `mp_auto` 的行，按行号唯一建一张。商户退款单号（`MPRF` + 日期 + 10 位）建单时定下，存在单子上。原订单金额从原来那笔线上充值单取；找不到原单的记「没能退」（`ORDER_NOT_FOUND`）。状态只能照下面变，触发器兜底；只追加的记录在 `mp_refund_events` |
| 申请退款 | 事务外调微信支付的退款接口，原因写「会员储值退回」。连不上、微信出错、太频繁的隔 2^n 分钟再试（最长 1 小时）；商户号余额不够（`NOT_ENOUGH`）隔 30 分钟再试；都用同一个单号，所以不会退两次。微信明确拒绝的（例如超过可退金额，多半是店里已在商户平台退过；顾客的微信注销了）记「没能退」 |
| 结果 | 退款通知（网关同一个 `/v1/pay/notify`，按事件类型分）或每 5 分钟查一次退款。成功记已退到（退到哪、微信退款单号、时间），异常、关闭的记下来给店主。单号或金额对不上的通知只记一条、不改状态。找不到原路退回单的退款通知（例如商户平台上手动退的）记一条，同一笔只记一次，回收到 |
| 同一张单一张一张办 | 申请、查退款、店主的重试与另行处理要跨着调微信，所以每一张原路退回单有一把会话级咨询锁（单独借一条连接拿着，不开事务、不锁别的表）。锁里先重读这一张，按读到的单号办，之后每次改写都核对单号。每分钟的扫描拿不到就跳过这一张，下一分钟再来；店主的操作最多等 15 秒。这样不会出现扫描拿着旧单号去申请、而店主已经换了新单号，一行退两次（独立审查的 P1） |
| 店主处理（`mp.recharge`） | 「原路退回」一栏列出没退成的。待申请的可以「马上再试」（同一个单号）。关闭、没能退的「重试」：先查旧单号，微信那边已经退到或在处理的照实记，确认没退到才换一个新单号重新申请。异常、关闭、没能退的可以「已另行处理」，要写怎么处理的；没能退的、向微信申请过的先按现在的单号查一次，微信那边在退或退到了的不让另行处理。重试、另行处理都带看到的单号，单号变了回 409（`REFUND_CHANGED`），请店主刷新再看；所以结果待确认时按原内容重新提交也不会做两次 |
| 取行 | 不记「已经取到第几行」：行号小的可能比行号大的晚提交，所以每次从「交给门店系统、还没建单的里行号最小的」往后取，按行号唯一建单 |

状态：`new` 待申请 →（`processing` 处理中 →）`success` 已退到；也可能 → `abnormal` 退款异常（→ `success` 或 `closed` 或 `handled`）、`closed` 退款关闭、`failed` 没能退（这两种 → 重试回 `new`，或 → `handled` 已另行处理）。`failed` 的，微信那边对现在这个单号说在退、退到了，以微信的为准（→ `processing`、`success` 等）。

**2b 对账一起核对退款行**：账单里商户退款单号是 `MPRF` 开头的退款行（门店系统自己申请的）与原路退回单逐笔核对。
- 微信说退到了、门店还没记的，先按现在的单号查一次，补上了就不算没对上。
- 标出来的四种：门店系统里没有这张原路退回单；微信已退、门店还没记已退到（查退款也没补上）；门店记了已退到、微信那天的账单里没有（零点前后的另外说明）；退款金额对不上。
- 在商户平台手动退的（单号不是 `MPRF` 开头）只列在退款里，不核对。
