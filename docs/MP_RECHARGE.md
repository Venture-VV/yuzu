# 小程序第二期：线上充值（设计稿；小程序线，2026-11-04）

店主定的三期（MP2）里，第二期是资金：线上充值（微信支付），以后加线上领券。这一版**只写设计，不写代码**：流程、密钥放在哪、记账规则、要主线加的入口、怎么测、分几步做。做法汇总在 `PENDING_DECISIONS.md`「微信小程序」MP17–MP22；店主 2026-11-04 都已定：MP17、MP19、MP20 按默认，MP18 加自定义金额的框（后台可开关），MP21 储值退回交主线开发，MP22 领券限制做成多个选项、默认每个模板每人限领 1 张。

第二期动的是真钱和储值，按资金候选版本走：CI 全绿后店主合并，独立验收在合并后补做（AGENTS.md「快速开发周期」）。对顾客开放要等 yuzu 正式切换（ROADMAP 第 3 节 M5），在那之前只在测试服的演示库上联调。

## 1. 顾客怎么用

1. 「我的」→「充值」：列出店主在后台勾选的充值金额（第 3 节）；后台开着「自定义金额」时，下面另有一个填金额的框（整元）。每一项（或填好的金额）写实付、按充完以后所在档预估的赠金、充完是哪一档、套餐上挂的券；首充、续充有最低额时写明。冻结的会员不能充（MP6）。
2. 点一项 → 确认 → 微信支付。
3. 付完回到小程序：
   - 门店系统已经入账：「充值成功」，写本金、赠金、充完的档阶；
   - 还没入账（到账通知在路上）：「已支付，门店系统入账中」，页面自己再查，最多等 1 分钟，之后可以离开，入账后在「余额与流水」里能看到；
   - 没有付：回到充值页，这张单 15 分钟后自动关掉。
4. 入账后的余额、流水、券、档阶都和前台充值一样显示（同一本账）。

同一位会员同时只能有一张没完成的充值单：还有没付完的，先让顾客继续付或者取消，免得付两次。

## 2. 流程：下单在门店系统，支付密钥只在门店（MP17）

```
小程序 ──① 下单（选的哪一项）──▶ 网关 ──▶ yuzu：建线上充值单（会员、金额、套餐、预估赠金），
                                              向微信支付下单（JSAPI，带 openid、15 分钟到期），签好支付参数
小程序 ◀─② 支付参数────────────── 网关 ◀── yuzu
小程序 ──③ wx.requestPayment ──▶ 微信支付
微信支付 ──④ 到账通知 ──▶ 网关 /v1/pay/notify（不看内容，原样转）──▶ yuzu：验签、解密、核对单号与金额
                                              → 同一个事务里：钱包充值入账 + 充值单记「已到账」
小程序 ──⑤ 查这张单 ──▶ 网关 ──▶ yuzu（单子的状态）
yuzu ──⑥ 补单：到账通知没送到时自己去微信支付查单（门店断网、网关出错之后）
```

- **为什么放门店**：网关在公网上。支付凭据放在网关，网关被攻破的人就能伪造「已到账」（凭空加储值），也能调退款接口（钱退走了、储值还在）。放在 yuzu，网关只转发：到账通知由 yuzu 自己验微信的签名、自己解密，要核实时 yuzu 自己去查单。门店的 Mac mini 本来就能出外网（备份上传就要），只多连微信支付的接口；进门店的方向照旧不开。
- **只认门店定的金额**：充值单的金额、套餐在 yuzu 建单时定下，小程序传来的只是「选的哪一项」。到账通知里的金额、商户单号、AppID、商户号、付款人 openid 都要和这张单对上，任何一样对不上都不入账，记一条异常给店主看。
- **只在入账成功之后回微信「收到」**：验签失败、对不上、门店出错都回失败。微信会在 24 小时里按它的节奏重发；门店系统按商户单号去重，重发多少次只入账一次。
- **门店断外网**：网关转不进门店，回微信失败，微信接着重发。门店连上之后，yuzu 把「支付中」超过 5 分钟的单子逐张去微信查（补单），已付的照样入账。顾客那边在这段时间里看到「已支付，门店系统入账中」。
- **15 分钟关单**：下单时就告诉微信 15 分钟后过期；到期没付的单子 yuzu 去微信关掉、记「已关闭」。关单之后才到的付款（极少见）照样入账，记一条异常给店主看（MP19）。
- **结果待确认**：建单、拉起支付、查结果都可能遇到断网、超时。小程序把单号存在手机上，以门店系统里这张单的状态为准；单子没有结论（还在「支付中」）时不让再下新单，和第一期绑定的「结果待确认」同一个做法。

## 3. 记账规则：与前台同一条充值入账

| 项 | 做法 |
| --- | --- |
| 走哪本账 | 钱包的充值（`recharges`、`ledger_entries`），与前台充值同一条入账；不另建余额（AGENTS.md：会员钱包是唯一的储值账本） |
| 赠金、充值赠券、升档、首充与续充最低、首充礼、升级礼 | 都按会员体系 v2，用前台同一套算法，赠金按档自动算（线上不能自定义赠金） |
| 预估与到账 | 下单页的赠金、档阶是预估：**按到账那一刻的规则入账**，页面写明「以到账时为准」；到账时和预估不一样的，在充值单上记下两边的数（MP19） |
| 线上能充什么 | 两种（MP18，店主 11-04 定）：① 店主在后台「微信小程序」里勾选的充值套餐（固定金额，套餐上挂的券照发）；② 自定义金额的框（后台开关，默认开）：按整元填，最少是 1 元与首充 / 续充最低里大的那个，最多是线上单笔上限，不挂套餐、不发套餐券，赠金照样按档自动算——与前台不选套餐、直接填金额一样 |
| 限额 | 单笔不超过前台的单笔上限，另设线上单笔上限（默认 1 万元）与每人每天最多 3 笔；超过的不让下单——线上没有店主当场授权（MP20）。另以微信支付自己的限额为准 |
| 冻结的会员 | 不能下单；下单之后被冻结的，到账照样入账（钱已经付了），记异常给店主看 |
| 经办人 | 系统账号「小程序」（不能登录） |
| 收款方式 | 微信；付款单号记微信支付的交易单号 |
| 班次、日结、交班表 | 不进任何收银员的班次、不算哪个钱箱的钱；日结、看板、交班表里单独一行「线上（小程序）」 |
| 退款 | 系统里现在没有储值退回，前台充值也不能退。店主 2026-11-04 让主线开发储值退回（MP21）；做好之前线上充值不在小程序里退，做好之后，线上充值的原路退回接在上面：门店系统扣回储值、调微信支付的退款接口原路退回，记谁批的 |
| 发票 | 不做 |

## 5. 要主线加的（按 MP8：小程序线写需求，由主线做；或主线同意后小程序线开一个只改这一处的小 PR）

1. **钱包的「线上收款」充值入口**（`wallet.ts`）：现在的充值要经办人开着班次（`lockPaymentShift`），经办人是员工。线上充值要：
   - 不要收银员班次，经办人是系统账号「小程序」；渠道记「小程序」，日结、交班、看板能分开显示；
   - 收款方式 `wechat`，付款单号写微信交易单号；
   - 赠金按档自动算（不能自定义）；首充与续充最低、单笔上限照旧，超上限直接拒绝；
   - 让小程序线在同一个事务里调用：与充值单记「已到账」一起提交，按充值单的操作编号去重；锁的顺序照钱包现在的（会员一行之后再锁小程序线自己的充值单一行）。
2. **日结、交班、看板**：「线上（小程序）」单独一行；交班表不把它算进任何钱箱。
3. **系统账号「小程序」**：不能登录，不出现在排班与交班里。
4. **储值退回**（店主 2026-11-04 定，交主线开发；当天已转告主线）：会员退储值时扣回本金与赠金、按原收款方式退、记谁批的。小程序线的线上充值原路退回接在它上面。

主线现在没有开着的 PR；等主线开了下一个 PR，小程序线在那边留言写清这几条，并核对迁移号 `046`。

## 6. 测试与验收

- **集成测试**（CI，小程序线写、测试会话复核）：用本机生成的测试密钥模拟微信支付（下单、查单、关单、到账通知的签名与加密）。覆盖：
  - 验签失败、解密失败、金额或单号对不上：都不入账；
  - 同一笔的通知重复到、并发到：只入账一次；
  - 通知先到、查单先到，两种顺序；门店断网后补单；
  - 关单之后才到的付款；
  - 下单与到账之间改了会员规则；
  - 冻结的会员、超限额、一人两张未完成的单子。
- **小程序**：充值页与结果页的单元测试；开发者工具冒烟加「模拟充值」一步（本地 AI）。
- **真钱**：在演示库上用 0.01 元真实付款（`MINIPROGRAM.md` 第 6 节），测完在商户平台原路退回（系统里不做退款）。不往演练库、正式库写测试数据。
- **对账**：微信支付的交易账单与系统里的线上充值逐笔核对（2b）。
