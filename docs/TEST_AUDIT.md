# 用例体检（2026-11-18，工程治理三期）

对着 `main` 的 v8.1.10 做的一次体检：用例分了哪几层、哪些其实没在跑、哪些写法不稳。结论是**底子是好的**（没有只靠 mock 自己证明自己的用例，没有被悄悄跳过的），问题集中在「有 9 条浏览器用例 CI 里从没执行过」和「CI 变慢了」两处。这份是当时的记录，不随代码更新；改法里归测试会话与 Codex 的部分（CI 的测试步骤）只写建议。

## 1. 分层

| 层 | 文件 | 用例 | 要什么 | 多久 |
| --- | --- | --- | --- | --- |
| 秒级（`npm run test:unit`，三期新分出来的） | 36 | 310 | 什么都不要 | 8 秒 |
| 集成测试（`npm test`） | 233 | 2,130 | PostgreSQL 16 的独立测试库（按文件并行，每个进程一个库） | 本机 3 分钟，CI 4 分半 |
| 浏览器验收（`npm run e2e`） | 99 + 员工食堂 3 | 门店电脑 342 条，另四个尺寸只跑视口与只读的 | 构建好的应用 + 合成演示库 | CI 三组 17 / 13 / 10 分钟 |

- 集成测试全部打真实数据库、经 `buildApp` 起整个应用再发请求：没有 mock 掉数据库或钱包的用例。对外接口（支付、平台验券、开票、短信、AI）用的是仓库里自带的模拟实现，用例里写明。
- 秒级这一档里是共用的计算与规则（扣款构成、档阶、营业日、会员规则）、页面的请求层与编码识别、版面格式、各个检查脚本。

## 2. 有没有被悄悄跳过的

| 查了什么 | 结果 |
| --- | --- |
| 用例里留着 `.only` | 0（三期起 `check:gov` 硬拦） |
| 无条件的 `.skip` / `.todo` / `.fixme` | 0 |
| 集成测试里按条件跳过 | 1 处：`compose-config` 在本机没有 Docker Compose 时跳过，CI 里必跑 |
| 浏览器用例里的 `test.skip(条件)` | 148 处，见下 |

148 处条件跳过的构成：

| 条件 | 处数 | 算不算问题 |
| --- | --- | --- |
| 按屏幕尺寸、按是不是「门店电脑」这一组 | 132 | 不算：会改数据的流程只在门店电脑跑一遍，别的尺寸只看版面，是 0.7.18 定的做法；CI 的汇总按总数核对 |
| 应用没带 `INTEGRATIONS_MOCK=true` 启动 | 8 | **算**：见第 3 节 |
| 看演示库里有没有某种数据 | 8 | 要留意：见下 |

「看数据」的 8 处（数据不凑巧时这条用例等于没跑，结果里记的是跳过）：

| 用例 | 跳过的条件 |
| --- | --- |
| `backfill.spec.ts` 两条 | 演示库里没有在店会员 / 在店客人 |
| `frontdesk-recovery.spec.ts` 一条 | 演示库里没有合适的多候选尾号 |
| `print.spec.ts` 一条 | 演示单据落在前一个营业日（演示数据带 `--previous-day` 灌的时候） |
| `customer.spec.ts` 两条 | 演示库里没有会员 / 第一位会员已停用 |
| `legacy.spec.ts` 两条 | 演示库没有执行 `seed-legacy-demo` |

CI 灌的是固定的五块演示数据（不带 `--previous-day`），这 8 条平时都在跑。它们的风险在别处：哪天演示数据改了、这些条件不再成立，用例会变成「跳过」而不是「失败」，汇总只核对总数、看不出来。

## 4. CI 用时

`main` 上 v8.1.9 那一次（[运行记录 44321870405](https://github.com/Venture-VV/yuzu/actions/runs/44321870405)）整次 19 分钟，0.7.18 提速后是 7 分钟：

| job | 用时 | 其中 |
| --- | --- | --- |
| 浏览器验收 · 门店电脑 a–l | 18 分 36 秒 | Playwright 16 分 53 秒（47 个文件） |
| 浏览器验收 · 门店电脑 m–z | 14 分 45 秒 | Playwright 13 分 14 秒（52 个文件） |
| 浏览器验收 · 平板、小屏电脑、手机 | 12 分 | Playwright 10 分 17 秒 |
| 类型检查 · 集成测试 · 构建 | 7 分 36 秒 | 类型检查 52 秒 + 代码整洁 52 秒（同一次类型检查跑了两遍）+ 排版 19 秒 + 集成测试 4 分 30 秒 + 构建 25 秒 |
| 演示数据 | 2 分 47 秒到 11 分 | 有一次装浏览器依赖花了 9 分钟（别的 job 是 18 秒），偶发 |
| 汇总 | 20 秒 | 等最慢的那一组 |

整次用时 = 最慢的那组浏览器验收 + 汇总。一个月里用例从 385 项涨到 1,100 多项，分组还是当时的三组。

## 5. 固定等待

`waitForTimeout(...)` 一共 21 处（`emenu` 4、员工食堂 3、`contracts` 2、`budget-invoices` 2、巡场 2，其余各 1）。数量不多，但每一处都是「机器慢一点就可能不够」的地方；改用例的时候顺手换成等某个状态（`expect(...).toBeVisible()`、`waitForResponse`）。

- 分出秒级一档（`npm run test:unit`）与快测（`npm run test:quick`），见 `TESTING.md` 第 4 节。

## 7. 给测试会话与 Codex 的建议（CI 的测试步骤归你们，这里只写依据）

1. **让那 8 条模拟接口的用例在 CI 里跑**：浏览器验收的「启动应用」带上 `INTEGRATIONS_MOCK: 'true'`（CI 的应用是 `APP_ENV=development`，允许模拟）。带上以后 `v8022.spec.ts` 的 AI 那条会走「问一次」而不是「还没配置」的分支，两条分支用例里都写了。用例总数不变，跳过数少 8。
2. **把 `member-refund-online.spec.ts` 接进 CI**：单开一个小 job，或者在「门店电脑 m–z」那组的应用上加 `MP_PORT`、`MP_GATEWAY_KEY`、`MP_PAY_MOCK=true` 并给 Playwright 设 `E2E_MP_PORT`、`E2E_MP_GATEWAY_KEY`（`TESTING.md` 第 4 节有命令）。
3. **浏览器验收重新分组**：现在按首字母分两段，a–l 比 m–z 慢 3 分半，整次 CI 卡在 a–l 上。把门店电脑分成四组（例如 `[a-d]`、`[e-l]`、`[m-r]`、`[s-z]`），汇总 job 的组数从 3 改成 5；各组交回的 JSON 结果里有每个文件的用时，按它调分界。照现在的用时估，整次能回到 11–12 分钟。
4. **「看数据」的 8 处跳过在 CI 里改成断言**：CI 的演示数据是固定的，这些条件在 CI 里应当总是成立。用例里把 `test.skip(没有数据)` 换成「在 CI（`process.env.CI`）里没有数据就失败、本机才跳过」，演示数据哪天变了能第一时间看到。
