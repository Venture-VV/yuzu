## 2. 目标与原则

- **越快越好地用真实业务测试**：按里程碑推进，不按日历；一步的条件满足了就往下走，能并行的并行。
- **首个正式版本 R1** = 前台收银 + 会员储值 + 交班日结 + 打印 + 部署运维。餐饮单点、按摩 / SPA 用价目表项目挂到手牌（不用手动金额行，以后才能按项目补出部门营业额）；客房、押金、后厨、后勤库存先沿用现行流程。
- **先测试服，再影子运行，最后切换**：测试服上按真实业务演练；正式服先「影子运行」（新旧双录、旧流程仍是正式账、每晚对账），连续两个营业日零未解释差异再切换。
- **任何时候只有一个正式记账库**：系统没有离线队列，也没有双库同步，两处同时记账一定会变成两本账。

## 6. 环境与部署

| 环境 | 放在哪 | 数据 | 访问 |
| --- | --- | --- | --- |
| 测试服 · 演练库（主用） | 云服务器 A，独立 Compose 项目 | `APP_ENV=development`，新建独立数据库，不写演示数据；导入真实的 747 个柜号与汤崎价目表，核对票种票价；员工用测试账号 | 只经 Tailscale（安全组关闭全部公网入站，包括 22）；不得已用门店出口 IP 白名单时全程是 http 明文，只能用测试账号 |
| 测试服 · 演示库（可选） | 云服务器 A，另一个 Compose 项目 | `APP_ENV=development` + 四套演示数据（登录页显示演示账号密码） | 只经 Tailscale，绝不对公网开放 |
| 正式服 · 推荐：门店线下 | 门店 Mac mini（[部署手册](DEPLOY_MAC_MINI.md)），接 UPS | `APP_ENV=production`，全新数据卷 | 员工专用局域网（与顾客 Wi-Fi 隔离）；店主在店外经 Tailscale；路由器不做端口转发 |
| 正式服 · 备选：云服务器 B | 另一台云服务器，不与测试服共用 | 同上 | 全部前台终端装 Tailscale；或走公网 HTTPS（先做完加固清单并完成 ICP 备案）；门店必须有 4G / 5G 备份线路 |
| 应急冷备与恢复演练 | 云服务器 A 的独立 Compose 项目，或店主电脑 | 平时不运行；演练时从 OSS 取回备份，恢复、check、比对指纹后删库 | 仅店主与 Codex |
| 独立验收库 | Codex 所在的 Mac | 按提测 SHA 新建的演示库 / 测试库 | 仅 Codex；严禁指向门店库、测试服或正式服 |
| 门店现有试用实例（8080，trial） | 门店 Mac | 早期试用库 | 建议测试服上线后停用（店主决定）；数据不迁入正式服 |

- **为什么推荐正式服放门店**：系统不能离线，正式服在云端时门店外网一断，前台就不能接待和结账；放在门店，外网断了局域网照常收银，而且部署手册、OSS 加密备份与恢复脚本都已按 Mac mini 写好（还没在门店 Mac mini 上实测）。门店有稳定宽带 + 4G / 5G 备份线路、又不想维护门店硬件时，可以改放云服务器 B。
- **发布顺序**：GitHub 上通过 CI 的完整 SHA → 测试服 → 店主批准 → 正式服部署窗口（营业低峰；周末与切换日不更新）。窗口内：前台暂停改纸质单 → 备份并记指纹 → `./scripts/update.sh <完整 SHA>` → check 全 ✓、比对指纹 → 观察 30 分钟。回滚 = 换回上一版 + 恢复升级前备份。
- **备份**：正式服每小时 `pg_dump` → age 加密 → OSS 私有 Bucket，每份旁记数据指纹；每月取回一份做恢复演练，切换前后改为每周。RPO ≤ 1 小时，RTO 约 30–60 分钟。
- **公网访问加固清单**（正式服放云端又走公网时必须先做）：Caddy HTTPS；compose 透传 `COOKIE_SECURE=true`；Fastify 开 `trustProxy`；反向代理原样透传 Host（否则同源校验会让所有写操作 403）；按 IP 限流（现在按用户名在内存里计数，别人能反复把店主账号锁住）；安全响应头；中国内地服务器用域名 + 443 需先完成 ICP 备案（通常要两三周，要提前办）。
- **故障**：应用无响应 10 分钟没恢复，就改用预编号的纸质应急单。正式服整机故障 30 分钟修不好，由店主下令、确认原正式服已停止写入后，把最近一小时的备份恢复成临时正式库；原正式服修好后先保持停写，把临时库整库迁回并比对指纹，再切回。任何时刻只允许一个可写实例。外网中断时，正式服在门店则照常收银（扫码失败改收现金）；在云端则改用纸质单并切到 4G 线路，恢复后补录（按补录时间记账，备注纸质单号与原时间）。

- **候选版本**：当天的修复合进同一个候选 SHA 一次提测，验收报告逐条给结论。验收往返是主要瓶颈（G2 到第 3 轮才放行）。
- **版本号**：测试服 v0.3.x；R1 切换并对账通过后打 v1.0.0。部署一律用完整 SHA（没有 tag 时 `update.sh` 把短 SHA 写成版本号）。
- **用量**：同时编码的会话不超过 2–3 个，不开大规模并行；给验收往返与热修留出额度。
- **真实数据不离开店主设备**：会员余额、员工名单只在店主电脑与正式服上处理；云端会话只看脱敏的表头样例。
- **冲销类操作留痕**：反结账、降档或改免票、优惠 / 免单、代付统一走「当场授权 + 原因」，并进入每日异常清单；R1 不按 #3 放宽店员的冲销权限。

## 9. 切换后（M6）

按营业额与痛点逐个上线，每个都先在测试服验收、再进正式服；开发前店主先定规则。

1. **S6 技师**：钟房看板、上下钟、加钟退钟、提成（G6）。汤崎价目表 29 项里 27 项是技师服务。
2. **S5 餐饮**：点单、估清、KDS（G5）；不洗浴的外来就餐客独立结账；挂账来源按部门拆分。
3. **S7 客房**：房态、夜审、押金（G7）。押金是负债，不计收入。
4. **收银完善**：退款渠道登记、离店后更正收款、部分退款与明细转移；部门营业额；看板异常置顶与数字钻取。
5. **Batch 4**：岗位 × 权限矩阵（#3）；库存采购二期（#13–#25）；后勤真实期初（G4）。
6. **S8 候选**：次卡套票、零售扣库存、硬件与支付接口。先问清：顾客手里有没有旧次卡要核销，柜锁或手环是否依赖旧系统发牌。
