### 0.1 复测第 2 轮意见修复：交班时正在处理的收款

Codex 在 `6dd6574` 复测：开班期间发起、在取充值单号时等待的现金充值，交班先完成后才提交，充值单 `shift_id` 为空——既不在已交班次的快照里，也不属于之后的班次。原因：收款在取单号之后才对班次加锁，等锁期间交班已经完成。

**收款与交班的共同协议**（`src/server/modules/shifts.ts` `openShiftOf` / `lockPaymentShift`，不新增迁移）：

| 顺序 | 结果 |
| --- | --- |
| 收款先拿到班次（入账事务在锁业务行之前就对经办人的班次加共享锁） | 交班（排他锁）等这笔提交后再汇总，计入本班次；员工看到的应有现金已过期时交班 409 `SHIFT_CHANGED`，刷新后按新的应有现金交班 |
| 交班先拿到班次 | 之后拿到锁的收款，开始处理时就在这个班次上的：整笔拒绝 409 `SHIFT_CLOSED`（details 带 `shiftNo`），不入账、余额与流水不变、操作编号不占用；开新班后原样重提记到新班次，只入账一次 |
| 收款开始时没有开班 | 照常收款、不记班次（开班仍是可选的）；开始后才开了班的记到新开的班次 |
| 重复提交查回原单 | 返回原单，不受之后交班的影响 |

适用于充值、结账、反结账（反结账提醒记到反结账人的班次），以及升级时仍未交班的旧班次（`legacy_window`）。会员工作台的储值消费不是收款，不参与。

**建议复测**（独立演示库；持锁的脚本不能同步等交班返回——收款持有班次共享锁时交班会等它，应先发出交班请求、确认在等锁，再放锁）：

| # | 交错 | 预期 |
| --- | --- | --- |
| R1 | 原复现：开班（备用金 0）→ 另一连接 `BEGIN` 后对当日充值单号计数行加锁（`INSERT INTO doc_counters … ON CONFLICT … DO UPDATE`）→ 发起 ¥100 现金充值（卡在取号）→ 发起交班（应有现金 0；此时交班也在等锁）→ 放锁 | 充值 200，`shift_id` = 该班次；交班 409 `SHIFT_CHANGED`（`expectedCash` 10000）；按 ¥100 交班后快照含这笔 |
| R2 | 另一连接 `BEGIN; LOCK TABLE audit_logs IN SHARE MODE`（让交班停在拿到排他锁、写审计之前）→ 发起交班 → 发起 ¥200 现金充值 → 放锁 | 交班 200（快照 0）；充值 409 `SHIFT_CLOSED`，没有充值单、余额与流水不变；开新班后同一编号重提 200，记到新班次 |
| R3 | 同 R2，把充值换成现金结账 | 结账 409 `SHIFT_CLOSED`，客人仍在店、账单未结、没有结账单；开新班后重提记到新班次 |
| R4 | 同 R2，把充值换成反结账（反结账人在班上） | 反结账 409 `SHIFT_CLOSED`，结账单仍有效；开新班后反结账提醒记到新班次 |
| R5 | 另一连接锁住会员行（`SELECT … FROM members WHERE id = … FOR UPDATE`）→ 发起充值（卡在会员锁）→ 交班（直接 200）→ 放锁 | 充值 409 `SHIFT_CLOSED`；之后不开新班重提，按未开班收款（`shift_id` 为空），已交班次快照不变 |
| R6 | 升级路径：在 `e425a9a`（迁移 015）开班、收几笔款，切到新 SHA 启动（迁移 016），再做 R1、R2 | 与 R1、R2 相同；交班快照仍含升级前的单据（时间窗口补算） |

### 0.2 复测第 3 轮意见修复：交班表取自同一时刻

Codex 在 `c15541e` 复测：交班汇总分多条查询（读已提交），汇总到一半时另一位员工反结账本班次的单，保存的交班表里结账合计与现金、团购券收款还是反结账之前的数，团购平台合计却已是 ¥0。

修复（`src/server/modules/shifts.ts` `shiftSummary`，不新增迁移）：交班表的各项用**一条语句**汇总，取自同一个快照。没有改用可重复读事务：交班要先等正在入账的收款提交（班次排他锁），可重复读的快照取在第一条语句开始、早于等锁，会漏掉等到的收款（第 0.1 节的协议）。

| # | 交错 | 预期 |
| --- | --- | --- |
| R7 | 原复现：前台开班，¥499 结账（现金 100 + 美团券 399）→ 另一连接 `BEGIN; LOCK TABLE recharges IN ACCESS EXCLUSIVE MODE` → 前台交班（应有现金 100，此时在等锁）→ 店主反结账这张单（200）→ 放锁 | 交班 409 `SHIFT_CHANGED`（`expectedCash` 0）；按 0 交班后快照：结账 0 张、收款方式与团购券都为空，各项一致 |
| R8 | 另一连接 `BEGIN; LOCK TABLE audit_logs IN SHARE MODE`（交班汇总完、写审计前停住）→ 交班 → 店主反结账（停在写审计）→ 放锁 | 交班 200，快照是反结账之前：结账 1 张 ¥499、现金 100、美团券 399，各项一致；反结账 200 |

一致性断言：收款方式合计 = 结账合计；团购平台合计 = 团购券收款；现金结账 = 现金收款；充值方式合计 = 充值实收；应有现金 = 备用金 + 现金结账 + 现金充值。回归测试：`tests/shift-boundary.test.ts`（13 项；R7 的用例在修复前的代码上失败）。

复测要点：A9 储值结账后在会员详情 / 流水找到「手牌结账 JZ…」——没有「撤销」，接口 409 `CHECKOUT_LINKED`，反结账后余额完整恢复；B1–B5 之外，收款与交班并发（例如一台终端充值时另一台立刻交班）交班表不漏记、开班期间发起的收款要么计入本班次、要么整笔拒绝（见 0.1）；期初导入期间改会员姓名或手机号整批拒绝；三个视口账单底栏与结账对话框无横向滚动；升级路径：在首次提测的 `e425a9a` 建库、开班并收几笔款，切到新 SHA 启动，迁移 016 执行，当班中的班次交班表仍包含升级前的单据。`npm test` 预期 **267 passed**（25 个文件），迁移 16 个，`check` 仍为 19 项。

加锁顺序：手牌（反结账）→ 同行组 → 来访 → 账单 → 会员（id 升序）→ 赠金批次；收款与反结账对经办人未交班的班次只加共享锁，交班只锁班次一行（排他）。

## 7. 验收要点（阻断项）

- 账错：营业额与收款不等、储值支付与会员消费不等、反结账后余额没有恢复、日结核对项不通过。
- 重复扣款 / 重复结账：同一编号或并发导致同一账单结两次、同一张团购券有两笔有效登记。
- 挂单离店：收款不足仍结清，或有消费的来访不结账就释放手牌。
- 越权：店员反结账、后勤岗位用储值收款、店员替别人交班。
- 数据丢失：反结账删除了原单、明细或流水；交班记录被修改。
- 旧模块：会员、库存、前台 S2 自检或已有 E2E 回归失败。
