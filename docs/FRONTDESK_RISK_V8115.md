## 2. 手牌芯片号与刷卡发牌

### 2.1 数据

- `hand_tags.card_uid`（可空）：读卡器读到的卡号（NFC 的 UID，或 IC / ID 卡的十进制卡号）。去掉分隔符（空格、冒号、短横线）、转大写后存，4–32 位数字或大写字母。同一门店里不重复（部分唯一索引 `hand_tags_card_uid_uq`）。
- 老的手牌都是「没绑」，照常手输牌号发牌。

### 2.2 接口

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/frontdesk/tags/by-card?uid=` | 查看在店手牌 | 芯片号 → 牌号与现在的状态：`{ found: false }`（没绑手牌），或 `{ found: true, tag, state, visit }`，`state` 是 `free` 空闲 / `in_use` 已在店（带来访）/ `locked` 已锁定 / `inactive` 已停用 |
| `PUT /api/frontdesk/tags/:id/card` | 维护手牌池 | `{ cardUid }` 绑定，`{ cardUid: null }` 解绑。已经绑在别的牌上的拒绝（`CARD_BOUND`，写明是哪张）。在店的牌也能绑、能解。记审计「手牌绑 / 解绑芯片号」 |
| `GET /api/frontdesk/tags` | 查看在店手牌 | 手牌池清单多带 `cardUid` |

### 2.3 接待发牌对话框

- 顶上一行读卡器状态：已连接 / 没连上（没连上时写「请手输牌号」）。看的是本机终端的设备服务（桥）与它下面的读卡器（`docs/HARDWARE.md` 第 3 节）。
- 刷到一张牌：牌号填进**现在这一位客人**——那一行空着就填它，不然填第一个空行，都填了就换掉现在这一行；这一行高亮；**不提交**。核对后按回车或点「确认发牌」才发。
- 同一次接待里重复刷同一张：提示「本次已刷」。
- 读不出来写明原因：读卡器没连上、没读到卡、这张卡没绑手牌、牌已停用、已锁定、已在店、分区不符。手输一直在。
- 分区：店员没自己选过分区的那一行，分区跟着刷到的手牌；自己选过（或跟着会员的性别带出来）的不改，写「分区不符」。
- USB 读卡器当键盘用的（把卡号打进来再回车）：
  - 光标在牌号框里：很快打进来的一串（间隔不超过 50 毫秒、至少 4 个字符）认作读卡，框里原来的内容不动，那一串按芯片号查；
  - 手敲进来的不是牌号（哪张牌都对不上）时，回车也按芯片号查一次；
  - 光标不在任何输入框里：在窗口上收。
- 回车只在两处算「确认发牌」：光标在牌号框里（框里已经是一张完整的牌号），或不在任何输入框里。称呼、查找会员这些框里的回车不发牌——读卡器万一把卡号打进了那些框，末尾的回车不能变成确认。
- 浏览器的 Web NFC 要 HTTPS，内网 http 用不了，所以走设备模块的读卡通道（本机终端的桥 / USB 读卡器）。

### 2.4 断网后自动核对

发牌请求照旧先存本机再发（「结果待确认」那一套，`AGENTS.md` 开发约定）。网络恢复时（`lib/connection` 的恢复通知）本机自动按原编号核对：

1. 按原编号只读查回——已经生效的清掉，提示「只生效了一次」；
2. 没生效、记录不超过 30 分钟：按原编号、原内容重提一次（同一个编号，服务端保证只生效一次，不会重复发牌）；
3. 重提被明确拒绝：不代表之前那次不会生效，**不自动作废、不下结论**，记下拒绝的原因，留在「结果待确认」里等人处理（查回 / 按原内容重新提交 / 确认作废，与以前一样）。

平时（进页面、每分钟）只查回、不重提。只有发牌会自动重提；挂账、换牌、结账照旧由人处理。连不上服务器、请求根本没发出去的那种，与以前一样当场告诉店员没发出去，不留待确认。

### 2.5 给房态中心的接头：`TagCardInput`

`src/client/features/frontdesk/TagCardInput.tsx` 是能单独用的牌号输入部件，接待发牌、换牌都用它，房态中心登记手牌号直接用：

```tsx
<TagCardInput
  value={code}
  onChange={setCode}
  // 刷到的牌这里能不能用：能用返回 null，不能用返回原因。发牌要空闲的牌；房态登记要在店的牌
  check={(found) => (found.state === 'in_use' ? null : `手牌 ${found.tag.code} 现在没有在店的客人`)}
  // 带出牌号以后：found.visit 是在店的那次来访（房态登记据此带出会员与等级）
  onCard={(found) => setVisitId(found.visit!.id)}
/>
```

- 它自己带读卡器状态那一行与读卡结果（成功、失败原因）；一屏上有几个牌号框时，只让当前那一个 `listening`，状态行由页面自己放一条 `ReaderStatusLine`（`showStatus={false}`、`showMessage={false}`、`onMessage`）。
- 没给 `check` 时查到的都接受；`isTagCode` 告诉它框里的内容算不算牌号（算的话回车交给 `onEnter`，不按芯片号查）。
- 要卡号本身的（后台给手牌绑芯片号）用同一个文件里的 `useCardReader`。

### 2.6 后台「手牌与前台 → 手牌池」

点一张手牌：「芯片号」一栏写现在绑的卡号；点「绑定」后刷一下（或手输）、确认；绑着的可以「换一张卡」「解绑」。清单上绑了的牌带一个小标，每个分区写「已绑芯片 N」。

## 3. 发牌前风控

一个功能开关「发牌前风控」（设置键 `frontdesk_risk_rules`，按店，默认开；后台「手牌与前台 → 前台规则」里改，要「修改经营规则」）。关掉以后发牌与以前一样：不查黑名单、不拦未结离店、不带预约。补录纸质单不查（客人早已按纸质单进过店）。

### 3.1 黑名单

- 表 `guest_blacklist`：会员或手机号（二选一）、姓名、原因、登记人与时间、解除人与时间与原因。只能「登记 → 解除」：数据库不许改登记内容、不许删、解除了的不许再改。同一位会员、同一个手机号同时只有一条没解除的。全公司一份（跟会员走）。
- 按手机号登记时，这个号码已经是会员的记成那位会员（以后换了号码照样拦）；不是会员的要写称呼，这个号码以后办了会员照样拦。
- 发牌时命中的会员**拒绝**（`GUEST_BLACKLISTED`），提示原因与登记人；同一次接待里有一位命中整笔拒绝。值班经理自己发牌也一样，要先解除。被拦下的那次另记一条审计「发牌被黑名单拦下」。
- 入口：会员详情里「黑名单」一块（能看会员的人看得到在不在；加入、解除要「维护黑名单」）；后台「手牌与前台 → 黑名单」是清单，能按会员或手机号登记、解除、连已解除的一起看。

| 接口 | 权限 |
| --- | --- |
| `GET /api/frontdesk/blacklist?all=1` | 维护黑名单 |
| `GET /api/frontdesk/blacklist/member/:id` | 查找与查看会员 |
| `POST /api/frontdesk/blacklist`（`{ memberId 或 phone + name, reason }`） | 维护黑名单 |
| `POST /api/frontdesk/blacklist/:id/lift`（`{ reason }`） | 维护黑名单 |

### 3.2 未结离店

- 这位会员名下有没处理完的「未结离店」待办（第 4.3 节；哪家店登记的都算）时，发牌被拦下（`CHECKIN_RISK_AUTH_REQUIRED`），要值班经理及以上当场授权。
- 授权用途 `checkin_risk`（`POST /api/auth/authorize`），对象是「发牌」：这几位会员 + 放行的原因；5 分钟内有效、只能用一次、只能申请的人用。没有未结离店时申请授权被拒绝（`GRANT_NOT_NEEDED`）。授权人可以就是当班的值班经理本人（再输一次自己的密码）。
- 发牌请求带 `riskGrantId`，在同一个事务里核销；授权人、时间、原因记在这位会员的来访上（`visits.risk_approved_by / risk_approved_at / risk_reason`），客人卡与经办记录里写着。
- 待办写了处理结果以后不再拦。

### 3.3 当日重复到店、预约

- 当日重复到店：提示「今天第 N 次到店」，写上一次的牌号与离店时间；不拦。按营业日、只算本店、不算撤销的。
- 预约：这位会员今天待到店的预约带出来（时间、项目、技师、备注）。发牌成功后，技师、客房的预约在**同一个事务里**标「已到店」并挂上这张牌（与「预约」页点到店写的一样，审计里写明是发牌带出的）；派对房到店要开使用单，仍在「预约」页点到店，页面上写明。发牌的回复里带 `arrivedBookings`。

### 3.4 预先看与再核对

`GET /api/frontdesk/members/:id/risk`（查看在店手牌）给页面预先看：`{ enabled, blacklist, unsettled, visitsToday, bookings }`。发牌的事务里再核对一遍，页面看到的不算数：

- 黑名单在锁住会员一行以后再查一次（登记黑名单先对会员一行加排他锁，两边串行——不会出现登记成功了同一刻的发牌照样发出去）；
- 未结离店在核销授权之前读；预约在事务开头锁住、发牌成功后才改。

命中留痕都在「接待发牌」那条审计的 `risk` 里：未结离店的放行授权（会员、待办、授权人、原因）、今天第几次到店、带出并标到店的预约。

## 4. 发牌后的异常

### 4.1 超时在店

12 / 24 / 72 小时三级：黄 / 橙 / 红，各配文字「超 12 小时」「超 24 小时」「超 72 小时」与图标。手牌卡片上是卡片底下的一条色带（有状态的卡片更高，同一排的卡片跟着拉齐），收银台待结账清单、客人卡抬头上是小标。原来的「超 6 小时」柚黄提示并进这三级，收银台的筛选改成「超 12 小时」。

### 4.2 客人卡上的「异常处置」

发卡台的客人卡（要「接待发牌、挂账、换牌」）：

| 处置 | 做什么 |
| --- | --- |
| 提醒 | 记一条「已提醒」（谁、几点、备注） |
| 加收 | 挂一笔「超时加收」（金额、原因）。就是一条手动金额的明细，走原来的挂账，结账时一起收，不另记余额。值班经理及以上直接加；别人要当场授权（用途 `checkin_risk`，对象是「加收」：这次来访 + 金额 + 原因） |
| 上报 | 记一条上报，指给一位责任人，进「异常待办」 |
| 临时外出 / 返回 | 来访标「外出」，手牌板上这张牌写「外出」；牌照旧占着、不能发给别人，账单不动；回来点「返回」 |
| 手牌丢失 | 进换牌对话框，原因、锁定原手牌、丢牌赔偿预先选好——一步走完「锁旧牌、收赔付、换新牌」；新牌可以刷卡带出 |
| 未结离店 | 记一条待办（应收多少、情况、责任人）。不动账单；这位会员下次来店发牌时被拦下来授权。真要把钱记成挂账，照旧在收银台用「挂账」结 |

- 接口 `POST /api/frontdesk/visits/:id/incidents`，`kind` 为 `remind / surcharge / report / away / return / unsettled`，带操作编号（类型 `visit_incident`）：同一编号重提返回第一次的结果；超时、断网、5xx 后进「结果待确认」，查回、按原内容重提、确认作废与挂账、换牌同一套。
- 已离店的来访不能再记。一次来访同时只有一条没处理完的未结离店。
- 都进来访的「经办记录」；收银台的账单上看得到有几条（不能登记）。

### 4.3 表与「异常待办」

- `visit_incidents`（只追加）：来访、当时的会员、种类、备注、金额（加收、未结离店）、加收挂上的那条明细、加收的授权人、登记时指的责任人、操作编号、营业日、登记人与时间。
- `visit_incident_events`（只追加）：待办的处理记录——指派给谁、处理结果。一条待办只能写一次处理结果（部分唯一索引）。
- 待办 = 没写处理结果的「上报」「未结离店」。发卡台顶上「异常待办」写着条数，点开是清单（先登记的在前）：能改派责任人、写处理结果；还在店的点牌号打开客人卡。
- 权限：登记、指派、写上报的处理结果要「接待发牌、挂账、换牌」；未结离店的处理结果要「前台风控的当场授权」（处理完这位会员发牌就不再拦）。

| 接口 | 权限 |
| --- | --- |
| `GET /api/frontdesk/incidents/todos` | 查看在店手牌 |
| `POST /api/frontdesk/incidents/:id/assign`（`{ assigneeId }`） | 接待发牌、挂账、换牌 |
| `POST /api/frontdesk/incidents/:id/resolve`（`{ note }`） | 接待发牌、挂账、换牌；未结离店另要前台风控的当场授权 |

手牌板的每张在店手牌多带 `awaySince`、`openTodos`；看板多带 `risk: { enabled, openTodos }`。来访详情多带 `awaySince`、`riskApproval`、`incidents`。

## 5. 权限、审计、加锁

**新权限**（默认值班经理及以上，后台「岗位权限 → 前台风控」里调）：

| 权限 | 中文名 |
| --- | --- |
| `frontdesk.blacklist` | 维护黑名单（加入、解除、看清单） |
| `auth.checkinRisk` | 当场授权未结离店的会员发牌、超时加收；处理未结离店的待办 |

**新审计动作**：`hand_tag_card` 手牌绑 / 解绑芯片号、`blacklist_added` 加入黑名单、`blacklist_lifted` 解除黑名单、`checkin_blocked` 发牌被黑名单拦下、`visit_incident` 异常处置、`incident_assigned` 异常待办指派、`incident_resolved` 异常待办处理结果。发牌带出的预约到店记原来的 `booking_arrive`（`detail.via = 'checkin'`）。

**快捷原因**（后台「数据字典与字段」可改）：超时加收的原因、加入黑名单的原因、未结离店放行的原因。

**加锁顺序**（已写进 `docs/LOCKING.md` 第 1 节）：

- 接待发牌：预约（这几位会员当天待到店的技师、客房预约，id 升序）→ 手牌 → 同行组 → 来访 → 账单 → 会员（共享锁）→ 授权凭据。预约的确认、到店、取消都先锁预约一行，方向一致；没有先锁来访再锁预约的路径。锁预约的那一句带上全部候选条件（本店、这几位会员、这个营业日、待确认 / 已确认、不是派对房），等锁的行锁到以后按最新一版重新核对：等锁期间被取消、到店、改期到别的营业日的都不锁、不标到店（Codex 审查 f6327a4；用例「预约改期与发牌同时来」）。
- 登记黑名单：会员一行（排他）→ 写一条；解除只锁那一条。
- 登记异常：来访 → （加收：账单 → 操作编号 → 授权凭据）→ 写异常。
- 待办的指派、处理结果：只锁那一条异常。
- 手牌绑 / 解绑芯片号：只锁那一张手牌。

## 8. 默认做法（待确认）

| 编号 | 事项 | 默认 |
| --- | --- | --- |
| FK1 | 谁能做什么 | 新增两项权限「维护黑名单」「前台风控的当场授权」，默认值班经理及以上。登记异常、指派、写上报的处理结果按现有的「接待发牌、挂账、换牌」；未结离店的处理结果要「前台风控的当场授权」 |
| FK2 | 发牌前风控要不要开关 | 一个功能开关，默认开，只有能改经营规则的人（店主）能关；关了发牌与以前一样。补录纸质单不查风控 |

| FK4 | 未结离店怎么放行、怎么销 | 值班经理及以上当场授权（可以是当班经理本人再输一次密码），一次授权只管这一次发牌、5 分钟内有效，要写原因。哪家店登记的都算。结账不自动销待办，要值班经理及以上写处理结果才不再拦 |
| FK5 | 重复到店怎么算 | 按营业日、只算本店、不算撤销的；只提示不拦 |
| FK6 | 预约带出哪些 | 今天这个营业日、待确认或已确认的。技师、客房的发牌成功后自动标到店；派对房要开使用单，仍在「预约」页点到店。只有会员本人带出自己的预约 |

## 9. 没做的

- 读卡器的真机：页面按 `docs/HARDWARE.md` 的桥协议与键盘式读卡器做，用例里是模拟的键盘式读卡器；桥的 APK 照旧等真机与规格。
