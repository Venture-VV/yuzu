店主 2026-10-31 定：v0.7.4 CI 通过就合并，不等独立验收，G7 验收在合并后补做（[PR #20](https://github.com/Venture-VV/yuzu/pull/20) 已合并，标签 `v0.7.4`）。合并时 Codex 的自动代码审查还在跑，结果提了四条（一条 P1、三条 P2），都在客房里，这一版修正。

- **G7 独立验收请以 v0.7.5 为准**：按 `docs/HANDOFF_V074.md` 第 4、5 节（R1–R19、M1–M8）验收，再加本文第 2 节的四项。v0.7.4 上客房退房的押金核对有 P1，不要在 v0.7.4 上做客房的资金验收。

- 接口变化只有一处：`POST /api/rooms/stays/:id/close` 必须带 `expectedDeposits`（员工看到的押金余额，按收款方式），见第 3 节。

## 1. 范围

| # | 审查意见 | 修正 |
| --- | --- | --- |
| C1（P1） | 退房只核对要补的房费，不核对押金：员工打开退房后另一台终端先退了一部分押金，退房仍提示按原来的金额退，系统却只记退剩下的 | 退房请求带上员工看到的押金余额（按收款方式），服务端锁好入住单后逐项核对，对不上拒绝 `DEPOSIT_CHANGED`，对话框重新取核对。收、退押金都要锁入住单，锁好后余额不会再变：退的就是员工交给客人的 |
| C2（P2） | 收过押金、在住期间已经全部退完的入住单，退房仍要求开班（按押金记录条数判断），对话框里却能点确认 | 只在员工看到有押金要退时才对班次加锁、要求开班；锁好入住单后照样核对（这时冒出押金也拒绝） |
| C3（P2） | 两台终端同时给同一位客人换房：后到的那次在锁房间之前读到的原房间已经变了，会再去锁第三间房（加锁顺序不对），然后报服务器错误 | 换房锁好两间房后，核对入住单还在原来读到的房间，被别的终端先换走了拒绝 `ROOM_CHANGED`，不再另锁房间 |
| C4（P2） | 入住时房价刚被改过被拒绝（`PRICE_CHANGED`）后，对话框一直用旧房价，只能关掉重开 | 入住对话框按房间编号从刷新后的房态看板取房间：房价跟着刷新，填好的内容还在，再确认就按新房价入住 |

## 2. 验收要点（在 v0.7.4 的 R1–R19、M1–M8 之外）

| # | 操作 | 预期 |
| --- | --- | --- |
| V1 | 入住收现金押金 ¥200；终端 A 打开退房（看到「现金 ¥200 全部原路退回」）；终端 B 在入住单上退现金 ¥50；终端 A 确认退房 | 拒绝，提示押金刚刚有变动、现在是现金 ¥150；对话框重新核对后显示 ¥150，再确认才退房；押金台账：退 ¥50（B）+ 退 ¥150（退房），合计 ¥200；交班现金押金净额为 0 |
| V2 | 同 V1，但终端 B 是再收一笔微信押金 ¥30 | 终端 A 确认被拒绝；重新核对后按现金 ¥200、微信 ¥30 原路退 |
| V3 | 打开「收款前必须先开班」；入住收现金押金后在住期间全部退完；用没开班的值班经理 / 店总退房 | 不要求开班，直接退房；押金台账没有新的退款行 |
| V4 | 同 V3，但还有押金没退 | 没开班的员工退房提示先开班（`SHIFT_REQUIRED`）；当班的员工可以退房 |
| V5 | 两台终端几乎同时给同一位客人换房（换到不同的空房） | 一次成功；另一次拒绝「入住单刚刚换过房，请刷新后重试」（409，不是 500）；不会出现两次换房记录叠在一起 |
| V6 | 入住对话框开着、填好手牌与称呼；后台把这个房型的房价改掉；点确认 | 提示房价刚刚改为新价格；对话框里的房价随即变成新价格，手牌与称呼还在；再点确认按新房价入住 |

自动化：`tests/rooms.test.ts`「并发与核对（v0.7.5）」三项覆盖 V1–V5（V5 用数据库锁让后到的换房停在房间锁上、先到的换房提交后再放行）；`e2e/rooms.spec.ts`「房价刚改过」覆盖 V6。

## 3. 接口

- `POST /api/rooms/stays/:id/close`：`{ clientKey, expectedDue, expectedDeposits: [{ method, balance }] }`。`expectedDeposits` 取自 `GET /api/rooms/stays/:id/checkout-preview` 的 `depositByMethod`（没有押金时是 `[]`）；收款方式重复时 400；与此刻的余额对不上时 409 `DEPOSIT_CHANGED`，`details.depositByMethod` 是现在的余额。
- 升级前保存在浏览器里、还没确认结果的「退房」请求（v0.7.4 的页面）没有 `expectedDeposits`，原样重提会被拒绝（400）：按「结果待确认」的规则先在服务端作废原编号，再重新退房。客房功能默认关闭，正常不会遇到。

## 4. 已执行的验证（开发会话）

结果见 PR 描述（npm test、客房 E2E、CI）。在修正前的代码上，新加的三项集成测试都失败（退房按旧押金照退、押金退完仍要求开班、换房报服务器错误），修正后通过。
