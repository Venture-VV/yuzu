## 0. 升级后马上会看到的变化（请先读）

- **平时什么都不多**：网络正常时页面与 8.1.2 一样。网络断了、刚恢复、系统更新以后，页面顶上才浮出一条提示（不挤动版面，打印时不显示；电子菜单、对客导览大屏上缩成右下角的小提示）。
- **断网时点提交不发出去**：明确写「连不上服务器，这次没有发出去；填的内容还在，网络恢复后再提交」，不再等 15 秒、也不进「结果待确认」。已经在「结果待确认」里的，网络恢复后马上自动查回。
- **系统忙不用再点一次**：等锁超时、死锁、请求太频繁、服务器正忙，页面自己原样重发（同一个操作编号），员工看不到。
- **头像菜单多「网络与同步」**：本机连没连上、版本、这台电脑上的「结果待确认」、最近的问题；店主、店长另看全店最近的页面报错。
- **交班表里多一条提醒**：这台电脑上还有「结果待确认」时提醒先处理（不拦）。
- **一块出错不再白屏**：只换掉那一块，导航还能用，并自动报给服务器。
- **服务器**：多了 `/api/ping`、过载保护、频率限制；`.env` 可以调（`OVERLOAD_MAX_INFLIGHT`、`OVERLOAD_MAX_LAG_MS`、`RATE_LIMIT_SESSION_PER_MIN`、`RATE_LIMIT_IP_PER_MIN`，写 0 关掉），**访问网段 `ACCESS_ALLOW_CIDRS` 默认不设**（与 Z5 一致）。数据库连接的事务开着不动超过 2 分钟会被断开。
- **代码**：全仓库排版统一（单独一个提交，`git blame` 跳过它）；CI 多两步：`npm run check:code`、`npm run format:check`。

## 4. 验收要点

1. **断网提示**：门店电脑登录后拔网线（或关 Wi-Fi）→ 几秒内顶上红条「连不上服务器…数据截至几点…现在提交不会发出去」→ 插回 → 绿条「网络恢复了，页面数据已刷新」几秒后收起，页面数据自己刷新。连着 Wi-Fi 但服务器关着时一样会提示（不只看网卡）。
2. **断网时提交**：会员充值走到「确认入账」时断网 → 点确认 → 写「这次没有发出去」，顶上没有「结果待确认」，填的内容还在 → 恢复后再点 → 入账一次。
3. **结果待确认马上查回**：用浏览器开发者工具让充值的回复丢掉（或提交后马上断网）→「结果待确认」→ 恢复网络 → 不用等一分钟就自动查回。
4. **系统忙自动重发**：两台电脑同时给同一位会员记账（或用 `e2e/resilience.spec.ts` 的拦截方法）→ 后到的那笔自动重发成功，只入账一次。
5. **页面代码下载失败**：开发者工具里把某一页的代码文件拦掉一次 → 页面自己重新加载、打开；一直拦着 → 只自动重新加载一次，之后给「重新加载」按钮（不一直刷）。
6. **系统更新提示**：页面开着时把系统更新到新版本 → 一分钟内顶上「系统已更新，方便时点刷新」；点「稍后」先收起。
7. **页面出错**：出错只换掉那一块，左边导航还能点；店主在「网络与同步」里看得到这条报错（地址、是谁、浏览器）。
8. **网络与同步**：头像菜单进；断网时也能打开（不重新加载）；待确认的笔数与「去处理」；「清掉页面缓存并刷新」不清待确认记录。
9. **交班提醒**：这台电脑上有「结果待确认」时，交班表里有提醒，照样能交班。
10. **服务端防护**（测试服的 `.env` 里临时调小再改回）：`RATE_LIMIT_SESSION_PER_MIN=5` → 页面连点几下也不报错（自动等一会儿重发）；`OVERLOAD_MAX_INFLIGHT=1` → 同时开几个页面不出错；`ACCESS_ALLOW_CIDRS=10.0.0.0/8`（不含自己的网段）→ 登录被拦、写明「这个网络不能使用系统」，供应商链接照常打开；`/api/ping` 一直能回。改回以后重启。
11. **员工食堂**：手机上用开发者工具把网速限成很慢 → 4 秒内先出来上次的页面（饭卡码照常）。
12. **整洁**：`npm run check:code`、`npm run format:check` 通过；小程序线的目录没有被排版（`git show --stat <排版提交>` 里没有小程序线的文件）。

## 5. 做过的反向验证

- 断网时**重提**「结果待确认」的那一笔：被挡下时照旧待确认（不当成被拒绝、不删本机记录）——`tests/client-api.test.ts`、`useOperation` / `sendErpOp` / 前台 / 电子菜单 / 管家部都按「第一次提交才算没发出去」。
- 服务器回 503 但不是过载保护（网关、带别的错误码）：照旧当网络问题、结果待确认（不自动重发）。
- `Retry-After` 太长（超过 12 秒）不重发、照原样报。
- 过载、限流、访问网段拒掉的请求：确定没处理（用例核对会员没建）；出错的、被拒的请求不占「同时在处理」的名额。
- 访问网段：编码过的地址（`/%61pi/…`）一样拦；不信任的来源自己写的转发头不算；写错的网段、负数启动就报错。
- 页面报错：别的网站发来的不收（来源检查）、太长的不收、每个 IP 每分钟 20 条。
- 整洁检查：在一份样例代码上认得出没等结果的 `tx\`…\``、`void tx\`…\``、`tx.unsafe(…)`，放过 `await`、`return`、`Promise.all`。

## 6. 已知的限度

- **断网时不能记账**（有意不做离线记账，`docs/RESILIENCE_V813.md` 第 4 节）；员工食堂扫码的「断网补登」照旧。
- 「网络与同步」的最近问题只记这一页打开以后的；全店的页面报错只在服务器内存里留 200 条，重启清空。
- 频率限制、过载保护的计数在应用进程里（一家店一个实例足够；以后多实例要换成共享的）。
- 自动重新加载只在「打开一页时代码没下载下来」，同一页 1 分钟内一次；本机存储用不了时不自动加载。
- 管家部 `Workspace.tsx` 的主组件还有约 3,400 行，要重新理状态才能再拆；三个结账弹窗涉及钱，这一版不合并。
- postgres.js 没升到 4.x（10-29 才发的大版本），3.4.9 的风险用整洁检查兜住。
- 外部接口（扫码收款、平台验券、开票）不做熔断：它们已经是「事务外调用 + 结果不确定按单号查回 + 每分钟补查」。
