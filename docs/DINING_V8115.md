## 2. 桌台动作（B1，`src/server/modules/tables-v8115.ts`）

- **结账以后先待清台**：餐饮规则「结账后先待清台」（`clearAfterCheckout`，默认开；后台「餐饮 → 餐饮规则」可关，关了结账后直接可用、与原来一样；用例基线 `legacySwitchesOff` 里关着）。桌台结账在同一事务里把这几张桌改成待清台（维修中的不动）。
- **清台**：待清台 → 可用。待清台、维修中的桌**不能开台、不能换过去**（`TABLE_DIRTY`、`TABLE_MAINTENANCE`）。
- **维修 / 恢复**：要原因与预计恢复时间（晚于现在、最远 90 天）；用餐中的桌不能维修（`TABLE_IN_USE`）；「恢复」回到可用。
- **并台**：在主台的详情里选几桌并进来（都在用餐中）。附台的开台指向主台，账单不搬动（明细还在各自的账单上）；一组一个主台、最多 10 桌（`TABLE_MERGE_LIMIT`），不串成几层（`TABLE_MERGED`）。
- **结账**：附台不能单独结，主台也不能撇下附台单独结（`TABLE_MERGED`）；结账核对（`checkout-preview`）选了主台或附台都把一组带上，页面跟着勾上，附台写「并入桌 X」。走现有的多桌一起结。
- **拆台**：附台不再并入主台，各结各的。撤台前先拆台（并着别的桌、并入了别的桌的都是）。
- **换台**照旧；附台换了桌照旧并在主台。**反结账**照旧（`frontdesk/checkout.ts` 没改）：待清台、维修中的桌也能恢复这次开台，重新结账以后照规则待清台。
- **桌台历史**：`table_events` 与开台、换台（转出 / 转入）、撤台、结账、反结账排在一起，最近的在前，最多 200 条。一次开台换过台的，开台记在原来那张桌、结账记在结账那一刻的桌。
- **操作编号**：清台、维修、恢复、并台、拆台都带 `clientKey`，同一编号重提返回第一次记下的那条（`replayed: true`），同一编号拿去做别的拒绝（`IDEMPOTENCY_CONFLICT`）。

## 3. 台账合并退菜（B2，`src/server/modules/dining-808.ts`）

- 「退菜记录」页签去掉；旧地址 `/dining/voids` 跳到 `/dining/ledger?type=voided`。原来的 `/api/dining/voids` 接口（按退菜的时间查）留着，页面不再用。
- 台账的类型（`type`）：全部 / 正常 / 退菜 / 赠送 / 折扣。
  - 退菜 = 作废的明细；
  - 赠送 = 被签赠券抵掉的行，折扣 = 被别的券或会员折扣抵到的行——都按结账单上记的「抵到哪几行」（`checkout_payments.coupon_lines`），只算没反结账的结账单；
  - 正常 = 其余有效的行。
- 退菜的行多三样：原因（明细上的）、怎么批的与审批人（审计里的：小额直接退 / 本人 15 分钟内 / 经理 / 当场授权（授权人））、责任岗位。
- **责任岗位**：退菜时选（服务员 / 厨房 / 水吧 / 果吧 / 客人原因 / 其他），请求里带 `blame`，记在 `frontdesk_void` / `table_void` 的审计里，不改明细表。点单页、桌台的退菜弹窗必选；服务端不强制（前台作废别的明细、老请求不带），没选的写「未选责任岗位」。
- 汇总多「退菜率」：退菜份数 ÷ 全部份数，另写金额占比（`voidRate`），按日期与分类筛完、类型筛之前的那一批算。
- 导出跟着筛选（文件名带「-退菜」等）；原来 14 列不动，最后多「类型、审批、责任岗位」三列；合计一行的「出品」列写退菜率。

## 4. 出品口下单权限与房号备注（B3，`src/server/modules/dining-order-v8115.ts`）

- **权限**：新加「点单：在餐厅 / 水吧 / 果吧下单」三项（`dining.orderRestaurant`、`dining.orderWater`、`dining.orderFruit`），默认给店主、店总、值班经理、店员（原来有「餐饮点单」的岗位）。新职责**康美部**（`kangmei`）默认有「餐饮点单」与水吧、果吧两项（没有餐厅），不和别的职责分组互斥。
- **核对**：点单页只列有权限的出品口；服务端逐行核对（按菜现在的点单分类，后台没设的按默认归），有一道不行整单拒绝（403 `OUTLET_FORBIDDEN`，写明哪几道）。同一编号原样重提不再核对，照原样返回第一次的结果。
  - 手牌客人下单（`POST /api/dining/orders`）只要「餐饮点单」+ 出品口权限，**不再另要「前台挂账」**（康美部是后勤岗位）；退菜、改单照旧要「前台挂账」。
  - 桌台点单照旧要「餐饮点单」+「前台挂账」，再加出品口核对。
  - 前台（发卡台）的「加项目」、平板电子菜单、小程序扫码点餐不经过点单页，照旧不按出品口核对。
- **手牌号、房号至少填一项**（`GET /api/dining/guest?tag=&room=`）：
  - 只填房号：`findGuestByRoom(tx, room)` 找这间房现在的客人，返回 `{ visitId, tagCode }` 或 `null`（找不到拒绝 404）。**这一版只认在住的客房**；房态中心（块 D）合进来以后在这个函数里接上「这间服务房现在登记的客人」，签名与返回值不变。下单带 `roomOnly: true` 与 `deliverRoom`，在挂账的事务里锁住来访以后再核对一次这间房还是这位客人（换了房、退了房 409 `ROOM_GUEST_CHANGED`）。
  - 都填：账记在手牌上，房号写在送达位置（`deliverRoom`，不核对房号）。
  - 只带 `tag` 的照旧（手牌找不到时当房号找在住的客人，找到了按只填房号处理）。
- **出品单**：送到房间的记 `deliver_room`，「送到哪」写「房 W301」（原来勾「送到客房」的照旧写「客房 W301」）。
- **整单备注**（`orderNote`，≤ 60 字）：写进这一单每道菜的出品单——厨房出品屏每道菜下面一条「整单：…」，点菜单每次下单一段写一次。桌台点单也能写。
- 配送人不做限制。
- **与菜品管理（`docs/DISHES_V8115.md`）的接头**（ZT26–ZT28）：
  - 加料是另外的菜，点单页把它加成单独一行（备注「配 某菜」），服务端照样逐行核对它自己的出品口——只能在餐厅下单的人给餐厅的菜配水吧的加料，整单拒绝、写明是那道加料。点单页的做法 / 加料弹窗里，加料在这个岗位不能下单的出品口的标「不能在水吧下单」、不能选（`outletBlockedText`，按菜单里那道菜的出品口），不藏起来。
  - 套餐下单一行，按套餐自己的出品口核对，不看含的几样（含的几样不单独下单、不单独记账，只记在出品单上）。
  - 整单备注（`kitchen_items.order_note`，≤ 60 字）与这一行的备注（`note`，≤ 40 字：做法、手写的口味、「配 某菜」）分开存、分开显示：厨房屏上这一行的备注（柚黄底）、套餐含的几样（湖蓝底）、整单备注（纸色底、虚线框，前面写「整单：」）各占一条；点菜单上整单备注写在那一次下单的抬头下，这一行的备注、套餐含的几样写在各自的行上。

## 6. 加锁与幂等

写进 `docs/LOCKING.md` 第 1 节最后一条：

- 清台、维修、恢复：操作编号的咨询锁 → 桌台一行（`FOR UPDATE`）→ 写 `table_events`；
- 并台、拆台：操作编号的咨询锁 → 桌台（id 升序；先不加锁地看这几次开台在哪张桌）→ 开台（id 升序，锁住以后核对没被转走）→ 写 `table_events`；
- 桌台结账：班次（共享锁）之后、开台之前也先锁桌台（id 升序），结账以后待清台；附台不能单独结在锁住开台以后核对（主台的附台在锁住主台以后读，并台、拆台都要锁主台，不会在这之后再变）；
- 开台、换台在原来锁住的桌台行里核对待清台、维修中；撤台在锁住开台以后核对没在并台；反结账照旧（桌台 → 开台），不改桌台状态；
- 都是「桌台 → 开台」，没有反过来的路径；`table_events` 的外键只指向调用方已经锁住的桌台、开台；
- 台账、桌台历史只读；点单页按出品口核对、按房号找客人不加锁，只填房号的在挂账的事务里锁住来访以后再只读地核对一次。

桌台动作不涉及钱：结果不确定时在当前页面再点一次同样的按钮（沿用原编号，服务端只记一次）；不存本机、没有「确认作废」——状态核对挡住了重复（已经清过台的再清提示不用清台）。下单、退菜照旧走前台那一套「结果待确认」。

## 8. 验收要点

1. 桌台结账以后格子写「待清台」，点它「清台」回到空闲；待清台时开台、换过去都被拒。后台关掉「结账后先待清台」，结账以后直接空闲。
2. 空桌「维修」：不填原因或预计时间不能提交；维修中格子写原因与预计时间，不能开台；「恢复」回到空闲；用餐中的桌维修被拒。
3. 两桌用餐中：在 A 桌「并台」选 B 桌 → B 格子写「并入桌 A」，B 的详情没有「结账」；A 结账时一起勾上 A、B，应收是两桌之和；B 「拆台」以后各结各的；并着的桌撤台被拒。
4. 「历史」里开台、换台、并台、拆台、结账、反结账、清台、维修、恢复都在，最近的在前。
5. 台账选「退菜」：只列退的菜，写原因、怎么批的（审批人）、责任岗位；选「赠送」「折扣」只列签赠券、券或会员折扣抵到的菜；汇总的退菜率等于退菜份数 ÷ 全部份数；导出的文件跟着筛选、多三列。打开旧地址 `/dining/voids` 跳到台账的「退菜」。
6. 康美部账号（后勤 + 康美部）：点单页只有水吧、果吧；点水吧的菜能下单；用接口点餐厅的菜被拒。
7. 只填房号（在住客房）找到客人，下单后厨房屏写「送到房 X」；房号没人住被拒；手牌号、房号都填的记在手牌上、写送到房。整单备注在厨房屏每道菜下面、点菜单上都看得到。
8. 回归：老的桌台、点单、退菜、结账、反结账照旧；`check` 全部 ✓。
