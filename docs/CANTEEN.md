# 员工食堂 · 柚子饭堂

> 店主 2026-11-06：Codex 在 [PR #68](https://github.com/Venture-VV/yuzu/pull/68) 做了第一版（独立员工服务 + 同步）。店主请 Claude 按自己的审美和功能设计重做：**界面可爱一点；不影响别的模块，就是多出来一个员工食堂模块；有专门的食堂负责人；借这个小功能让大家真正用上新系统，从一个小功能、小入口开始一步步熟悉。**
>
> 之前和 Codex 定下的照旧：yuzu 后台能管理就行；员工走独立的 HTTPS 入口（备案后正式上线，之前在测试环境跑通）；食堂是一个专门的部门；食堂负责人扫员工的动态码，对上工号和后台名单就算打卡成功。

## 0. 一句话

员工手机上打开 **柚子饭堂**：看今天吃什么、给喜欢的菜点个赞、到饭堂门口亮出 **饭卡码**；**食堂负责人**用手机一扫，打卡就记进 yuzu。**厨师**在手机上发布每天的菜单。yuzu 后台（ERP「员工食堂」）管名单、打印开通卡片、看用餐记录。

## 1. 谁用、用来做什么

| 谁 | 在哪儿用 | 能做什么 |
| --- | --- | --- |
| 员工（所有人） | 手机：柚子饭堂 | 今天 / 明天 / 这周的菜单；给菜点赞；亮出饭卡码；看自己这个月吃了几顿；换个头像 |
| 厨师（食堂部门） | 手机：柚子饭堂「厨房」 | 以上全部，加上编辑、发布菜单（复制昨天的一键带出），看每道菜收到几个赞 |
| 食堂负责人（食堂部门） | 手机：柚子饭堂「厨房」「扫码」 | 以上全部，加上扫码打卡、没手机的同事手动登记、撤销登记错的、看今天每餐多少人 |
| 管理员（店主、店总） | 电脑：yuzu → ERP →「员工食堂」 | 开关模块、选食堂部门、设开饭时间；员工名单（单个加、粘贴一批加、停用）、打印开通卡片、重新开通；看菜单、用餐记录（筛选、撤销、导出） |

- 员工账号与 yuzu 的系统账号（`staff`）**分开**：员工账号只能登录柚子饭堂，进不了管理后台，也没有任何 ERP 权限；系统账号的登录也进不了柚子饭堂。
- 名单只由管理员在 yuzu 后台维护（防止有人给外人建号蹭饭）；食堂负责人在手机上只能搜名单、手动登记。

## 2. 和 PR #68 有什么不同、为什么

| | PR #68 | 这一版 |
| --- | --- | --- |
| 架构 | 独立员工服务 + **第二个数据库** + 同步协议（同步版本号、打卡游标、凭据版本、授权版本） | yuzu 自己**多开一个员工端口**（和小程序端口同一个做法，`docs/MINIPROGRAM.md` 第 1 节）；数据只在 yuzu 一个库；公网入口是网关服务器上的 Caddy 转发（和小程序共用那台服务器） |
| 停用员工 | 下一轮同步成功后生效 | **马上生效**（每个请求都查名单） |
| 门店连不上 | 超过 5 分钟没同步就停止登录、发码、核验 | 员工的饭卡码**在手机上离线生成**，不用等网；负责人那边扫到的先记在手机上，**联网后自动补登** |
| 开通账号 | 后台建人给临时密码，首次登录改密，8 小时要重新登录 | 后台**打印开通小卡片**（二维码 + 开通码），员工扫一下设自己的密码，之后 30 天不用再登录 |
| 打卡 | 不限次数 | **每人每餐记一次**，重复扫提示「已经打过卡啦」，人数就是吃饭的人数 |
| 菜单 | 后台也能改（要回写员工服务、处理回写失败） | 只在手机上由厨师 / 负责人改，后台只看 |
| 好玩的 | 没有 | 点赞、选头像、「这个月吃了几顿」、吉祥物「柚柚」 |

保留 #68 想对的地方：员工 / 厨师 / 负责人三种角色、食堂部门、码由服务端核验且一码一用、菜单带版本号防覆盖、员工账号不碰 ERP 权限。

## 3. 架构

```
员工手机（浏览器，可添加到桌面）
   │ HTTPS  staff.<域名>（备案后；备案前见第 9 节）
   ▼
网关服务器上的 Caddy（与小程序同一台：只做 HTTPS 与转发）
   │ Tailscale（只放行网关服务器到门店 yuzu 的员工端口）
   ▼
门店 yuzu · 员工端口 CANTEEN_PORT
   │ 单独的 Fastify 实例：只有柚子饭堂的页面与 /api/canteen/*；没有管理后台、没有别的接口
   ▼
yuzu 数据库（名单、菜单、点赞、打卡都在这里）← 管理后台 ERP「员工食堂」直接读写
```

- **为什么不再建一个库同步**：食堂只是名单、菜单和打卡，没有必要维护两份数据和一套同步协议（还要两边分别备份、恢复时对齐版本号）。小程序已经定了「公网服务器只转发、数据只在门店」，柚子饭堂照同一个做法，部署时只是在同一台网关服务器的 Caddy 里多加一个站点。
- **员工端口的边界**：只挂柚子饭堂的静态页面和 `/api/canteen/*`；写请求核对来源（Origin 与 Host 一致）；会话 Cookie 单独一个名字（`yuzu_canteen_sid`，HttpOnly、SameSite=Strict，HTTPS 时加 Secure）；登录、开通按工号与来源 IP 限次；请求体上限 32 KB。主端口上没有 `/api/canteen/*`，员工端口上也没有 `/api/erp/*`。
- **模块开关**：ERP 注册表里加模块「员工食堂」（分组「员工服务」，**默认关**）。关着时后台接口按 ERP 规则拦截，员工端口的接口一律回「饭堂还没开张」。没设 `CANTEEN_PORT` 的实例不开员工端口，其余一切照旧。
- **门店系统连不上时**：员工照样能亮码（离线生成）、能看上次打开时的菜单；负责人扫到的码先存在手机上，显示「已记下，联网后自动补登」，恢复后按原操作编号补交（第 6 节）。

## 4. 数据（迁移 `090_canteen.sql`，只建自己的表）

| 表 | 内容 |

## 5. 饭卡码

- **离线生成**：登录后手机拿到一把只属于自己的码钥匙（`HMAC(CANTEEN_CODE_SECRET, 员工编号 + code_epoch)`，服务端不存、随时能算出来）。饭卡码每 **30 秒**换一次：`YZC1:<员工编号>:<时间段>:<签名>`，签名是码钥匙对时间段的 HMAC 取 8 位。手机按上次联网时记下的服务器时间差修正本机时钟。
- **服务端核验**：负责人扫到码交给 yuzu，按扫到的时间核对时间段（前 90 秒到后 30 秒内的都认）、签名、员工是否启用。签名用常量时间比较。
- **一码一用**：同一人同一餐只记一次，所以同一个码再扫只会提示「已经打过卡啦（几点几分）」，不会多记。
- **作废**：管理员停用员工、重新开通（忘了密码）时，`code_epoch` 加一、员工端会话全部删掉：旧手机上的码钥匙随之失效，马上扫不进。
- **能防到什么程度**：码不是固定的工号，截图一分半钟后就失效；转发出去的码只能用一次，本人再来就会提示已打卡。负责人看到的是姓名、工号、部门和头像，当面核对；这不是门禁闸机，挡不住有人尾随进门。

## 6. 打卡规则

- **餐次**按扫到的时间落在哪个开饭时间里：默认早餐 07:00–10:00、午餐 10:30–14:30、晚餐 16:30–20:30，夜宵 22:00–次日 01:00 默认不开（后台可改、可开，**待确认 K2**）。跨午夜的夜宵记在开始那天。不在开饭时间扫码，提示「现在不是开饭时间」并列出时间。
- **每人每餐一次**（**待确认 K3**）。重复扫码不是错误，黄色提示「已经打过卡啦」。
- **手动登记**：同事没带手机、手机没电时，负责人搜名字或工号点一下登记，记为「手动」（可写一句备注）。
- **撤销**：负责人当天可以撤销自己登记错的（写原因），管理员在后台随时可以撤销；撤销只做标记、不删记录。
- **断网补登**：负责人手机发不出去或结果不明（超时、服务器出错）时，先把这一笔（操作编号、码、扫到的时间）存在手机上并读回核对，**存不下就不发**；之后每 10 秒、以及恢复联网时按原操作编号原样补交，直到拿到明确结果。服务端按扫到的时间核验码，只收 24 小时内扫到的（**待确认 K5**）。补登结果在扫码页列出：成功几条、哪几条无效（例如码过期、员工已停用）。
- 同一个操作编号重复提交，返回第一次的结果（并发也只记一条）。

## 7. 菜单与点赞

- 每天每餐一份菜单，最多 30 道菜，每道菜名最多 20 个字，可选一个表情（按菜名自动带出，例如「鱼」🐟、「鸡」🍗、「面」🍜，厨师可以改）和标签：辣 🌶、素 🥬、新 ✨、招牌 ⭐；一句话备注最多 100 字。
- 厨师和负责人可以保存草稿、发布；员工只看得到已发布的。改菜单带版本号：两个人同时改，后保存的提示「菜单刚被别人改过」，看过最新的再改，不会互相覆盖。保存的回复没收到时，原样重试（同一个操作编号、同一个版本号）会拿到同一个结果。
- 「复制昨天」「复制上周同一天」把那天的菜带进编辑框，改一改再发布。
- 点赞：员工给喜欢的菜点 ❤️，再点取消；厨师在厨房页看到每道菜几个赞，后台菜单页也能看到。

## 8. 开通与登录

1. 管理员在后台加人（单个加，或把「工号 姓名 部门」一行一个粘贴进来，先预览再加），然后**打印开通卡片**：每人一张小卡片，有「柚柚」、姓名、工号、二维码和 8 位开通码，7 天内有效（**待确认 K6**）。
2. 员工用手机相机扫卡片上的二维码（或在登录页点「我有开通码」手动输入），看到「欢迎你，某某」，设一个至少 6 位的密码，就进来了。
3. 之后 30 天不用再登录（用着就一直顺延，**待确认 K7**）；换手机、忘密码时管理员点「重新开通」打一张新卡片，旧手机上的登录和饭卡码马上失效。
4. 同一个工号连续输错 5 次密码锁 15 分钟；同一个来源 IP 10 分钟内最多试 30 次（**待确认 K8**）。
5. 第一次打开会教员工「添加到桌面」：iPhone 用 Safari 的分享 → 添加到主屏幕，安卓用浏览器的「安装应用」。在微信里打开会提示「点右上角 ··· 在浏览器打开」（微信里不能添加到桌面，扫码页也可能用不了相机）。

## 9. 上线步骤

**代码合并后、备案之前（测试环境跑通）**——只在测试服 A 的演示库（`yuzu-demo`）上开，不在门店试用库、演练库上开：

1. 演示库那台的 `.env` 叠加 `compose.canteen.yaml`，设 `CANTEEN_PORT`、`CANTEEN_CODE_SECRET`（`openssl rand -hex 32`）。
2. 在测试服 A 上用 `tailscale serve` 把员工端口发成 tailnet 内的 HTTPS 地址（带有效证书，相机和添加到桌面都能用）；参加测试的手机装 Tailscale 加入店主的 tailnet 就能打开。也可以用香港的服务器挂 Caddy 转发（不用备案，但跨境网络不保证稳定）。
3. ERP「模块设置」打开「员工食堂」，「员工食堂 → 设置」选食堂部门、核对开饭时间、填员工入口地址；加几位测试员工、打印开通卡片，按第 12 节的清单在 iPhone 和安卓真机上走一遍。

**备案之后（正式）**：网关服务器的 Caddy 加一个站点 `staff.<域名>`，转发到门店 yuzu 的员工端口（经 Tailscale，规则只放行网关服务器到这个端口）；门店 yuzu 叠加 `compose.canteen.yaml`、设 `CANTEEN_COOKIE_SECURE=true` 与 `CANTEEN_TRUST_PROXY=<网关服务器的 Tailscale 地址>`，`CANTEEN_BIND` 设成门店那台的 Tailscale 地址（默认只监听本机 127.0.0.1，适合 `tailscale serve`）。部署照旧由 Codex 按 `main` 的版本标签做，开不开由店主定。

```
# 网关服务器的 Caddyfile 里加一段（示例）
staff.<域名> {
  reverse_proxy <门店 yuzu 的 Tailscale 地址>:8090
}
```

| 环境变量 | 说明 |
| --- | --- |
| `CANTEEN_PORT` | 员工端口；不设就不开（默认不开）。不能与 `PORT`、`MP_PORT` 相同 |
| `CANTEEN_HOST` | 员工端口监听的地址，默认同 `HOST` |
| `CANTEEN_CODE_SECRET` | 饭卡码的密钥，至少 32 个字符；开了员工端口就必须配。换了它所有人的饭卡码要重新打开柚子饭堂（联网一次）才能用 |
| `CANTEEN_COOKIE_SECURE` | 员工端走 HTTPS 时设 `true` |
| `CANTEEN_TRUST_PROXY` | 前面的转发服务器的地址（逗号分隔，可写网段）；限次按它转来的真实来源 IP 算。不设就不信任转发头 |

## 10. 这一版不做

收费、餐补、饭卡余额、报餐与备菜人数、按部门限餐；门禁闸机与电锁；菜品照片；「下周想吃什么」投票；食堂负责人在手机上加人（名单只在后台管）；员工账号与系统账号合并登录。以后要做时再排。

## 12. 测试与验收

- 集成测试 `tests/canteen.test.ts`：模块开关、名单与开通、登录与锁定、饭卡码（过期、伪造、停用、重新开通后作废、跨天）、每餐一次、手动登记与撤销、断网补登（24 小时内外）、同一编号并发、菜单版本与发布、点赞、员工端口与主端口互不认会话、来源检查。
- 手机浏览器流程 `e2e-canteen/`（Pixel 5 与 iPhone 尺寸）：后台开模块、加人、打印开通卡片 → 厨师开通并发布午餐 → 员工开通、点赞、亮码 → 负责人开通，用「从相册选」识别员工的码打卡、重复扫提示已打卡、断网扫到先记下、联网后补登成功 → 后台看到记录。CI 单独一个检查「员工食堂：手机端浏览器验收」。

给测试 AI 的验收要点（独立演示库，不碰门店库与测试服的演练库）：
