# 8.1.15 菜品管理（《浴族系统需求汇总》餐饮第 4 条）

店主 2026-11-19 的《浴族系统需求汇总》餐饮第 4 条：「新增菜品管理模块」。对照现状与分块见 [`YUZU_REQ_V8115.md`](YUZU_REQ_V8115.md) 第 3 节 C（这是块 C，迁移 `189_dishes.sql`）。需求原文的做法：

- 餐饮里多一个页签「菜品管理」（有权限的人才看得到）。
- 一张表看全部菜品：名称、分类、出品口与小类、档口、价格、上架 / 下架、今天的沽清、图片（电子菜单里有图的带出来）。
- 新增 / 编辑：名称、分类、价格、出品口、档口、图片、规格、做法、加料、套餐。
- 上下架一点就生效；改价单独一项权限、写改价记录，以前的订单照下单时的价；维护权限按出品口分三项；Excel 导出与导入。

没写细的地方按默认做，记在 [`PENDING_DECISIONS.md`](PENDING_DECISIONS.md)「8.1.15 追加：《浴族系统需求汇总》」里的「块 C：菜品管理（CP）」CP1–CP12，都待确认；本文第 11 节列了编号对照。

## 1. 菜品是什么：就是餐饮价目项目，不另建表

- **菜品 = 价目项目里挂了出品档口、不需要技师的那些**（`service_items.station_id` 不为空且 `technician_required` 为否）。这与点单页的菜单、厨房屏的沽清列表是同一个口径，只是菜品表里连下架的、档口已停用的也列出来。
- 原来散在三处的维护照旧能用：后台「价目」（名称、分类、各档价格）、后台「餐饮 → 出品档口与菜品」（档口、点单分类）、后台「电子菜单」（平板上的图文与版面）。菜品管理是在同一份数据上给一个统一的入口，再补三样原来没有的——做法、加料、套餐——与改价留痕。
- 在菜品管理里新增的菜直接写进价目（不需要技师、挂上选的档口、点单分类写明），后台价目里马上有它；后台价目里新建的项目，挂上出品档口以后就出现在菜品表里。
- 价目全公司一套（`docs/CONVENTIONS.md` 第 2 节），做法、加料、套餐、改价记录也不按门店分；今天的沽清照旧读 `dish_limits`。
- 规格沿用价目里的三档（标准 / 专业 / 优选）。点单页卖的仍是默认档（第一档填了的价），在点单页选档不在这一版（CP1）。

## 2. 数据（迁移 189）

只加表、加列，老的价目、订单、出品单一行不动；升级以后什么都不用配，点单与以前一样（`tests/upgrade-dishes.test.ts`）。

| 表 / 列 | 内容 |
| --- | --- |
| `dish_methods` | 做法：`item_id`、`name`（1–8 个字，前后不带空格）、`sort_no`；主键（菜、做法）。保存一道菜时整批换 |
| `dish_addons` | 加料：`item_id`、`addon_item_id`（另外一个价目项目）、`sort_no`；不能选自己 |
| `dish_combo_items` | 套餐内容：`combo_item_id`、`item_id`、`quantity`（每份套餐含几份，1–99）、`sort_no`；不能选自己。触发器兜底「套餐不套套餐」：子项自己不能是套餐，已经在别的套餐里的菜不能再做成套餐 |
| `service_items.dish_image_id` | 菜品自己的图（引用 `emenu_images`：图按内容存、只追加）；空着时菜品表带出电子菜单里那道菜的图 |
| `kitchen_items.parts` | 出品单上的套餐内容：下单当时含哪几样（`[{ "name": …, "quantity": … }]`，每份套餐的份数），不是套餐为空数组。写入以后不可改（另加一条触发器；原来出品单的保护不动） |
| `dish_price_changes` | 改价记录，只追加：菜、当时的菜名、哪一档、改前、改后、原因、从哪里改的（`dishes` 菜品管理 / `import` 菜品导入 / `catalog` 后台价目 / `price_list` 价目表导入）、经办人、时间。改前为空 = 原来没有这一档（新建菜品的定价也记一条），改后为空 = 去掉了这一档 |
| `dish_ops` | 菜品管理的操作编号，只追加：编号、类型（新增 / 编辑 / 上下架 / 改价 / 导入）、原请求摘要、哪道菜、第一次的结果、经办人 |

## 3. 权限

新增四项（`src/shared/permissions.ts`，默认店主、店总；别的岗位在后台「岗位权限」里加）：

| 权限 | 管什么 |
| --- | --- |
| `dish.restaurant` / `dish.water` / `dish.fruit` | 维护餐厅 / 水吧 / 果吧的菜品：新增、编辑、上下架、做法、加料、套餐、图片、导入 |
| `dish.price` | 定价与改价：新建时定价、以后改价都要它，并且要有这道菜所在出品口的维护权限 |

- **看**：有任一项就看得到「菜品管理」与全部菜品（含自己改不了的出品口）、改价记录、导出。
- **改**：在事务里锁住这道菜以后，按库里这道菜现在的出品口核对（没设过点单分类的按默认归的那一处）；把菜挪到另一个出品口，两边的权限都要有。页面上没有权限的那几道，按钮是灰的并写明原因——页面上看到的不算数，服务端逐项核对。
- **改价**：`dish.price` + 这道菜所在出品口的维护权限。新建菜品要定价，所以也要 `dish.price`（CP6）。
- 导入逐行核对：每一行照那道菜的出品口，改价、新建的行还要 `dish.price`；不够的写在那一行的问题里。
- 只有菜品权限、进不了餐饮的岗位（没有点单、厨房出品屏、结账这些；少见）：主导航多一个「菜品」入口（`/dishes`），打开的是同一页（CP7）。

## 4. 改价与改价记录

- 改价在菜品表里点「改价」：填各档的新价（空着 = 不卖这一档，至少留一档）、写原因（快捷原因在数据字典 `dishPriceReasons`，仍然可以手填）。页面带上打开时看到的各档价格，与现在的不一样（别人刚改过）拒绝 `DISH_PRICE_STALE`；价格没变拒绝 `DISH_PRICE_SAME`。
- 改的是全公司的价目（`service_item_prices`），默认档的价同步到 `service_items.price`；每一档的变化记一条改价记录。第二家店的本店价（8.0.22）不在这里改。
- **以前的订单照下单时的价**：账单明细上本来就留着当时的单价（`bill_lines.unit_price`），改价不碰明细。改价以后按旧价确认的下单会被拒绝（`PRICE_CHANGED`，原有的行为），按新价重新确认。
- 后台价目里改到菜品价格的两处也进改价记录：单个项目保存（原因记「在后台价目里修改」）、价目表导入（「按价目表导入」）。那两处的权限照旧（「管理充值套餐与消费项目」）；不是菜品的项目改价不进这份记录。
- 改价记录在菜品表上方的「改价记录」（全部菜品，最近 200 条，新的在前）与每道菜的改价弹窗里（这一道的）。

## 5. 点单这一头：做法、加料、套餐

下单的接口与请求格式都没变：做法、加料是页面把它们拼成原有的「一行一道菜 + 口味备注」，套餐内容由服务端在建出品单时记下。

- **做法**：点单页点一道有做法或加料的菜，先弹出选项（`DishOptionsDialog`）。选的做法写进这一行的出品备注，用「，」隔开，后面还能接手写的备注（`composeDishNote`：「微辣，免葱，面硬一点」）；合起来最多 40 个字（出品备注的上限），放不下不让加进已点。
- **加料**：选了的加料另起一行（它自己的价、份数），备注写「配 某菜」（`addonNote`）。加料是另外的菜：各算各的钱，各有各的沽清与出品档口；只列现在能点的（在售、档口启用）。
- **套餐**：下单一行、按套餐这个价目项目自己的价。建出品单时（`createKitchenItems`，手牌点单、桌台点单、平板电子菜单、小程序扫码点餐都经过它）把当时含的几样记在出品单上（`kitchen_items.parts`）：以后改了套餐的内容，已经下的单还是当时的。
- **看得到的地方**：点单页的菜单上，套餐写着「含 …」，有做法、加料的写着「可选做法、加料」；已点里套餐那一行写着「套餐含 …」。厨房出品屏的出品单上，做法与「配 某菜」在口味备注里，套餐另有一行「含 …」（多份时写「每份含 …」）。点菜单（小票可视化）上套餐那一行也列出来。
- 菜单接口 `GET /api/dining/menu` 的每道菜多三项（有的才带）：`methods`、`addons`（`id`、`name`、`price`）、`combo`（`name`、`quantity`）。厨房屏 5 秒取一次的沽清列表不带。
- 平板电子菜单、小程序：点套餐同样会在出品单上列出含的几样（同一条下单路径）；做法、加料在这两处先不提供（CP11）。

## 6. 导出与导入

- **导出全部**（Excel）：一行一道菜，列是 编号、名称、分类、出品口、小类、档口、标准价、专业价、优选价、状态、做法、加料、套餐内容，后面三列只读（今日沽清、图片、电子菜单）。价格写元。
- **导入**（Excel `.xlsx` 或 CSV，UTF-8 / GBK 自动识别）：按表头的名字找列，列的先后、多出来的列都不要紧。
  - 有「编号」的按编号找菜（可以顺便改名），没有的按名称找，找不到就新建。新菜要写出品口（果吧以外还要小类）、档口、至少一档价格。
  - 已有的菜，格子空着是不改；做法、加料、套餐内容、某一档价格要清掉写「无」。
  - 加料、套餐内容写菜名（套餐内容写「菜名×份数」），用顿号隔开；这份表里新建的菜也能用。
  - **先预览再生效**：预览把整份照生效的做法在事务里跑一遍、最后回滚，什么都不写——核对的规矩、权限、约束与单道保存是同一批函数，不会「预览说能导、生效时被拒绝」。每一行在一个保存点里做，有问题的记下原因、只回滚这一行，接着看下一行。
  - **整份有问题不写**：有一行有问题，生效时整份拒绝（`IMPORT_INVALID`，带逐行的问题）。
  - 生效要带回预览的摘要（`planHash`）：预览以后菜被别人改过、文件换过，算出来的不一样就拒绝（`IMPORT_CHANGED`），请重新预览。有改价要写原因。
  - 最省事的做法：先导出、在导出的表里改、再导回来——没动的行算「没变」，原样导回来什么都不改。
- 导入不改图片、不改今天的沽清，也不删菜（不卖了的下架）。一次最多 1,000 行。

## 7. 页面

- **餐饮 → 菜品管理**（`/dining/dishes`，`features/dining/DishesTab.tsx`）：
  - 上面一栏：搜索（菜名、分类、档口、小类、做法）、按出品口筛（全部 / 餐厅 / 水吧 / 果吧，带数量）、按状态筛（全部 / 上架 / 下架 / 沽清）；新增菜品、导入、导出全部、改价记录。再写一行：共几道、上架下架沽清各几道、这位员工能维护哪几处。
  - 菜品表：宽屏（1280 起：收银机、平板）一行九格——图片、名称（套餐写出含的几样，做法、加料列在下面）、分类、出品口与小类、档口、价格、状态、今日沽清、操作（编辑、改价、上架 / 下架）；窄屏（手持点单机）同一份内容排成一道一张卡片。都不横向滚动。

- **新增 / 编辑**（`DishEditor.tsx`）：名称、出品口与小类（没有权限的那几处选不了）、档口、分类、图片；规格与价格（新增时填，编辑时只读并指到「改价」）；做法（手写或点常用的）；加料、套餐内容（搜菜名加进来，套餐每样的份数用 `QtyInput`）。已经当了别人的加料、进了别的套餐的菜，套餐内容那一段写明不能再做成套餐。

- **导入**（`DishImportDialog.tsx`）：选文件、下载模板、预览（新建 / 修改 / 没变各几道、逐行的问题、每一道改什么）、改价原因、生效。
- **点单时选做法、加料**（`DishOptionsDialog.tsx`）：见第 5 节。

## 8. 接口

都要登录。看 = 有任一项菜品权限；维护 = 有任一处的维护权限，再在事务里按那道菜的出品口核对。

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/dining/dishes?q=&outlet=&status=` | 看 | 菜品表（不带条件是全部）、出品档口、已有的价目分类 |
| `POST /api/dining/dishes` | 维护 + 定价 | 新增；`clientKey`、名称、分类、`slot`、`stationId`、`imageId`、`methods`、`addons`、`combo`、`prices`、`active` |
| `PUT /api/dining/dishes/:id` | 维护 | 编辑（不含价格、上下架）；另带 `rev` |
| `POST /api/dining/dishes/:id/active` | 维护 | 上架 / 下架 |
| `POST /api/dining/dishes/:id/price` | 定价 + 维护 | 改价；`prices`、`expected`、`reason` |
| `GET /api/dining/dishes/price-changes?itemId=` | 看 | 改价记录 |
| `GET /api/dining/dishes/export.xlsx` | 看 | 导出全部（记一条导出的审计） |
| `POST /api/dining/dishes/import/preview` | 维护 | 预览；`fileName`、`csv` 或 `xlsxBase64` |
| `POST /api/dining/dishes/import` | 维护 | 生效；另带 `clientKey`、`planHash`、`reason` |
| `POST /api/dining/dishes/images`、`GET /api/dining/dishes/images/:id` | 维护 / 看 | 图片（压缩后的 Base64，单张不超过 1 MB） |

审计动作：`dish_saved`（新增、编辑，写明改了什么）、`dish_active_set`、`dish_price_changed`、`dishes_imported`（整份一条，不逐道记）。

## 9. 操作编号、版本与加锁

- **操作编号**：新增、编辑、上下架、改价、导入各带一个 `clientKey`，记在 `dish_ops`。同一个编号、同样的内容重提，返回第一次的结果（`replayed: true`），不会多建一道、多记一条改价；同一个编号换了内容拒绝（`IDEMPOTENCY_CONFLICT`）。
- **不进门店的「结果待确认」**（CP10）：菜品维护是档案维护、不是收款，不存本机、没有「确认作废」，所以不占 `idempotency_keys` / `op_fences` 的类型。结果不明（超时、断网、服务器出错）时弹窗留着，内容没动的话再点一次用的还是原来的编号；也可以关掉刷新，看表里是不是已经改了。
- **版本**：编辑带打开时的版本 `rev`（这一行最后一次修改的时刻），别人先改过（含后台价目、后台「出品档口与菜品」改了这一行）拒绝 `DISH_CHANGED`。什么都没改的保存不动这一行、不记审计。
- **加锁**（`docs/LOCKING.md` 第 1 节末尾）：操作编号的咨询锁 →「菜品维护」咨询锁（菜品管理的写入全部串行）→ 这道菜与它引用的加料、套餐子项（`service_items`，id 升序，`FOR NO KEY UPDATE`）→ 做法 / 加料 / 套餐子表 → 改价记录 → 操作记录。导入锁全部价目项目（id 升序）。
  - 与后台价目、后台「出品档口与菜品」锁的是同一批行、同一个顺序（id 升序），互相排队；`FOR NO KEY UPDATE` 不挡点单写明细时对这一行的外键检查——营业中维护菜品、预览导入不会让下单等着。
  - 不碰来访、账单、出品单的锁；点单读价目、做法、加料、套餐都不加锁。

## 10. 验收要点

1. 菜品表里是全部挂了出品档口的价目项目（含下架的），不是菜品的不在；搜索、按出品口、按状态筛对；今天的沽清与厨房的「沽清」页一致；电子菜单里有图的菜带出图。
2. 新增一道带做法、加料的菜；新增一个套餐（含哪几样、每样几份）。后台价目里有它；点单页的菜单马上有。
3. 套餐不套套餐、套餐不能当加料、当了加料或进了套餐的菜不能再做成套餐；不能选自己、不能选不是菜品的项目。
4. 下架一点就生效：点单页的菜单马上没有、下单被拒绝；电子菜单上标「已下架」、不能点；已经点了的不受影响。再上架照常。
5. 改价：没有 `dish.price` 的改不了；改价记录里有改前、改后、谁、几点、原因；以前的订单金额不变，之后的按新价。后台价目里改菜品的价也进改价记录。
6. 只有水吧权限的人：水吧的菜能改、能上下架；餐厅、果吧的菜看得到、按钮是灰的，接口也拒绝；把水吧的菜挪到餐厅被拒绝。
7. 导出的 Excel 原样导回来：全部没变。改几格再导：预览里列出每一道改什么；写错的行逐行有问题，整份不写；改好以后生效。
8. 点单：选做法、加料以后出品单上是「微辣，免葱」「配 牛肉面」；套餐一行，出品单上列出含的几样；账上的金额 = 主菜 + 加料 + 套餐各自的价。改了套餐内容以后，已经下的单还是当时的。
9. 同一个操作编号重提（连点、重试）：新增不会多一道，改价不会多记一条，导入不会写两遍。
10. 四种屏幕上菜品表、三个弹窗、点单的选项弹窗都不横向滚动、按钮在屏幕里。

## 11. 默认做法（待确认）

全文在 `docs/PENDING_DECISIONS.md`「块 C：菜品管理（CP）」，这里只列编号与一句话：

| 编号 | 事项 |
| --- | --- |
| CP1 | 菜品就是餐饮价目项目，不另建表；规格是价目里的三档，点单页仍卖默认档 |
| CP2 | 做法：平铺、可多选、不加钱，最多 12 种、每种 8 个字 |

- 平板电子菜单、小程序上选做法与加料。
- 菜品的排序、批量上下架、删除菜品（不卖了的下架）。
