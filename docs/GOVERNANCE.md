# 工程治理 · 让 AI 能长期开发 yuzu（三期）

店主 2026-11-18：学完视频《如何用 AI 长期开发一个复杂项目》，给跑了快一个月的 yuzu 出一套改进方案并分三期做完——少硬编码、清冗余的历史代码、重构文档、完善测试、系统瘦身、统一代码与界面规范。学习记录与开源工具调研见 [`GOVERNANCE_NOTES.md`](GOVERNANCE_NOTES.md)；这份是方案与进度，随三期更新。默认做法（待确认）见第 6 节。

## 1. 一句话

yuzu 的代码本身不乱（重复率 0.78%，没用到的文件 0 个），问题出在**约束的方式**：规则都堆在一份 88 KB 的 `AGENTS.md` 里靠 AI 每次读，没有变成检查；文档只增不减；界面的字号、颜色靠手写。三期做的是同一件事——**把规则从「写在文档里请大家遵守」改成「入口小、专题分开、能查的都让 CI 查」**，再借着检查把存量清掉。

## 3. 三期

每一期一个版本、一个 PR：开发、自测 → 改成待审（Codex 审查）→ CI 全绿、审查没有问题 → 合进 `main` → 开下一期的草稿 PR。

### 一期 · 文档收拢与护栏（不改业务行为）

| 做什么 | 做到什么算完 |
| --- | --- |
| `AGENTS.md` 收成入口：只留红线、按任务去哪看、开发约定小节、提交与 PR 规则 | 预算 24 KB（原来 88 KB，拆完 18 KB）；原文一个字不丢地搬到专题文档，脚本核对 |
| 拆出专题文档：`docs/LOCKING.md`（加锁顺序，按模块分节）、`docs/COMMANDS.md`（命令）、`docs/CONVENTIONS.md`（开发约定） | 写哪个模块读哪一节，不用整份读 |
| 文档索引 `docs/README.md`：现行规范 / 模块设计 / 发版快照 三类 | 每份文档都在索引里（检查兜底） |
| `README.md` 按现状重写；`CHANGELOG.md` 分卷（8.1 留下，更早的进 `docs/changelog/`） | README 不再有过期的状态描述 |
| 文档检查 `npm run check:docs`（进 CI）：死链、引用不存在的文档、索引不全、`AGENTS.md` 超预算 | CI 里跑、能拦住 |
| 治理基线 `npm run check:gov`（进 CI）：第 2 节的数字记成基线，**只许持平或下降** | 新写的代码不会让这些数变多 |
| 版本号只留一处（`package.json`） | 发版只改 `package.json` 与锁文件；镜像、页面显示的版本不变 |

### 二期 · 代码瘦身与去硬编码（行为不变，靠全量用例兜底）

| 做什么 | 做到什么算完 |
| --- | --- |
| 删掉没人引用的导出与类型；收回只在本文件用的 `export` | knip 基线归零；之后新的死代码由 `check:code` 直接报出来 |
| 接入 oxlint，修掉存量 | 进 CI，0 处 |
| 合并重复实现：导入页的公共部分、两个结账弹窗的公共段、两个「结果待确认」横幅 | 重复率基线下降 |
| 字号进令牌：在样式表里定字号阶梯，把手写的 `text-[13px]` 换成令牌（像素不变） | 手写字号基线归零；以后改一种字号只改一处 |
| 颜色进令牌：页面代码里的十六进制颜色换成样式变量（UI 工作台除外） | 颜色基线只剩设计工具里的 |
| 设置键、依赖声明、首屏主包 | 设置键集中登记；没声明的依赖补上；主包体积记基线 |

### 三期 · 测试分层与界面规范

| 做什么 | 做到什么算完 |
| --- | --- |
| 测试分三档：秒级（不要数据库）、快测（只跑和改动相关的）、门禁（全量，CI） | `npm run test:unit` 一分钟内；`AGENTS.md` 的开发约定小节写明每档什么时候跑 |
| 用例体检：CI 里从不执行的、长期按条件跳过的、靠固定等待的 | 清单进文档，能修的修、该删的删（只删重复覆盖的，资金与权限的一项不少） |
| 覆盖率记基线 | 报表进 CI 的摘要页，不设硬门槛 |
| CI 提速：浏览器验收重新分组（现在三组 17 / 13 / 10 分钟不均）、类型检查只跑一遍 | 整次 CI 回到 12 分钟以内；门禁一项不少，汇总照旧核对用例总数 |
| 界面规范 `docs/DESIGN.md` 按现状重写：令牌、字号阶梯、共享组件清单与用法 | 新页面照它做；违反的由检查报出来 |
| 共享组件约束：数量输入、加载失败、二级页签、快捷原因等必须用公共部件 | 写成检查 |
| 每版巡检清单与项目内 Skill | 发版前照清单过一遍 |

## 4. 怎么不和别的线冲突

主线同时有另一个开发会话在 [PR #127](https://github.com/Venture-VV/yuzu/pull/127) 做 8.1.10 的 ERP 功能，小程序线在 Gemini 手里。

- **不碰小程序线的目录**（`miniprogram/`、`src/gateway/`、`src/server/modules/mp/`、`src/client/features/mp/`、`src/shared/mp.ts`）；检查与基线都不算它们。
- **一期只动文档、脚本、CI 与版本号的读法**，不改业务模块。
- **二期的批量改写避开另一个会话正在改的文件**（开工时看它的 PR 改了哪些），那些文件留在基线里，等它合并后再清。
- **基线是上限，不是定值**：检查只在数字变多时不通过，别的会话正常开发不用碰基线文件。
- **文档不改名、不搬家**（交接说明留在原地）：代码注释、PR、飞书里引用的路径照旧能用。只有 `CHANGELOG.md` 的旧卷移走、`AGENTS.md` 里的专题搬到新文档。
- **版本号按合并先后取下一个**；治理的文档名不带版本号。

## 5. 长期规则（一期合并后生效，写进 `AGENTS.md`）

1. **入口小**：`AGENTS.md` 有体积预算，新规则写进专题文档，入口只加一行指路。
2. **第二次出现就写成检查**：同一类问题审查里第二次被提出，就加进 `check:code` / `check:gov`，不再只写进文档。
3. **基线只降不升**：存量问题记数，清掉一批就把基线调低。
4. **交接说明是快照**：发版当时的记录，写完不再改；现行规则以专题文档为准，两边不一致以专题文档为准。
5. **每版巡检**（发版前）：`check:docs`、`check:gov` 通过；这一版新加的文档进了索引；被新方案替换掉的旧函数、旧页面已经删掉。

## 8. 治理基线怎么用

`npm run check:gov`（约 5 秒）把现在的数字和 `scripts/governance-baseline.json` 比，**只在变多时不通过**：

| 检查 | 口径 | 一期的基线 | 不通过时怎么办 |
| --- | --- | --- | --- |
| 分层 | `shared` 不引 `server` / `client`，`client` 不引 `server`，`server` 不引 `client` | 0（硬规则） | 把共用的部分放进 `src/shared` |
| 十六进制颜色 | 页面代码（`src/client`、`src/canteen-app`）的字符串、模板、JSX 文字里的 `#rgb` / `#rrggbb`，按模块目录记数 | 207 处、15 个目录 | 用样式表里的变量或 Tailwind 的色名 |
| 手写字号 | `text-[Npx]` 出现了哪几种 | 32 种（处数不拦，二期换成令牌后再拦） | 用已有的字号 |
| 大文件 | 超过 1,500 行的源文件 | 8 个 | 把独立的部分搬到新文件 |
| 没人引用的导出 | knip：导出了、整个仓库没有任何地方用到 | 68 个 | 没用就删；只在本文件用就去掉 `export` |
| 重复代码 | jscpd：70 个词、8 行起算 | 上限 1%（现在 0.78%） | 抽成公共函数或部件 |

- 数字变少不用管；清掉一批以后跑 `npm run check:gov -- --update` 把基线收紧（只会调低）。
- 确实要放宽的（例如设计工具里新加一组默认颜色）：`npm run check:gov -- --update --allow-increase`，并在 PR 说明里写原因。不要手改基线文件来过检查。
- 小程序线的目录不查。
