## 1. 8.1.0 里有什么

- **功能与 8.0.22 完全一样**：8.0.20–8.0.22 那一批（进销存做深、财务与合同做深、对外接口、多门店、AI 辅助）全部做完，见变更记录的 v8.0.20–v8.0.22。
- 这一版只改版本号、协作约定、CI 的线范围检查与文档。**没有新迁移，不改业务代码**；从 8.0.22 升上来什么数据都不动。
- 从 8.1.0 起：主线 8.1.1、8.1.2 照 Z1 加最后一位；小程序线交给 Gemini 以后照旧不改 yuzu 的版本号，它合并的代码随主线的下一个版本标签一起发。

## 2. 升级（给 Codex，在店主批准的窗口做）

**从哪个版本升上来**：以 Codex 的发布记录为准。店主的飞书文档（第一百二十版，2026-11-13）记着：阿里云正式服、影子运行、门店本机测试服（8890）三套都已手动切到 **8.0.19**（`020b8d3`）。直接 `./scripts/update.sh v8.1.0` 就行，不用逐版升：应用启动时按编号补齐所有没执行过的迁移。从 8.0.19 升上来要执行 29 个：`126`–`129`、`138`–`158`、`161`–`163`（`159`、`160` 没用上、没有文件）。其中 `154` 给前台、班次等表加门店列，默认值是只读函数、不重写整张表，只有按店唯一的几个索引要扫一遍表，数据量小的库几秒钟。

**先后**：测试服演示库 → 测试服演练库 → 影子运行 → 正式服，一个过了再做下一个。每一个：

1. 停在店主批准的窗口；`./scripts/update.sh v8.1.0`（脚本自己先备份、留着旧镜像、记下这次新加的迁移，再重启；启动时自动迁移）。
2. 登录页与导航栏显示「8.1.0 + SHA」和对的实例标识（正式服 / 影子运行·不作数 / 测试服·不作数 / 演示库）；标识或 SHA 显示错误是阻断项。
3. `docker compose exec app node dist/server/cli.js check` 全部 ✓；`fingerprint` 记下摘要。演示库再跑一次 `demo-check`。
4. 有问题：`./scripts/rollback.sh` 回到升级前的版本（这次加了迁移，会同时恢复升级前的备份），在主线当前开着的 PR 上留发布记录与问题。

## 3. CI 的「线范围检查」

小程序线交给 Gemini 以后，两边按目录分工照旧（`AGENTS.md`「四个 AI 按线协作」）。为了不靠人盯，CI 多一个检查 `线范围：小程序线只改自己的文件`（`scripts/check-line-scope.mjs`，用例 `tests/line-scope.test.ts`）：

- **只对小程序线的 PR 生效**：分支以 `gemini/` 开头，或标题以【小程序线】开头，或带「小程序线」标签。主线的 PR 照旧通过（显示「不是小程序线的 PR」）。
- **随便改的**：`miniprogram/`、`src/gateway/`、`src/server/modules/mp/`、`src/client/features/mp/`、`src/shared/mp.ts`、`compose.mp.yaml`，以及小程序线自己的用例与文档（`tests/mp-*.test.ts`、`tests/gateway*.test.ts`、`e2e/mp-*`、`docs/MINIPROGRAM.md`、`docs/MP_*`、`docs/HANDOFF_MP*`、`docs/DEPLOY_GATEWAY.md`）。名字像、其实是主线的两份用例除外：`tests/mp-entries.test.ts`、`tests/mp-claim-coupon.test.ts`（测的是主线写给小程序线的入口）。
- **登记处**（允许，但在检查结果里列出来，由主线开发会话复核只是「加挂接的几行」）：`src/server/app.ts`、`src/shared/permissions.ts`、`src/client/App.tsx`、`src/server/lib/audit.ts`、`src/shared/admin.ts`、`src/server/config.ts`、`src/shared/types.ts`、`tests/helpers.ts`、`.env.example`、`docs/ROADMAP.md`、`docs/PENDING_DECISIONS.md`、两份部署手册（`docs/DEPLOY_MAC_MINI.md`、`docs/DEPLOY_TEST_SERVER.md`）、`GEMINI.md`、`.gemini/settings.json`。登记处的文件不能删、不能改名。
- **迁移**：只能新加 `NNN_mp_<用途>.sql`；改、删、改名已有的迁移一律不行（迁移只增不改）。
- **其余文件**（会员、钱包、券、结账、前台的核心，CI，`package.json` 等）：检查失败，写明是哪几个文件、该怎么办（在主线开着的 PR 上留言写清需求，由主线做）。

它只看 PR 改了哪些文件，不跑业务代码，几秒钟。拿以往小程序线合并的 PR 回放过（#55、#57、#59、#61、#62、#64、#81、#84、#87）都通过；最早的 #42、#44 动过后台外壳、部署手册与 CI，按现在的分工会被拦（部署手册后来归进了登记处）。

这个检查放在单独的工作流 `.github/workflows/line-scope.yml`，用 `pull_request_target`：跑的是 main 上的检查，PR 改不了它；它只把 PR 的提交取下来比对文件名，不检出、不执行 PR 里的代码，不用密钥。所以**这个 PR 自己看不到这个检查**（main 上还没有这个工作流），合并以后的 PR 才有；规则在 `tests/line-scope.test.ts` 里核对（含在临时 git 仓库里走一遍命令行）。店主可以在 GitHub 的分支保护里把「小程序线只改自己的文件」设成必须通过（不设也行：红了不合并就是）。改了 CI（加这个工作流）按 ROADMAP 第 7 节在 PR 说明里写明。
