# 员工 Web App 与食堂管理

本模块提供独立的员工入口：员工看菜单、出示动态员工码，厨师发布菜单，食堂负责人扫码核验并登记打卡。YuZu 内网后台负责部门、员工名册与员工端角色管理，并查看同步回来的菜单和打卡记录。

当前交付范围是合成数据测试环境及代码，不包含公网发布、正式环境部署、门禁硬件控制或真实员工数据导入。本文说明已实现的行为与配置，不代表 Android、iPhone 真机摄像头或正式上线验收已完成；验证结果应以对应完整提交 SHA 的报告为准。

## 1. 组成与数据方向

| 组成 | 作用 | 数据库与网络边界 |
| --- | --- | --- |
| YuZu 内网后台 `/erp/canteen` | 管理食堂部门、独立员工名册、角色、启停和密码重置；编辑菜单、查看打卡镜像 | 使用该 YuZu 实例的数据库；无需对公网开放 ERP |
| 独立员工服务 `src/employee/server/` | 员工登录、菜单、动态码、负责人扫码及同步接口 | 必须显式设置独立 `EMPLOYEE_DATABASE_URL`；独立监听端口 |
| 员工 Web App `src/employee/client/` | 手机浏览器页面及添加到桌面的 PWA | 经员工服务的 HTTPS 来源访问；不使用 ERP 登录会话 |
| YuZu 同步任务 | 主动向员工服务推送全量名册，并拉回菜单与打卡 | YuZu 发起出站请求；两端用专用共享密钥认证 |

员工名册、所属部门、是否启用、角色和管理员密码重置以 YuZu 为准。**菜单与打卡以员工服务数据库为主记录**：厨师直接向员工服务发布，YuZu 后台的菜单保存也先请求员工服务；确认成功后写入 YuZu 镜像。员工服务不可用时，后台不能假装已发布菜单。

YuZu 每轮同步推送名册，同时取回菜单快照和按游标增量返回的打卡记录。菜单按版本更新镜像，打卡按记录编号去重；失败时不推进成功时间或游标。打卡保留发生时的工号、姓名、部门、负责人姓名与时间，之后修改名册不会改写这份历史快照。日期与展示时间使用 `Asia/Shanghai`。

这是一套有人值守的扫码登记流程。它不连接电锁或闸机，也未加入人脸或手机设备绑定；负责人应当面核对返回的姓名、工号与本人。动态码缩短转发可用时间，但不能承诺消除代打卡。

## 2. YuZu 后台设置

食堂模块默认关闭。由有权管理 ERP 模块的管理员启用后，具有 `canteen.manage` 权限的后台账号可进入「员工服务 → 员工食堂」。

1. 在已有部门管理中准备一个启用的食堂部门，在食堂页面选择并保存。
2. 新建独立员工名册记录，填写工号、姓名、部门和角色。工号由 2–32 位字母、数字、下划线或短横线组成，保存时转大写；同一名册中不能重复。
3. 新建成功后复制本次显示的临时密码，单独交给本人。页面关闭后不提供密码查询；遗失时使用「重置员工端密码」。不要填写、索取或分发 ERP 密码。
4. 查看同步状态，必要时点击立即同步；确认同步成功后，让员工在独立入口登录并更改临时密码。

| 员工端角色 | 菜单与个人功能 | 额外权限 |
| --- | --- | --- |
| 员工 `employee` | 查看已发布菜单、出示本人动态码、查看本人打卡、修改密码 | 无 |
| 厨师 `chef` | 同上 | 查看草稿，编辑和发布每日菜单 |
| 食堂负责人 `manager` | 同上 | 编辑菜单、扫码打卡、查看食堂打卡记录 |

厨师和负责人必须属于当前选定的启用食堂部门。更换食堂部门前，应先停用原部门中仍启用的厨师和负责人，再调整部门设置及人员归属。普通员工可以属于其他启用部门。

员工名册与 ERP 工作账号独立：新增厨师或负责人不会创建 ERP 登录账号，也不会授予 ERP 权限。停用员工或停用其部门后，该员工在下一次成功同步时失去员工端资格。紧急停用应立即同步并确认成功，不能只凭后台已保存就认为手机端已收到变更。

密码重置会生成新临时密码并要求再次修改。临时密码只在操作成功的提示中展示，不写入前端待确认请求，也不作为明文保存到操作回执中；网络重试可取回同一笔操作的临时密码。已关闭成功提示且密码丢失时，应另行重置。

## 3. 员工端操作

### 登录与安装到桌面

员工打开独立入口，以工号和员工端密码登录；首次登录或管理员重置后，必须先改密码。新密码至少 8 位，同时包含字母和数字。会话使用员工服务自己的 HttpOnly Cookie，HTTPS 环境带 Secure，SameSite 为 Strict，期限为 8 小时。

这是 Web App / PWA，不是微信小程序，也没有打包成 App Store 或安卓商店安装包。iPhone 可用 Safari 的「添加到主屏幕」，安卓可在支持的浏览器中选择安装应用或添加到主屏幕。安装与摄像头行为仍需按实际机型、系统和浏览器验收。

Service Worker 只缓存公共页面外壳及静态资源，不缓存员工资料、菜单、动态码、会话或打卡接口。离线时可能还能打开页面外壳，但不能获取有效员工码、更新菜单或确认打卡；不提供离线放行。

### 发布每日菜单

1. 厨师或负责人登录，进入「我的 → 菜单管理」。后台管理员也可在 YuZu 食堂页面操作。
2. 选择日期与早餐、午餐或晚餐，填写标题、逐行菜名及备注。
3. 保存草稿可继续编辑；选择发布后，普通员工可以看到该日期、该餐次的菜单。
4. 修改带原版本号提交。别人已修改时会提示版本冲突，应重新读取后再编辑，避免覆盖他人的更新。

每个日期和餐次对应一份菜单；标题最多 80 字，菜名 1–30 项、每项最多 80 字，备注最多 500 字。菜单的餐次只是展示分类，**没有扣费、饭卡余额、订餐、餐次额度或每天打卡次数限制**。

### 出示员工码与负责人扫码

1. 员工联网进入「员工码」，显示本人姓名、工号、部门和动态二维码。
2. 负责人进入「我的 → 负责人扫码打卡」，允许摄像头权限并扫描；也可选择员工码图片识别。
3. 服务端检查负责人仍属于食堂部门、双方账号仍有效、名册同步未过期、码未过期且未使用。
4. 只有收到服务器成功回执，才显示「食堂打卡成功」及员工姓名、工号、部门、时间和记录编号。负责人核对后继续扫描下一位。

动态码有效期为 **60 秒**，使用服务端时间核验。页面可自动或手动刷新；**每次发出新码，旧码立即失效**，包括同一账号在另一设备上取得的旧码。每个码只能成功使用一次；重复扫描不能新增打卡。需要再次登记时，员工可获取新码，没有额外的餐次或每日次数门槛。

二维码承载随机令牌，不是直接可编辑的工号。图片识别仍须联网向服务器核验，旧截图、已使用的码和被新码替换的码不会获准打卡。摄像头失败会给出 HTTPS、权限或设备提示；选择图片不是绕过核验的入口。

## 4. 同步、失效与版本

连接配置完整且食堂模块启用后，YuZu 启动时尝试同步，之后每 **30 秒**调度一次；上一轮未结束时不会并发开始下一轮。手动同步使用同一套同步流程。30 秒是调度周期，并非网络故障下的送达承诺。

员工服务以最后一次成功接收名册的时间判断新鲜度。超过 **300 秒**未成功同步，受保护的员工端接口会停止提供服务，包括登录、发码和扫码核验；不会继续把旧名册当作有效通行依据。恢复连接并完成同步后再重试。关闭模块、内网 YuZu 停机或同步密钥错误均可能导致这项保护触发。

同步版本和密码版本处理如下：

- YuZu 每次发出的同步快照带递增 `revision`。员工服务拒绝旧版本；即使一次响应丢失，后续同步也不会重复使用旧版本覆盖较新状态。
- 员工记录的 `version` 用于后台编辑冲突检查；菜单也使用独立版本号。
- 管理员重置密码会更换 `credentialVersion`。员工服务看到新凭据版本后，应用新的密码哈希并要求改密。
- 员工自行修改密码后，后续相同凭据版本的名册同步不会覆盖新密码。员工端自改密码不回传为 YuZu 的 ERP 密码。
- 员工服务的 `authVersion` 绑定登录会话和动态码。同步中的启停、角色、部门、工号或凭据变化会使该员工的旧会话与旧码失效；食堂部门变化会使全部旧会话与旧码失效。员工自行改密也会撤销旧会话与旧码，并建立新会话。

后台显示的最后同步时间与待同步状态用于判断两端是否已收敛，不能用服务 `/api/health` 正常替代同步确认。菜单与打卡镜像存在同步延迟；员工服务已确认的一笔打卡，应等待成功同步后再在 YuZu 查阅。

## 5. 配置与启动

环境变量由各自进程的私有运行配置注入，不把 `.env`、数据库连接串或共享密钥提交到 Git。两端使用同一专用 `EMPLOYEE_SYNC_KEY`，该密钥只在服务端，不放入前端构建或浏览器配置。

临时密码的原请求重放依赖生成时使用的同步密钥。**轮换 `EMPLOYEE_SYNC_KEY` 前，必须先完成或经服务端确认作废所有待确认的新建员工、重置密码请求**，再协调两端更新密钥。不要依赖轮换后的旧请求重放找回临时密码；忘记临时密码时重新发起密码重置。

### YuZu 进程

| 变量 | 用途 |
| --- | --- |
| `DATABASE_URL` | 此 YuZu 实例自己的数据库；测试时只能指向新建的隔离合成数据库 |
| `EMPLOYEE_PORTAL_URL` | 员工服务来源，例如 `https://staff.example.com`，只含协议、主机、可选端口，不带路径、查询参数或账号密码 |
| `EMPLOYEE_SYNC_KEY` | 专用随机共享密钥，至少 32 字符，与员工服务一致 |

后两项都留空时不连接员工服务；只填其中一项会拒绝配置。HTTPS 为默认连接要求，仅本机测试/开发可使用 localhost HTTP。仍需在 ERP 中启用食堂模块才能执行名册同步。

### 独立员工服务进程

| 变量 | 要求或默认值 |
| --- | --- |
| `EMPLOYEE_DATABASE_URL` | 必填，独立 PostgreSQL 数据库。配置检查拒绝与同进程 `DATABASE_URL` 完全相同的字符串；部署时仍须核对实际目标及数据库账号权限，不能靠 URL 写法不同实现隔离 |
| `EMPLOYEE_SYNC_KEY` | 必填，至少 32 字符且不能由少量重复字符组成；使用安全随机生成值 |
| `PUBLIC_ORIGIN` | 员工浏览器实际访问的来源，仅协议、主机、端口；生产必填 HTTPS，开发默认 `http://127.0.0.1:18962` |
| `EMPLOYEE_HOST` | 默认 `127.0.0.1`；仅按明确的反向代理/容器网络设计调整监听地址 |
| `EMPLOYEE_PORT` | 默认 `18962`，须与已运行服务错开 |
| `EMPLOYEE_TRUST_PROXY` | 可选，逗号分隔的真实反向代理 IP/CIDR；默认不信任转发头。不要配置任意来源均可信 |
| `APP_ENV` / `NODE_ENV` | 任一为 `production` 时启用生产启动校验；本地合成环境使用开发/测试配置 |
| `YUZU_INSTANCE` | 实例标识，开发默认 `employee-development`；生产必填 |
| `APP_VERSION` | 页面和健康接口显示的版本，未设置时为 `development` |
| `BUILD_COMMIT` | 完整构建提交标识；生产必填，开发未设置时为 `development` |

`PUBLIC_ORIGIN` 必须与地址栏来源一致，写操作会校验请求 Origin；不能将后台代理的内部地址错填为手机入口。生产反向代理应保留正确的 Origin 与 Cookie，并用证书提供 HTTPS。HTTP 仅接受本机开发来源，不接受直接用局域网 IP 作为手机入口。

仓库构建包含员工前端和服务端：

```sh
npm run build
npm run start:employee
```

员工服务启动时会在指定的独立员工库执行自身迁移，并从 `dist/employee/client` 提供静态页面。YuZu 按原启动流程运行并执行新增食堂迁移。启动前必须先核对两个数据库目标，不要让测试启动命令连接既有试用库或正式库。

需要前端热更新时可另开 `npm run dev:employee`，Vite 固定使用 `127.0.0.1:18963`，代理 `/api` 到 `EMPLOYEE_PORT`（默认 `18962`）。此时员工后端的 `PUBLIC_ORIGIN` 应设置为实际浏览器来源 `http://127.0.0.1:18963`；YuZu 的 `EMPLOYEE_PORTAL_URL` 仍指向员工后端端口，不指向 Vite。热更新入口不是正式手机部署。

本机测试服务使用已约定的独立端口范围 `18900–18999`，PostgreSQL 发布端口使用 `55400–55499`，新建测试库使用 `c1_` 前缀；启动前检查端口、数据库与其他测试聊天资源归属。默认端口不是占用许可。每个数据库使用专用账号和权限；分别命名数据库或容器并不能证明 AI 无权接触正式数据。

### 最简本机合成复现

先准备本机 PostgreSQL 和仅供合成测试使用、具有建库权限的账号，并确认 `18961`、`18962` 空闲。下面连接串中的账号、密码和 `<PG_PORT>` 都是占位符，必须替换为已核对的独立测试配置；不使用现有试用库或正式库的凭据。

```sh
npm ci && npm run build
CANTEEN_DEMO_DATABASE_URL='postgresql://TEST_USER:TEST_PASSWORD@127.0.0.1:<PG_PORT>/c1_staff_canteen_demo' npm run demo:canteen
```

脚本只读取显式提供的 `CANTEEN_DEMO_DATABASE_URL`，不读取 `DATABASE_URL` 或 `.env`；仅接受本机回环地址、无查询参数、以 `c1_` 开头且以 `_demo` 结尾的库名。它会自动创建缺失的独立配对库 `c1_staff_canteen_demo` 和 `c1_staff_canteen_demo_employee`，执行迁移并初始化合成部门、账号和连接。已有表但缺少本演示标记、或配对标记不匹配时拒绝写入。

脚本固定仅监听本机两个入口，端口占用时停止，不替换已有服务：

| 入口 | 地址 | 合成账号 |
| --- | --- | --- |
| YuZu 食堂后台 | `http://127.0.0.1:18961/erp/canteen` | `canteen_owner` |
| 员工 Web App | `http://127.0.0.1:18962/` | `EMP001`（员工）、`CHEF001`（厨师）、`MGR001`（负责人） |

这些账号的首次临时密码均为 `Initial-test-2026`，首登必须改密。**重复启动保留已有密码、菜单与打卡记录，不重置账号。** `Ctrl+C` 只关闭本脚本启动的服务，不删除数据库。演示内置的账号与同步密钥仅用于本机合成复现，不能沿用到正式入口。

保持演示进程运行，在另一终端执行浏览器验收：

```sh
npm run e2e:employee
```

需先准备 Playwright Chromium；也可指定已安装的 Chromium 可执行文件：

```sh
PW_CHROMIUM_PATH='/绝对路径/Chromium可执行文件' npm run e2e:employee
```

此浏览器配置只访问固定本机端口 `18961`、`18962`，不接受公网目标。运行前应确认没有其他全量浏览器验收正在执行。验收会编辑合成菜单、登记合成打卡，并把上述合成账号的初始密码改为 `Browser-test-2026`；之后手工登录请使用新密码，重启演示不会将其还原。若已自行设置其他密码，验收脚本不会替你重置。浏览器脚本中的虚拟摄像头核验不替代 iPhone 和 Android 真机摄像头验收。

## 6. 超时与待确认操作恢复

菜单保存、扫码登记，以及后台新建员工和重置密码均使用稳定的操作编号。请求发送前先保存原编号与原始内容并读回确认；保存失败就不发送。超时、断网或服务端错误后显示「结果待确认」，此时禁止另建同类请求替代原请求。

员工端将菜单与扫码的待确认请求按账号分别保存在当前标签页的 `sessionStorage` 中；刷新同一标签页后可恢复。YuZu 后台将待确认请求按后台账号保存在 `localStorage` 中。两者都不保存返回的临时密码。

恢复步骤：

1. 保留当前浏览器存储和原标签页，恢复网络；会话失效时以同一账号重新登录。员工端关闭标签页可能丢失本机待确认请求，不能把关闭页面当作撤销。
2. 员工端先点「核对结果」。查到完成则显示原结果；暂未查到不等于没有生效，继续使用「原样重试」，保持原编号和原内容。
3. 不再继续原操作时，使用「确认作废本次请求」，等待服务端明确返回已作废后才重新填写。服务端按原编号串行处理提交与作废，已完成的操作不会被当作未发生。
4. YuZu 后台使用「原样重试」找回回执；新建员工、重置密码与菜单可请求服务端确认作废。若返回已完成，继续原样重试取得完整结果；新建/重置的作废查询结果不含临时密码。
5. 后台部门与员工资料修改使用原 `version` 和原内容重试；服务端接受内容完全一致的精确重试。发生其他更新导致版本冲突时，不用修改本地待确认请求绕过冲突，应由管理员核对当前数据与原操作后处理。

不要手工清除存储、换新操作编号重发，或把「unknown」、重复提交时的拒绝、网络仍不可用视作已经撤销。若原存储损坏或标签页已关闭，应暂停重复操作，联系管理员核对服务器记录；需要原编号才能可靠处理原请求。没有实现离线排队后自动放行或自动补打卡。

## 7. 正式上线前置与尚需验证

本轮只使用独立合成测试环境，不公开新入口，不改变现有数据库或既有部署。备案完成后仍需单独完成部署准备和验收：

- 核对域名备案及选定托管地域的接入要求，配置 DNS、有效 HTTPS 证书与续期；正式地址须与 `PUBLIC_ORIGIN` 一致。
- 为员工服务部署反向代理、防火墙与登录/扫码等接口的限流；内置登录限流是进程内限制，不能替代多实例或公网入口层的防护。仅信任真实代理来源，并限制内部同步接口的可达来源。
- 配置独立数据库、最小权限账号、密钥保管与轮换流程；内网 YuZu 仅主动出站，不为同步公开 ERP。确认正式主机、数据库、备份和管理凭据不受测试 AI 的权限控制。
- 两端数据库分别备份并实做恢复演练。员工服务持有菜单和打卡主记录，不能只备份 YuZu 镜像。恢复时核对名册版本、凭据版本、递增同步序号、打卡游标与待确认回执，防止旧备份静默覆盖较新状态；需要时由运维协调重建镜像与同步位置，不在正常同步中自动重置数据。
- 在实际 iPhone Safari、Android 浏览器及添加到桌面后，验收摄像头授权、扫码速度、图片识别、切到后台恢复、动态码过期与换码、4G/5G 断网恢复及待确认找回。尚未完成的真机项目必须保留为待测。
- 使用专用测试账号演练厨师和负责人权限、停用同步、超过 300 秒拒绝、重置密码后旧会话/旧码失效、菜单并发修改和重复扫码；最终记录对应完整构建 SHA、环境和未测范围。

上述准备不等同于已经上线。正式启用仍应在备案及部署条件具备、业务验收完成后单独执行。
