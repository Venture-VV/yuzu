# v0.7.27 交接说明 · 给小程序线的两处：发券入口「小程序领取」、线上充值的原路退回

店主 2026-11-04 合并小程序线 #49（第二期 2a 线上充值、2b 对账）与主线 #50（v0.7.27 开工登记）后说继续开发。这一版先做小程序线等着主线的两处（按 MP8：小程序线写需求、主线做）：2c 线上领券要的发券入口、2d 线上充值原路退回要的退储值改动。设计与接口见 `docs/MEMBERSHIP_FINISH.md` 第 8 节，默认做法 `docs/PENDING_DECISIONS.md` M82（待确认）。

**退储值的改动动的是储值的退法**，按资金候选版本验收（快速开发周期：CI 全绿后店主合并，验收在 main 的 v0.7.27 标签上补做）。小程序线自己的 2c、2d 代码（领取记录、原路退回单、调微信退款）不在这一版，在小程序线的 PR 里。

## 2. 迁移、演示数据与固定预期

- 迁移 `049_mp_claim_refund_route.sql`：`coupon_issues` 的种类加 `mp_claim`、不挂发券规则，另加约束（1 张、有会员、有经办人、去重键 `mp_claim:` 开头）；`member_refund_lines.route`（`manual` / `mp_auto`，默认 `manual`），`mp_auto` 只能是充值、微信、不带单号，按行号取的部分索引。只放宽约束、加一列，不改已有的行；已有的退储值明细升级后都是「员工退」。
- `048` 是小程序线 2c 的（可领的券与领取记录），两条线的迁移互不依赖：先合哪边都行，迁移按文件名补跑没应用的。
- 演示数据、`*-expected.json` 不变（演示库没有小程序领取、也没有注册原路退回）。`check` 仍是 67 项。

## 3. 验收要点

1. **发券入口**（集成用例 `tests/mp-claim-coupon.test.ts`；页面上只在会员的券里看到「小程序领取」）：
   - 发 1 张，种类「小程序领取」、经办人「小程序」；同一个领取记录再调用不多发；同时发两次只出一张；
   - 停用、已合并的会员，停用、过期、档级不够的模板都拒绝，调用方事务里的其他写入一起回滚；
   - 只读判断 `mpClaimEligibility` 给出的原因与真正领取时一样，不写任何东西。
2. **退储值**（集成用例 `tests/member-refunds-online.test.ts`；页面：会员详情「储值与账户」→「退储值」）：
   - 没有小程序线注册原路退回时：线上那一行标「小程序」、写「请在小程序的微信支付商户平台原路退回后填退款单号」，必须填单号，与 v0.7.26 一样；
   - 接口直接提交「门店系统原路退回」：拒绝（`ONLINE_REFUND_UNAVAILABLE`），授权不浪费；
   - 注册并打开以后（小程序线 2d 合并后才有）：线上那一行默认「门店系统原路退回」、不填单号；前台充值的行、填了单号的都不能交给门店系统；
   - 日结「储值退回」的「其中退线上充值」、对账包 11 写明；v0.7.26 页面提交的请求升级后原样重提仍是同一笔。
3. **升级**：v0.7.26 的库升级到 v0.7.27，已有的退储值单照常显示、日结没有「有变动」误报（`tests/upgrade-mp-claim-refund-route.test.ts`）。
