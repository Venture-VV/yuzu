# 演示数据（飞书需求 RQ-007，v0.7.18 定稿）

店主 2026-11-02 在 PR #33 提出「完善演示数据，并让 CI 持续检查」，同日定 Q31 选 A：与 RQ-008（精简测试与 CI 等待，见 `docs/TESTING.md`）合成一版 v0.7.18，没有迁移；派对房等「开单即占用」（D39）排在之后的 v0.7.19。默认做法（待确认）见 `docs/PENDING_DECISIONS.md`「演示数据与 CI」。

目标：打开演示库就能体验较完整、互相关联的业务，不用每出一个新功能都临时手工补数据；准备、更新、核对都有一条命令，CI 每次在临时库里准备并核对。

## 1. 现状

- 五条命令各灌一块，要人工按顺序执行：
  - `seed-demo`：会员与项目；
  - `seed-inventory-demo`：库存、采购、应付；
  - `seed-frontdesk-demo`：747 张合成柜号与 13 位在店客人；
  - `seed-billing-demo`：结账、反结账、交班；
  - `seed-legacy-demo`：8–10 月旧账的合成样例。
- 每条都是「已灌过就跳过」；试用、正式环境一律拒绝。固定预期在 `src/server/demo/*-expected.json`。
- **没有覆盖**：客房、技师与钟房、餐饮与厨房、空间台账与底图（房态图）、实时位置。这几块的浏览器验收各自临时造数据，跑完再收回（例如实时位置的用例自己导入样例台账、打开开关、最后关掉），演示库里平时看不到。
- CI 只在浏览器验收之前灌一次、跑一遍一致性自检 `check`，不核对「灌出来的东西对不对、页面上看不看得到」，也不验证重复执行是否安全。

## 2. 做法

### 2.1 一条命令准备：`demo-prepare`

```bash
node dist/server/cli.js demo-prepare            # 新库从零准备；已有演示库只补缺
node dist/server/cli.js demo-prepare --previous-day   # 营业日切换后不久执行时，整体放到前一个营业日
```

- 依次执行：迁移 → 会员 → 库存 → 前台 → 结账 → 旧账 → **场景**（新增，见 2.2）→ 一致性自检 `check` → 演示核对 `demo-check`（2.6）。
- 每一块已经有了就跳过，缺的就补；最后打印一张表，写明每块是「已写入」还是「已存在，跳过」，场景块逐条列出写了什么，再列出核对结果；核对不通过时退出码 1。
- 实测：新库从零准备约 13 秒（本机），已准备好的库再执行 0.3 秒。
- 原来的五条命令照旧可以单独用，`demo-prepare` 只是按固定顺序调用它们，再加上场景块。
- **两次执行结果一致**：第二次全部跳过，数据指纹不变（CI 核对）。

### 2.2 场景块写什么

全部是合成数据：名字带「演示」或「样例」，会员手机号沿用 199 号段，柜号用合成柜号，不带任何真实会员资料。所有业务都走正式接口（接待、挂账、入住、派钟、点单、刷卡上报）：命令在自己的进程里起一个不监听端口的应用，用演示店主 `linlan`（后台设置、模拟刷卡）与前台 `xiaozhou`（开班、接待、派钟、入住、点单、厨房、房态）的临时会话调用，结束时删掉会话。账单、流水、位置与各模块的自检天然一致。

### 2.3 时间

- 场景块走正式接口，按执行当时的时间写在当天的营业日，不随 `--previous-day` 前移。前台、结账两块照旧：营业日切换后 5 个半小时内执行会提示，加 `--previous-day` 把这两块整体放到前一个营业日（与 `seed-frontdesk-demo`、`seed-billing-demo` 同一套）。
- 已有演示库过几天再执行：场景块已经有了就跳过，不再补当天的。前几天的在店演示客人照旧在店，前台会提示跨营业日；技师在岗、估清按天清零，`demo-check` 过了准备的那个营业日就不核对这两项。要当天的新场景用 `demo-reset` 重建（2.7）。（待确认）

### 2.4 已有演示库：只补缺、不覆盖

- 前五块的「已灌过就跳过」不变。
- 场景块按编码、工号、名称认已有的东西：已有且一致的直接用，缺的补上，不改、不删已有的记录。
- 功能开关（客房、技师、餐饮、实时位置）只在从来没设过时打开（默认规则）。设过且打开的沿用；实时位置已设了别的接待区、技师休息区时也沿用，结束时提醒「人员位置可能与预期不同」。设过但关着的当冲突停下（2.5）：关着的功能接口不收，演示业务写不进去，原定「写入但列出关着的」做不到。（待确认）
- 已经有在用底图的不换，只提醒「样例房间可能不在这份底图上」。
- 演示账号沿用现有的（`linlan`、`xiaozhou` 等）：已有同名账号不改密码、不改岗位。

### 2.5 冲突就停下

场景块走正式接口、每个接口各自一个事务，没法整块放进一个事务里回滚，所以改成：**先只读核对全部冲突，有冲突什么都不写**，逐条列出冲突与处理办法；没有冲突才逐步写入，每一步都可以重复执行——已有的按编码、工号、名称认出来直接用；业务操作（接待、派钟、入住、开台、点单、刷卡）的操作编号与选中的手牌先记在 `settings.demo_showcase_progress`，中途出错（例如断电、某个接口拒绝）再执行一次会原样重发，系统按操作编号返回原结果，不会重复接待或派钟，接着补完。冲突例如：

- 台账里的 `T301` 已经被改成别的业态、换了楼层或停用；
- 工号 `D01` 是一位不带「演示」标记的技师，或演示技师被停用（名字、备注都是演示场景的、又是演示店主建的技师不算：那是上次在「建技师」与「打演示标记」两步之间中途退出留下的，再执行时补上标记）；
- 样例房号已被一间没挂样例空间的房间占用，或样例空间挂在别的房间上；
- 演示项目、菜品、档口、桌台、刷卡点被停用或改了用途（菜品设成「需要技师」、刷卡点装到别处）；
- 客房、技师、餐饮、实时位置有一项被后台关了；
- 有一份底图正在转换。

处理办法有两种：在页面上改名或停用冲突的那条，再执行一次；或者在独立演示库上用 `demo-reset` 重建。

### 2.6 核对：`demo-check`（只读）

```bash
node dist/server/cli.js demo-check
```

- 先跑一致性自检 `check`，再看五块都在（合成会员、合成物料、合成手牌、演示结账单、旧账样例导入）。
- 再按 `src/server/demo/showcase-expected.json` 核对场景块的关键状态：在店客人、客房房态、钟单、技师在岗、厨房出品、估清、桌台、在用底图与样例房间轮廓、平面图上的人员位置、刷卡点。
- 任何一项不一致都退出码 1，写明哪一项、期望与实际。演示库被人操作过（结了账、改了房态）之后会列出这些不同，这时要回到准备好的样子用 `demo-reset`。
- 只读；试用、正式环境拒绝（那里不该有演示数据，一致性自检用 `check`）。

### 2.7 重置：`demo-reset`（明确操作、先备份）

```bash
node dist/server/cli.js demo-reset --confirm <数据库名>
```

- 只在 `APP_ENV=development`、实例标识不是 `prod` / `shadow` / `test` 时可用，`--confirm` 必须写对当前数据库的名字。
- 先做一份备份（与 `backup` 命令同一套，写到 `BACKUP_PATH`，没设时 `BACKUP_DIR` 或 `./backups`），三项都满足才清库，否则什么都不动：
  1. `pg_dump` 成功写出备份文件（记下大小与 SHA-256，写在旁边的 `.json` 里）；
  2. 这份文件在临时库里完整恢复，并算出数据指纹与自检（比只看文件存在、大小、能列出目录更严）；
  3. 清库在一个事务里：先锁住这个库的所有表、挡住写入，再算一次现在的数据指纹，与备份恢复出来的相同才删——备份里就是现在的全部数据；备份之后有过写入（应用没停）的指纹对不上，拒绝；锁住之后再来的写入被挡在锁外，不会提交（Codex 复审 `174fa29` 后改：原来只比对备份前的指纹，备份到清库之间的写入会丢）。
- 之后清空这个库、重新执行 `demo-prepare`。
- 请先停掉应用：清库时等锁 10 秒拿不到（应用还连着）就放弃，库不变，备份已做好。
- 不提供跳过备份的开关。实测本机约 14 秒（备份核验 + 从零准备）。

### 2.8 环境保护（不变）

- 试用、正式环境（`APP_ENV=trial` / `production`）执行任何演示数据命令都拒绝，没有绕过开关。云上演练库是 `production`，同样拒绝。
- 库里有非合成的会员、手牌、库存时，各块按原规则拒绝。
- 仓库里不放真实会员余额、真实旧账、密钥或数据库备份。CI 只连它自己的临时库。

## 3. CI

新增 job「演示数据：准备、重复执行与核对」，与其他 job 同时开始，失败就让整次 CI 失败：

1. 临时库执行 `demo-prepare`（耗时写进 CI 摘要）→ `check` → `demo-check` → 记下数据指纹；
2. 再执行一次 `demo-prepare`：应全部跳过（输出里没有「已写入」），数据指纹不变；
3. 用 `APP_ENV=trial`、`APP_ENV=production` 执行 8 条演示数据命令（`demo-prepare`、`demo-check`、`demo-reset` 与五条 `seed-*`），都应因为环境被拒绝，数据指纹不变；
4. `demo-reset` 不写 `--confirm`、库名写错、实例标识是测试服时拒绝，数据指纹不变；
5. 启动应用，浏览器只读打开关键页面（`e2e/demo-showcase.spec.ts`，只在门店电脑尺寸跑，本机约 7 秒）：前台三位演示客人的手牌、房态看板、平面图的房态与人员、钟房服务中与待上钟、厨房待出与估清、旧账四份样例；这个用例要设 `E2E_DEMO_SHOWCASE=1` 才收（`playwright.config.ts`），平时的浏览器验收不跑它、用例总数也不算它；
6. 再跑一遍 `check` 与 `demo-check`；
7. 停掉应用，执行 `demo-reset --confirm yuzu_demo`：先备份并核验、再清库从零重建，`demo-check` 通过（耗时写进 CI 摘要）。

已有的空间台账、房态图、客房、钟房、餐饮、实时位置浏览器用例照旧跑，不重复堆一整套流程。浏览器验收的拆分与提速见 `docs/TESTING.md`。

## 4. 这一版不覆盖

- ERP 的费用报销、备用金、需求单、两级库存演示：库存、采购、应付已有一块，其余由各自的浏览器用例临时造。
- 退款单与券（RQ-006 还没做）。派对房等「开单即占用」（D39）在 v0.7.19 再加进场景块。
- 读卡器真机、刷卡上报的设备鉴权（RQ-001）。

## 5. 验证

- 新库：`demo-prepare` 一次准备完（本机约 13 秒）；`check` 49 项、`demo-check` 全过；`e2e/demo-showcase.spec.ts` 在门店电脑尺寸通过，跑完 `check`、`demo-check` 照样通过。
- 重复执行：第二次全部跳过（0.3 秒），数据指纹不变。顺带修了一处：演示数据灌数据时临时关掉「收款前必须先开班」，结束后原来只恢复了值、改了修改时间，库里有这条规则时每次执行指纹都会变；现在连同修改时间（按文字取回、精确到微秒）与修改人原样恢复。

- 环境保护：试用、正式环境下演示数据命令都拒绝；`demo-reset` 环境不是 development、实例标识是 prod / shadow / test、库名没写或写错时拒绝，备份没核验通过时不清库；核验通过时清库从零重建。
- 本机实测 `demo-reset`（真实备份）：备份 641 KB、临时库恢复核验通过，之后从零准备、`demo-check` 全过，共约 14 秒。
