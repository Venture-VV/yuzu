# 演示数据（飞书需求 RQ-007，v0.7.18）

店主 2026-11-02 在 PR #33 提出「完善演示数据，并让 CI 持续检查」，同日定 Q31 选 A：与 RQ-008（精简测试与 CI 等待，见 `docs/TESTING.md`）合成一版 v0.7.18，没有迁移；派对房等「开单即占用」（D39）排在之后的 v0.7.19。默认做法（待确认）见 `docs/PENDING_DECISIONS.md`「演示数据与 CI」。

目标：打开演示库就能体验较完整、互相关联的业务，不用每出一个新功能都临时手工补数据；准备、更新、核对都有一条命令，CI 每次在临时库里准备并核对。

## 1. 现状

- 五条命令各灌一块，要人工按顺序执行：
  - `seed-demo`：会员与项目；
  - `seed-inventory-demo`：库存、采购、应付；
  - `seed-frontdesk-demo`：747 张合成柜号与 13 位在店客人；
  - `seed-billing-demo`：结账、反结账、交班；
  - `seed-legacy-demo`：8–10 月旧账的合成样例。
- 每条都是「已灌过就跳过」；试用、正式环境一律拒绝。固定预期在 `src/server/demo/*-expected.json`。
- **没有覆盖**：客房、技师与钟房、餐饮与厨房、空间台账与底图（房态图）、实时位置。这几块的浏览器验收各自临时造数据，跑完再收回（例如实时位置的用例自己导入样例台账、打开开关、最后关掉），演示库里平时看不到。
- CI 只在浏览器验收之前灌一次、跑一遍一致性自检 `check`，不核对「灌出来的东西对不对、页面上看不看得到」，也不验证重复执行是否安全。

## 2. 做法

### 2.1 一条命令准备：`demo-prepare`

```bash
node dist/server/cli.js demo-prepare            # 新库从零准备；已有演示库只补缺
node dist/server/cli.js demo-prepare --previous-day   # 营业日切换后不久执行时，整体放到前一个营业日
```

- 依次执行：迁移 → 会员 → 库存 → 前台 → 结账 → 旧账 → **场景**（新增，见 2.2）→ 一致性自检 `check` → 演示核对 `demo-check`（2.6）。
- 每一块已经有了就跳过，缺的就补；最后打印一张表，写明每块是「已写入」「已存在，跳过」还是「补了哪些」。
- 原来的五条命令照旧可以单独用，`demo-prepare` 只是按固定顺序调用它们，再加上场景块。
- **两次执行结果一致**：第二次全部跳过，数据指纹不变（CI 核对）。

### 2.2 场景块写什么

全部是合成数据：名字带「演示」或「样例」，会员手机号沿用 199 号段，柜号用合成柜号，不带任何真实会员资料。所有业务都走正式接口（接待、挂账、入住、派钟、点单、刷卡上报），账单、流水与各模块的自检天然一致。

| 模块 | 写入 | 打开页面能看到 |
| --- | --- | --- |
| 空间台账与底图 | 导入 `docs/data` 的样例区域与空间（与 v0.7.14 起的验收同一份）；转换并启用样例底图（与 v0.7.15 起的验收同一份合成 DXF） | 后台「空间台账」；「客房 → 平面图」两层底图与房间轮廓 |
| 客房 | 客房功能（默认规则）、2 个房型；房间挂到样例空间：1 间在住（在店客人、带押金）、1 间待打扫、1 间维修，其余空闲 | 房态看板与平面图的房态颜色 |
| 技师与钟房 | 技师功能、4 位演示技师（工号 `D01`–`D04`）、3 位上牌；1 张服务中的钟单（客人在样例技师房）、1 张待上钟、1 张今天已下钟 | 钟房看板；平面图技师房「服务中」；看板「技师业绩」与提成 |
| 餐饮与厨房 | 餐饮功能、出品档口（厨房、水吧）、演示菜品；1 张开台点了菜；厨房出品屏有待出与已上的菜；1 道估清 | 点单、桌台、厨房出品屏、估清 |
| 实时位置 | 开关、接待区与技师休息区（样例区域）、2 个刷卡点（`DEMO-R1` 接待、`DEMO-R2` 装在样例房间）、项目所在区域；业务动作推出的位置，加 2 次模拟刷卡 | 平面图「人员」图层：区域人数、房间人数、在场名单、轨迹；后台「实时位置」可以接着模拟刷卡 |
| 会员、手牌、在店与已结账、交班 | 沿用现有四块 | 前台、结账记录、交班、日结、看板 |
| 旧账对照 | 沿用旧账合成样例 | ERP「旧账对照」 |

规则里还在「待确认」的（客房计费口径、技师服务类业态清单、实时位置的默认做法等），场景块一律按现在的默认值，不因构造样例另定规则。

### 2.3 时间

- 场景块写在执行当天的营业日。营业日切换后 5 个半小时内执行会提示，加 `--previous-day` 整体放到前一个营业日，与前台、结账演示数据同一套。
- 已有演示库过几天再执行：场景块已经有了就跳过，不再补当天的。前几天的在店演示客人照旧在店，前台会提示跨营业日。要当天的新场景，用 `demo-reset` 重建（2.7）。（待确认）

### 2.4 已有演示库：只补缺、不覆盖

- 前五块的「已灌过就跳过」不变。
- 场景块按编码、工号、名称认已有的东西：已有且一致的直接用，缺的补上，不改、不删已有的记录。
- 功能开关（客房、技师、餐饮、实时位置）只在从来没设过时打开。已经设过的不论开关都不改，结束时列出「这些功能关着：演示数据已写入，但页面上看不到，要看请到后台打开」。（待确认）
- 已经有在用底图的不换，只提醒「样例房间可能不在这份底图上」。
- 演示账号沿用现有的（`linlan`、`xiaozhou` 等）：已有同名账号不改密码、不改岗位。

### 2.5 冲突就停下

场景块整块在一个事务里，遇到对不上的记录整块回滚，什么都不改，并逐条列出冲突与处理办法。例如：

- 台账里的 `T301` 已经被改成别的业态；
- 工号 `D01` 是一位不带「演示」标记的技师；
- 样例房号已被一间没挂样例空间的房间占用。

处理办法有两种：在页面上改名或停用冲突的那条，再执行一次；或者在独立演示库上用 `demo-reset` 重建。

### 2.6 核对：`demo-check`（只读）

```bash
node dist/server/cli.js demo-check
```

- 先跑一致性自检 `check`。
- 再按 `src/server/demo/showcase-expected.json` 核对场景块的关键状态：在店客人、在住房间、服务中与待上钟的钟单、待出品的菜、在用底图与样例房间轮廓、平面图上有位置的人、旧账样例。
- 任何一项不一致都退出码 1，写明哪一项、期望与实际。

### 2.7 重置：`demo-reset`（明确操作、先备份）

```bash
node dist/server/cli.js demo-reset --confirm <数据库名>
```

- 只在 `APP_ENV=development`、实例标识不是 `prod` / `shadow` / `test` 时可用，`--confirm` 必须写对当前数据库的名字。
- 先做一份备份并核验通过（与 `backup` 命令同一套，写到 `BACKUP_DIR`），再清空这个库、重新执行 `demo-prepare`。
- 不提供跳过备份的开关。

### 2.8 环境保护（不变）

- 试用、正式环境（`APP_ENV=trial` / `production`）执行任何演示数据命令都拒绝，没有绕过开关。云上演练库是 `production`，同样拒绝。
- 库里有非合成的会员、手牌、库存时，各块按原规则拒绝。
- 仓库里不放真实会员余额、真实旧账、密钥或数据库备份。CI 只连它自己的临时库。

## 3. CI

新增 job「演示数据：准备、重复执行与核对」，与其他 job 同时开始，失败就让整次 CI 失败：

1. 临时库执行 `demo-prepare`（记下耗时）→ `check` → `demo-check` → 记下数据指纹；
2. 再执行一次 `demo-prepare`：应全部跳过，数据指纹不变；
3. 用 `APP_ENV=trial`、`APP_ENV=production` 执行，应被拒绝；
4. 启动应用，浏览器打开关键页面（`e2e/demo-showcase.spec.ts`，只在门店电脑尺寸跑，约 1 分钟）：前台在店客人、房态看板、平面图的房态与人员、钟房服务中、厨房待出品、旧账对照；
5. 再跑一遍 `check`。

已有的空间台账、房态图、客房、钟房、餐饮、实时位置浏览器用例照旧跑，不重复堆一整套流程。浏览器验收的拆分与提速见 `docs/TESTING.md`。

## 4. 这一版不覆盖

- ERP 的费用报销、备用金、需求单、两级库存演示：库存、采购、应付已有一块，其余由各自的浏览器用例临时造。
- 退款单与券（RQ-006 还没做）。派对房等「开单即占用」（D39）在 v0.7.19 再加进场景块。
- 读卡器真机、刷卡上报的设备鉴权（RQ-001）。

## 5. 验证（交付时填）

- 新库：`demo-prepare` 一次准备完；`check`、`demo-check` 全过；页面看到关键状态（门店电脑浏览器用例）。
- 重复执行：第二次全部跳过，指纹不变。
- 已有演示库：用上一版本的演示库只补场景块，不改已有记录；构造冲突时整块不写，并列出冲突。
- 环境保护：试用、正式环境拒绝；`demo-reset` 不写对库名、实例标识不对时拒绝，备份失败时不清库。
