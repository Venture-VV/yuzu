## 1. 3a 到期提醒（订阅消息）

**微信的规定**：这类门店只能用「一次性订阅」。顾客点一次「提醒我」、在微信的弹窗里同意，门店系统才能给这位顾客发**一条**这个模板的消息。长期订阅只给政务、医疗、交通、金融、教育这几类。

**顾客怎么用**
1. 在「我的券」的某张券、「会员卡」的会籍有效期、「余额与流水」的赠金旁，点「到期提醒我」，微信弹窗问同不同意。
2. 同意了：这张券（这段会籍、这批赠金）快到期时，门店系统发一条消息。点开消息进小程序对应的页面。
3. 不同意、或者在微信设置里关了：不发，页面照常用。

**规则**（默认，MP28）

| 提醒 | 什么时候发 | 消息里写 |
| --- | --- | --- |
| 券快到期 | 到期前 3 天 | 券名、到期日、「到前台结账时可用」 |
| 会籍快到期 | 会籍到期前 7 天；进入补充期当天再提醒一次（要再同意一次） | 现在的档阶、到期日、保级还差多少 |
| 赠金快到期 | 到期前 7 天 | 快到期的赠金金额、到期日 |

- 只在北京时间 10:00–20:00 之间发，赶上晚上的推到第二天上午（MP29）。
- 一次同意只发一条：发出去就用掉；发不出去（顾客拒收、模板被删）记下原因，不重试别的模板。
- 已经用掉、过了期、被作废的券，不再提醒；同意记录照样保留。

**做法**
- **门店系统**（小程序线）记两样，都只追加：
  - 顾客的同意：哪个微信、哪个模板、提醒哪张券或哪段会籍；
  - 待发的消息。
  - 每分钟扫一遍到点的，排进待发。
- **网关**：每 30 秒向门店系统取一批待发的消息，用 AppSecret 换来的接口凭据调微信的「发送订阅消息」接口，再把结果报回门店系统。
  - 方向与现在一样：网关连门店，门店不连网关；AppSecret 照旧只在网关。
  - 门店断网时消息在门店等着，连上再发。
- **模板**：店主在小程序后台「订阅消息」里，从公共模板库选三个模板，把模板编号填进 yuzu 后台「微信小程序 → 到期提醒」。没填的那种提醒不出现「提醒我」。
- **隐私指引**：发订阅消息只用到 openid，不另收信息；用户隐私保护指引照现在的写。

### 1.1 实现（2026-11-04，迁移 `050`）

**迁移 `050_mp_reminders_retention.sql`**（只建小程序线自己的表；同一个迁移另放解绑满 3 年清除，见 `docs/MP_PRIVACY.md`）

| 表 | 内容 |
| --- | --- |
| `mp_reminder_consents` | 顾客的同意，只追加：哪个微信（绑定记录）、哪位会员、哪种提醒（`coupon` 券、`membership` 会籍、`grace` 进补充期、`bonus` 赠金）、哪张券或哪天到期、哪个模板、哪天发、第几次。同一条绑定对同一样东西的同一种提醒，还在等、已发出的只记一条，再点返回原来那条；之前那条没发出、不用发了、或是按换掉的模板同意的，再同意一次记新的一条 |
| `mp_reminder_messages` | 每条同意最多一条消息：页面、字段、过了哪天就不用发。状态：排队 → 网关取走 → 发出 / 没发出 / 结果不明；到点时、网关来取时不用发的记「不发」与原因；要再试的隔一会儿再给。状态只能这样变、内容不能改、不能删，触发器兜底 |

**设置**：`settings` 的 `mp_reminder_rules`（开关、三个模板），带版本号保存。
- 每个模板：模板编号 + 每个字段填什么。字段名照模板详情（`thing1`、`date2`…），可以填的是名称、到期日、金额、提示、门店名，券没有金额。
- 字段按微信的格式写（不合格式的微信回 47003、整条发不出去）：`thing` 最多 20 个字（超了用「…」），`date` 写成「2026年11月20日」，`time` 写成那一天的「23:59」，`amount` 写成「¥12.00」，`phrase` 只要 5 个以内的汉字，`name` 10 个以内的汉字（不加省略号），`letter` 只有字母，`symbol` 5 个以内的符号。
- 会籍与补充期用同一个模板，三种提醒要三个不同的模板。没填模板的那种，小程序里不出现「提醒我」。

**设提醒**（`POST /api/mp/reminders`，网关 `/v1/reminders`，每个微信每分钟最多 20 次）
- 在一个事务里：这个微信的咨询锁（`mp_reminder:<openid>`）→ 绑定状态的共享锁 → 核对页面上的绑定版本号（之后解绑、换绑过的回 `BIND_STALE`）→ 同一个编号 → 核对模板与要提醒的东西 → 写同意。
- 拒绝的几种：
  - 模板刚换过：`TEMPLATE_CHANGED`；
  - 到期日对不上页面上的：`REMINDER_TARGET_CHANGED`；
  - 券用掉、作废、过期，L0，已经在补充期里，没有会到期的赠金：`REMINDER_TARGET_GONE`；
  - 不是自己的券：404；会员卡合并掉、停用的：照领券的说法。
- 到期日都是**最后能用的那个营业日**：券的有效期到、会籍周期的最后一天、补充期的最后一天；赠金在到期那天营业日开始时作废，最后能用的是前一个营业日（小程序写「¥X 赠金用到 M月D日」）。
- 哪天发：
  - 券：到期前 3 天；
  - 会籍：到期前 7 天；
  - 补充期：周期最后一天的下一天；
  - 赠金：最后能用的那一天的前 7 天。
  - 已经过了那天的，当天发。
- 结果不确定时小程序原样重提（同一个编号返回同一条），不用确认作废：晚到生效也是顾客自己要的提醒，不会记两条。

**每分钟排期**（门店系统的定时任务，与线上充值的补查互不等；日子都按营业日）
- 网关取走以后 5 分钟没回报的记「结果不明」，不再发第二次。
- 一条出错不挡后面的，下一分钟再排它；后台写着到了那天还没排成消息的有几条。
- 到期提醒开着、北京时间 10:00–20:00 之间：把到了那天的同意排成消息，字段按那时的情况算：
  - 会籍按那天推算（到期没处理的照规则推到那天），保级还差多少按本档门槛的 60% 算；
  - 补充期写补充期到哪天；
  - 赠金写那一天作废的还剩多少。
- 那时已经不用发的记「不发」与原因：解绑、合并、停用，券用掉、作废、过期，会籍续上或变过，没进补充期，赠金用完，模板换过。

**网关**（`src/gateway/reminders.ts`）
- 每 `MP_REMINDER_SECONDS` 秒（默认 30，0 不发）向门店系统取一批（最多 20 条）：`POST /api/mp/gateway/reminders/lease`，只认网关密钥，10:00–20:00 以外不给。
  - 门店系统取的时候再核对一次：解绑、合并、停用的，过了到期日的，排好以后两天没发出去的，券用掉、作废的，记「不发」；要再试的到了时间才给。
  - 带批次号：门店那边取好了、回答路上丢了的，下一轮带着同一个批次号再要，门店把那一批原样再给（还在期限里的）。
  - 回答里带这一批的期限（5 分钟）：快到期限（剩 30 秒）就不再开始发。
- 一条一条发：顾客拒收、模板不对只是这一条的事；微信忙、超时、连不上就停下这一批，剩下的没发、报「再试」，免得微信出问题时把顾客的同意都耗成「结果不明」。
- 用 AppSecret 换来的接口凭据调微信的「发送订阅消息」，凭据失效时重取一次。
- 回报结果：`POST /api/mp/gateway/reminders/report`，只认这一次取走用的凭据。
  - `sent` 发出；
  - `failed` 微信明确拒绝（43101 顾客拒收或次数用完，openid、模板、字段、页面不对，内容有敏感词）；
  - `retry` 没发出去（微信忙、频率限制、连不上、拿不到凭据），回到排队、隔一会儿再给（第 1 次以后隔 5 分钟、第 2 次以后隔 10 分钟），第 3 次还不行记没发出；
  - `unknown` 发了没收到回音（超时、半路断开），不再发。
- 回报送不到门店的，门店过了期限记结果不明。
- `MP_SUBSCRIBE_STATE` 决定点开消息跳到哪一版：默认 `formal` 正式版，测试网关配体验版时填 `trial`。

**后台「微信小程序 → 到期提醒」**（新权限 `mp.reminder`：店主、店总）
- 开关，三种模板与字段，结果待确认照其他开关；
- 最近 30 天同意了多少、各状态多少、还没到发的时候的有多少；
- 网关最近一次来取消息的时间：太久没来说明网关没开或连不上门店；
- 最近 50 条消息与原因。

**小程序**
- 「我的券」可以用的券、会员卡的会籍、余额页的赠金旁边有「到期提醒我」。会籍的设好了，才出现「进补充期也提醒我」。
- 点按里先弹微信的确认（`wx.requestSubscribeMessage`），同意了才发请求；设好的写「已设提醒」。
- 设提醒先存在手机上（存不了不发），记下了或门店系统明确拒绝才删；结果不确定的下次打开这几页时原样重提。

**测试**
- `tests/mp-reminders.test.ts`：设置、四种提醒、拒绝的各种、排期的时间与字段、发送的四种结果、不发的各种、开关、后台、自检。

## 2. 3b 邀请好友

**顾客怎么用**
1. 邀请人：「我的 → 邀请好友」，看到这个月还能邀请几次、好友能体验的档阶与天数。
   - 例：「L2·初，7 天」。
   - 不够条件的写原因：L1 及以下不能邀请、本月次数用完。
2. 点「邀请好友」→ 分享小程序卡片给微信好友。卡片带一个邀请码，7 天内有效，只能用一次。
3. 好友点开卡片 → 小程序登录 → 用微信手机号快速验证。
   - 已有会员：现在的档级要低于体验的档级。
   - 没有会员档案：当场建档，与 v0.7.25 一样，L0、渠道「老带新」、发开卡礼。姓名请好友自己填。
4. 门店系统调主线的入口，建临时身份。
   - 好友看到：「体验中：L2·初，至 11 月 11 日」。
   - 邀请人看到：「已邀请：王*（体验中）」。

**规则**
- 照 v0.7.25：
  - 每位会员每月 1 次；
  - 受邀人 12 个月内只能被邀请一次；
  - 同一时间只有一个临时身份；
  - 体验期满、转正、撤销都照主线。
- 小程序加的规则：
  - 邀请码 7 天有效、只能用一次；没用的邀请人可以收回（MP30）。
  - 发出去还没用的邀请码占着本月的次数；收回、过期的退回次数（MP30）。
  - 受邀人必须用微信手机号快速验证，不能手填号码。
- 赠送记名会籍（QY-042）默认先不放进小程序，仍在前台办（MP31）。

**要主线加的**：`createTrialInviteFromMp(tx, deps, { inviterId, invitee: { phone, name? }, claimKey })`。
- 规则、拒绝码与加锁顺序照 v0.7.25 的「邀请体验」；
- 经办人是系统账号「小程序」；
- 同一个 `claimKey` 再调用返回第一次的结果。

**小程序线**
- 邀请码表（迁移号用前登记）：邀请人、码、到期、状态、用的人、临时身份；
- 网关的分享与领取接口；
- 「我的 → 邀请好友」与领取页；
- 后台看邀请记录。

### 2.1 实现（2026-11-04，迁移 `061`，接主线 v0.7.28 的 `createTrialInviteFromMp`）

**迁移 `061_mp_invites.sql`**（只建小程序线自己的表）

| 表 | 内容 |
| --- | --- |
| `mp_invites` | 邀请码：哪位会员（哪条绑定）发的、码（10 位，不用容易看错的 0、1、I、O）、发起时好友能体验的档阶（只做显示，领取时以主线那时的规则为准）、7 天内有效、状态（待领取 → 已领取 / 已收回；过了有效期没人领的按时间算过期）。好友领了记下好友的会员、好友这个微信的绑定（绑上了的话）与主线建的临时身份。码、邀请人、有效期不能改，结束了的不能再改，不能删，触发器兜底。不存微信标识 |
| `mp_op_fences` | 加一类 `mp_invite`：好友领取的结果不确定时确认作废 |

**设置**：`settings` 的 `mp_invite_rules`（开关），带版本号保存，默认关。

**邀请人**（`GET`、`POST /api/mp/invites`，`POST /api/mp/invites/:code/revoke`；网关 `/v1/invites…`，发起、收回每个微信每分钟 20 次）
- 能不能邀请、好友能体验的档阶与体验到哪天、本月用了几次：照主线的 `trialOptions`，与前台的「邀请体验」同一套。
- 发出去还没人领、还在有效期里的占着本月的次数；收回、过期的退回（MP30）。
- 发一个码在一个事务里：这个微信的咨询锁（`mp_invite:<openid>`）→ 绑定状态的共享锁 → 核对绑定版本号（`BIND_STALE`）→ 同一个编号返回同一个码 → 开关、会员卡、次数 → 写邀请码。
- 结果不确定时小程序下次打开邀请页原样重提：晚到生效也只是多一个待领取的码，邀请人在列表里看得到、能收回。
- 收回：只能收回自己发的、还没人领的；与领取取同一个码的咨询锁，两边不会都成。

**好友**（`GET /api/mp/invites/:code`，`POST /api/mp/invites/:code/claim`，`POST /api/mp/invites/claim/abandon`）
- 看邀请：谁请的（名字只露第一个字）、能体验什么、到哪天有效、是不是自己发的、这个微信绑没绑会员。
- 网关先用手机号快速验证的 code 换手机号，再转给门店系统，与绑定一样每个微信每分钟 10 次。
- 领取在一个事务里：这个码的咨询锁 → 这个微信的绑定锁（排他，可能要绑定）→ 作废登记 → 邀请码一行 → 同一个编号重提返回第一次 → 核对绑定版本号 → 开关、码的状态 → 已经绑了会员的，验证的手机号要是这位会员的 → 主线的 `createTrialInviteFromMp`（同一个码只建一次临时身份）→ 这个微信还没绑定、这位会员也没绑别的微信的，顺带绑上 → 记下领取。
- 拒绝的几种：被领走了 `INVITE_USED`、收回了 `INVITE_REVOKED`、过期了 `INVITE_EXPIRED`、自己发的 `TRIAL_SELF`、档级不够低或 12 个月内被邀请过 `TRIAL_INVITEE`、还不是会员又没填姓名 `NAME_REQUIRED`、这个微信绑的会员不是这个手机号 `OPENID_BOUND`。主线的拒绝改成写给好友看的话。
- 手机号快速验证的 code 只能用一次，原样重提不了：结果不确定时小程序马上请门店系统「确认作废」这个编号，已经领到了回那一次，没有就登记作废、可以重新领；连作废都发不出去时记录保留，确认之前不能再领。

**后台「微信小程序 → 邀请好友」**（新权限 `mp.invite`：店主、店总）：开关；最近 30 天发起的各状态多少；最近 50 份邀请（谁发的、谁领的、体验到哪天）。

**小程序**：「我的 → 邀请好友」（还能邀请几次、好友能体验什么、发出去的邀请与收回；「发给好友」用分享卡片）；好友打开卡片的领取页（手机号快速验证，还不是会员的填姓名）。

**测试**：`tests/mp-invites.test.ts`、`tests/gateway.test.ts`（邀请好友）、`miniprogram/tests/invites.test.ts`。

## 3. 3c 扫码点餐

**顾客怎么用**
1. 在店里（已经开了手牌）打开小程序「点餐」，或者扫餐厅桌上的码。
2. 看菜单：店主勾了「小程序可点」的菜品，估清的写「今天没有了」。
3. 选好、确认 → 进厨房出品单，挂在自己的手牌账单上。扫了桌上的码的，出品单写这张桌，送餐照桌号。
4. 「我的账单」里能看到点了什么、多少钱。结账照旧在前台，跟服务员点的一样。

**谁能点**（MP32）
- 默认只给绑定了会员、而且这位会员有在店手牌（来访没结束）的微信。
- 手牌没挂会员的客人、同行的非会员，仍请服务员点。

**规则**（默认，MP33）
- 一单最多 20 份、¥500；超过的请服务员点，防止点错。
- 下单走「结果待确认」：同一个编号重提只下一次。
- 顾客自己不能退菜；要退请服务员，照现有的退菜。

**要主线加的**：`orderFoodFromMp(tx, deps, { memberId, items: [{ itemId, quantity, note? }], tableCode?, claimKey })`。
- 按会员找在店的来访与账单（没有回 `NO_OPEN_VISIT`）；
- 照餐饮点单记明细、扣估清、建出品单，锁的顺序照现在的「账单 → 明细 → 估清 → 出品单」；
- 经办人是系统账号「小程序」；
- 同一个 `claimKey` 只下一次；
- 只读的菜单接口：小程序可点的菜品、价格、估清。

**小程序线**
- 桌码：后台生成，码里只有桌号与一段签名，拍照转发到店外也没用，因为还要有在店手牌；
- 点单记录；
- 网关接口；
- 小程序「点餐」与「我的账单」；
- 后台设哪些菜品小程序可点。

### 3.1 实现（2026-11-04，迁移 `062`，接主线 v0.7.28 的 `orderFoodFromMp`）

**迁移 `062_mp_food.sql`**（只建小程序线自己的表）

| 表 | 内容 |
| --- | --- |
| `mp_food_orders` | 小程序下的每一单：哪条绑定、哪位会员、挂在哪次来访（手牌）、出品单号、送到哪张桌、合计，下单那一刻点了什么（名称、份数、金额、口味备注；账以主线的账单明细为准）。下单的操作编号唯一。只追加，不能改、不能删，触发器兜底。不存微信标识 |
| `mp_op_fences` | 加一类 `mp_food`：下单的结果不确定时确认作废 |

**设置**：`settings` 的 `mp_food_rules`（开关、小程序可点的菜），带版本号保存，默认关、一道菜都没勾。
- 可点的菜只能在「进厨房的菜」里勾（后台「餐饮」里挂了出品档口的）；菜名、价格、估清照「餐饮」。
- 扫码点餐开着、餐饮功能也开着，「我的」才有「点餐」「我的账单」。

**桌码**
- 18 位数字：`71` + 桌台编号（6 位）+ 签名（10 位）。签名用门店系统的 `MP_CODE_SECRET`（与会员码同一个密钥，签的内容不同），网关不存密钥，签名在门店系统核对。
- 与会员码（8、9 开头，16、19 位）、手机号（11 位）不会混；前台扫码盒扫到桌码认不出会员，不会串。
- 码里只有桌台编号：桌台改名照样认，停用的不认。拍照带出店也点不了：还要这位会员有在店手牌。
- 后台按启用的桌台生成，A4 一页四张打印，沿虚线裁开放在桌上；没配 `MP_CODE_SECRET` 时没有桌码，顾客照样能点，只是不写桌号。
- 现在的码里只是一串数字，要先打开小程序再扫；以后域名定了、在微信后台配了「扫普通链接二维码打开小程序」，码可以换成带这串数字的链接，微信扫一扫直接打开点餐页（小程序已经认得打开参数里的 `q`、`scene`、`t`）。

**点餐页**（`GET /api/mp/food/menu?table=<桌码>`；网关 `/v1/food/menu`，桌码格式不对网关先拒）
- 开没开、现在能不能点（没绑定、会员卡合并或停用、没有在店手牌都写原因）、在店手牌、扫到的桌（桌码不对、桌停用写原因，照样能点、不写桌号）。
- 可点的菜：勾了的、进厨房的；今天的估清（0 写「今天没有了」，剩 5 份以内写份数）；只限男宾或女宾的，只列这张手牌能点的。
- 一单的上限（MP33）：20 份、¥500。

**下单**（`POST /api/mp/food/orders`，新下 201、同一个编号重提 200；网关每个微信每分钟 20 次）
- 在一个事务里：这个微信的点餐咨询锁（`mp_food:<openid>`，与确认作废串行）→ 作废登记 → 绑定状态的共享锁 → 同一个编号重提返回第一次（只认下单的那条绑定）→ 核对绑定版本号（`BIND_STALE`）→ 开关、会员卡、可点的菜、桌码的签名 → 主线的 `orderFoodFromMp`（它自己的编号锁 → 来访 → 账单 → 估清 → 出品单，照点单页下单；经办人系统账号「小程序」）→ 记下这一单。
- 拒绝的几种：没勾的菜 `DISH_NOT_OPEN`、桌码不对或桌停用 `TABLE_CODE_INVALID`、没有在店手牌 `NO_OPEN_VISIT`、估清不够 `DISH_SOLD_OUT`、价格刚改过 `PRICE_CHANGED`、超过上限 `MP_ORDER_LIMIT`、只限男宾或女宾 `ITEM_GENDER`、手牌刚变过 `VISIT_CHANGED`、账单已结 `BILL_CLOSED`、没绑定 `MP_NOT_BOUND`。拒绝时什么都不留（账单、估清、出品单、点单记录都不变）。
- 结果不确定时小程序马上请门店系统「确认作废」这个编号（`POST /api/mp/food/orders/abandon`）：已经下了回那一单；还没有就登记作废，原来那次请求之后即使到达也不下，可以重新下。连作废都发不出去时记录保留，确认之前不能再下（免得点重）。别的微信用不了这个编号。
- 顾客自己不能退菜（MP33）：退菜请服务员在点单页作废明细，照现有的规矩。

**我的账单**（`GET /api/mp/food/bill`）：主线的 `mpOpenBill`——在店手牌账单上还有效的明细（名称、份数、金额，进厨房的菜写出品状态）与原价合计；会员折扣、券在前台结账时算。没有在店手牌时写原因。

**后台「微信小程序 → 扫码点餐」**（新权限 `mp.food`：店主、店总）
- 开关、可点的菜（按档口分组，可以一组都勾），结果待确认照其他开关；餐饮功能关着时提示先开；
- 桌码：每张启用的桌台一个，预览、A4 打印；
- 今天（按手牌的营业日）小程序下了几单、合计，最近 50 单（谁、哪个手牌、送到哪、出品单号、点了什么）。

**小程序**：「我的 → 点餐」（扫桌码、按档口分组的菜单、加减份数与口味备注、底部合计与下单、下好了写送到哪张桌）；「我的 → 我的账单」（下拉刷新）。

**测试**：`tests/mp-food.test.ts`、`tests/gateway.test.ts`（扫码点餐）、`miniprogram/tests/food.test.ts`、`miniprogram/tests/qr.test.ts`（后台打印桌码的二维码与小程序的同一份编码器、扫得出来）。

## 4. 3d 预约技师与派对房

**顾客怎么用**
1. 预约技师：选项目 → 选技师（或「不指定」）→ 选日期与时段 → 提交 → 「待门店确认」。
   - 前台确认后：「已预约」，可以再点「到店提醒我」。
2. 预约派对房：选房型 → 日期、开始时间、时长（按房型的档）→ 人数 → 提交 → 门店确认。
3. 到店：前台在预约看板上点「到店」，转成钟单（技师）或开使用单（派对房，v0.7.19 的「开单即占用」）。
4. 取消：开始前 2 小时以前可以自己取消；之后请打电话给门店。

**规则**（默认，待店主定）

| 事项 | 默认 | 编号 |
| --- | --- | --- |
| 能约多远 | 当天到 7 天后；按半小时一格 | MP34 |
| 每人同时 | 最多 2 个没到店的预约 | MP34 |
| 确认 | 前台人工确认（默认）；不确认的到开始前 1 小时自动取消并通知 | MP35 |
| 订金 | 先不收；以后要收用 2a 的线上付款，取消时原路退回 | MP36 |
| 爽约 | 过了开始时间 30 分钟没到店记爽约；90 天内爽约 3 次，30 天内不能在小程序预约 | MP37 |

**要主线新做的**（预约模块，主线排期）
- **预约单**：项目、技师或房间、开始与结束、人数、状态（待确认、已预约、已到店、已取消、爽约）、来源（前台、电话、小程序）。
- **可约时段**：
  - 按技师的排班、已有的预约、不能约的时段算；
  - 派对房按房间的营业时间、已有的预约与使用单算。
- **前台预约看板**：确认、改时间、到店转钟单或使用单、取消、记爽约。
- **给小程序的入口**：可约时段（只读）、`createBookingFromMp`、`cancelBookingFromMp`，带 `claimKey`、经办人系统账号「小程序」。

**小程序线**
- 小程序的预约页、「我的预约」、到店提醒（3a 的订阅消息）；
- 网关接口；
- 后台设哪些项目、房型可在小程序预约。
